Old 2.4a · Windows & Java Threads

Present in older notes; not listed in the new syllabus

The other two thread libraries named in the course PDF, alongside Pthreads (§2.4).

Win32 threads

The Windows API implements the one-to-one model (§2.3): every user-level thread created through the Win32 library is backed by its own kernel thread, so a blocking call in one thread does not stop the others and threads can run in parallel on a multicore machine. Each Windows thread consists of:

  • a thread ID,
  • a register set representing the processor state,
  • separate user and kernel stacks (the kernel stack is used when the thread runs in kernel mode),
  • a private storage area used by run-time libraries and dynamic-link libraries (DLLs).

The register set, the two stacks and the private storage area together are called the context of the thread. The primary data structures of a Windows thread are:

StructureFull nameLives inHolds
ETHREADExecutive thread blockKernel spacePointer to the owning process, start address of the thread routine, pointer to the KTHREAD
KTHREADKernel thread blockKernel spaceScheduling and synchronization information, the kernel stack, pointer to the TEB
TEBThread environment blockUser spaceThread id, user-mode stack, thread-local storage

ETHREAD and KTHREAD are only reachable in kernel mode; the TEB is the one structure user-mode code can touch.

Java threads

Threads are the basic model of program execution in Java: every Java program has at least one thread of control (the one running main()). Because the JVM sits on top of a host operating system, Java threads are mapped to whatever thread model the host provides (one-to-one on Windows and Linux). The Java API offers a rich set of thread-management features. There are two techniques for creating a thread:

  1. Extend the Thread class and override its run() method.
  2. Implement the Runnable interface, which declares a single method public void run(), and pass an instance to a Thread object.
// Technique 2 — Runnable
class Worker implements Runnable {
    public void run() { System.out.println("I am a worker thread"); }
}
Thread t = new Thread(new Worker());
t.start();   // allocates memory, initializes the thread, and calls run()
t.join();    // parent waits for the worker to finish
Exam tip

Never call run() directly — that just executes it as an ordinary method in the caller's thread. start() is what creates the new thread of control and then invokes run(). Creating threads via Runnable is usually preferred because Java has single inheritance.

Old 2.4b · Threading Issues

Present in older notes; not listed in the new syllabus

Six problems that appear the moment a program has more than one thread — a standard long-answer question.

1. The fork() and exec() system calls

fork() creates a separate, duplicate process. The question is what happens if one thread of a multithreaded program calls it. Two versions of fork() exist on different systems: one duplicates all threads of the parent, the other duplicates only the thread that invoked fork(). If a thread calls exec(), the program named in its parameter replaces the entire process — including all threads.

Which to use: if exec() is called immediately after fork(), duplicating all threads is unnecessary because they would be wiped out anyway, so duplicating only the caller is enough. If the child does not call exec(), it should duplicate all threads.

2. Thread cancellation

Terminating a thread before it has completed — for example when several threads search a database and one finds the answer, or when a user presses Stop in a browser. The thread to be cancelled is the target thread. Two cases:

TypeHow it worksDrawback / advantage
Asynchronous cancellationOne thread terminates the target thread immediately.May leave shared data inconsistent or fail to reclaim resources the target was holding (locks, files).
Deferred cancellationThe target thread periodically checks whether it should terminate, at safe cancellation points.Orderly clean-up is possible; this is the default in Pthreads.

3. Signal handling

In UNIX a signal notifies a process that a particular event has occurred. Every signal follows the same pattern: (1) it is generated by an event, (2) it is delivered to a process, and (3) once delivered it must be handled by a signal handler.

Synchronous signals
Delivered to the same process that performed the operation that caused them. E.g. illegal memory access, division by 0.
Asynchronous signals
Generated by an event external to the running process. E.g. the user pressing <ctrl><c>, a timer expiring.

Each signal is handled by one of two handlers: the default handler (run by the kernel) or a user-defined handler that overrides the default. In a single-threaded program delivery is trivial — the signal goes to the process. In a multithreaded program there are four options:

  1. Deliver the signal to the thread to which it applies (natural for synchronous signals).
  2. Deliver the signal to every thread in the process (e.g. a terminate-process signal).
  3. Deliver the signal to certain threads in the process.
  4. Assign a specific thread to receive all signals for the process.

4. Thread pools

Creating a new thread for every request has two problems: the time to create it (which may exceed the time to do the work) and, with unlimited threads, the risk of exhausting CPU time and memory. A thread pool creates a number of threads at process start-up and places them in a pool, where they sit waiting for work.

Fig 1. Thread pool — a request is handed to an idle pooled thread, which returns to the pool when the service completes.

Advantages: servicing a request with an existing thread is usually faster than creating a new one; the pool bounds the number of threads alive at any moment. The pool size can be tuned from the number of CPUs, the amount of memory and the expected number of concurrent client requests (or adjusted dynamically).

5. Thread-specific data

Threads share their process's data — one of the benefits of multithreading (§2.1). Sometimes, however, a thread needs its own copy of certain data: thread-specific data. Example: in a transaction-processing system each transaction is serviced by a separate thread and each is given a unique transaction identifier; thread-specific data associates each thread with its identifier. Thread libraries (Pthreads, Win32, Java) provide support for it; it is similar to static data but unique to each thread.

6. Scheduler activations

The many-to-many and two-level models (§2.3) need communication between the kernel and the user-level thread library so that the application always has the right number of kernel threads. The usual scheme is the scheduler activation: the kernel provides the application with a set of virtual processors (lightweight processes, LWPs), and the kernel informs the thread library of certain events through upcalls — a communication mechanism from the kernel to the thread library, handled by an upcall handler. For example, when a user thread is about to block, the kernel makes an upcall telling the application, and allocates a new virtual processor so the library can run another thread on it; when the blocking event finishes, another upcall tells the library the thread is runnable again.

Exam tip

"Explain the various threading issues" is usually 8–10 marks: name all six — fork/exec, cancellation (asynchronous vs deferred), signal handling (4 delivery options), thread pools, thread-specific data, scheduler activations — with one or two lines each.

2.1

CPU Scheduling — Basic Concepts

Why scheduling exists, the CPU–I/O burst cycle it exploits, and the four moments a scheduling decision can happen.

The multiprogramming objective

On a single-processor system, only one process runs at any instant; every other process waits for the CPU. Left unmanaged, a process that blocks for I/O would leave the CPU idle and wasted. The objective of multiprogramming is to keep some process running at all times: several processes are kept in memory simultaneously, and whenever one process has to wait, the OS takes the CPU away from it and hands it to another ready process.

The CPU–I/O burst cycle

Process execution alternates between two states: a CPU burst (executing on the CPU) and an I/O burst (waiting on I/O). A process starts with a CPU burst, then an I/O burst, then another CPU burst, and so on, until a final CPU burst ends with a system request to terminate. CPU-scheduling algorithms exist entirely because of this cycle — every time a process's CPU burst ends (or is cut short), there's a decision to make about who runs next.

Fig 2. The CPU–I/O burst cycle — process execution alternates between CPU bursts and I/O waits until termination.

Distribution of CPU bursts. Measured burst durations follow a characteristic curve (the PDF's histogram): the frequency peaks sharply at very short bursts of about 2 ms (roughly 150 occurrences), falls to about 30 at 4 ms and is almost zero beyond about 8 ms, with a long thin tail out to 40 ms. In other words the curve is exponential/hyper-exponential: a program has many short CPU bursts and a few long ones. An I/O-bound program typically has many short CPU bursts; a CPU-bound program has a few long ones. This is why the choice of scheduling algorithm — and, for Round Robin, the quantum (≥80% of bursts should fit inside it) — matters.

The CPU scheduler and preemption

Whenever the CPU goes idle, the OS's short-term scheduler (CPU scheduler) picks one process from the ready queue and allocates the CPU to it. The ready queue need not be FIFO — it can be a priority queue, a tree, or an unordered list; conceptually all ready PCBs are just lined up waiting for a turn. A scheduling decision can arise at exactly four points:

  1. A process switches from running → waiting (e.g. an I/O request).
  2. A process switches from running → ready (e.g. an interrupt occurs).
  3. A process switches from waiting → ready (e.g. I/O completes).
  4. A process terminates.

When scheduling happens only at points 1 and 4, the scheme is non-preemptive (cooperative): once given the CPU, a process keeps it until it terminates or blocks itself. When scheduling can also happen at points 2 and 3, the scheme is preemptive: the OS can yank the CPU away from a running process. Preemption is what makes time-sharing possible, but it introduces real risk — if two processes share data and one is preempted mid-update, the other may read an inconsistent state (this is exactly the race-condition problem Unit 3 tackles in depth).

Fig 3. The four preemption decision points, and the dispatcher — the module that actually hands the CPU to whichever process the scheduler picked.

The dispatcher is the module that gives control of the CPU to the process the scheduler selected: it switches context, switches to user mode, and jumps to the correct location in the user program. The time this takes is the dispatch latency — it should be as fast as possible, since it runs on every single process switch.

Scheduling Criteria

The five measures used to compare scheduling algorithms, and which direction "better" points for each.

Different scheduling algorithms favour different classes of processes, so comparing them needs agreed criteria. All five below appear regularly as define-and-explain questions on their own.

CriterionDefinitionGoal
CPU utilizationFraction of time the CPU is actually busy (0–100%; realistically 40% lightly-loaded to 90% heavily-loaded).Maximize
ThroughputNumber of processes completed per unit time.Maximize
Turnaround timeTotal time to execute a process = time waiting to get into memory + waiting in the ready queue + executing on the CPU + doing I/O.Minimize
Waiting timeSum of the periods a process spends waiting in the ready queue specifically — the only part of turnaround time the scheduler actually controls.Minimize

Exam tip

"Discuss the scheduling criteria" (asked directly, 5 marks) wants all five, each with its definition and its optimization direction — don't just list definitions. Note precisely: turnaround time = full journey (arrival to completion); waiting time = turnaround time minus burst time, i.e. only the ready-queue portion. Mixing these two up is the single most common mistake in scheduling numericals.

Reference: Silberschatz, Galvin & Gagne, ninth edition — §6.2 — CPU scheduling.

Assumptions for these scheduling calculations

The worked tables assume one CPU burst per process, no I/O during that burst and no scheduling overhead unless stated. Then turnaround = completion − arrival and waiting = turnaround − burst. For a process that also waits for I/O, that I/O time is not time spent in the ready queue and must be accounted for separately.

Clarifying an ambiguous point — the exact long-run RR value

FCFS repeats exactly every 100 ms, so 60% is exact. RR does not repeat its first cycle. Later cycles depend on a detail the question does not give: when a process returns from I/O at the same instant another is preempted, which one is queued first? A simulation over thousands of milliseconds settles at 6/11 ≈ 54.5% if the returning process goes first, and at 60% if the preempted process goes first. In the exam, write the 50% first-cycle method above and state your queue-order assumption. The conclusion (RR ≤ FCFS here) holds either way.

2.3

FCFS Scheduling

The simplest scheduler — and the clearest demonstration of why simple isn't always good.

First-Come, First-Served (FCFS) allocates the CPU to whichever process requests it first, implemented with a plain FIFO queue: a new process's PCB is linked to the tail of the queue, and whenever the CPU frees up, it goes to the process at the head. FCFS is non-preemptive — once a process has the CPU, it keeps it until that CPU burst completes, it blocks, or it terminates.

FCFS is trivial to implement, but average waiting time is highly sensitive to arrival order, not just to the workload itself — the exact same three processes can give wildly different average waits depending on which one happens to arrive first.

Fig 4. The convoy effect — when a long process arrives first, every later process waits behind it; average waiting time drops from 17ms to 3ms purely by reordering arrivals.
The convoy effect

When several short processes queue up behind one long process, all of them wait far longer than their own burst time would suggest — CPU and device utilization both suffer while everyone waits for the big process to release the CPU. It's the headline weakness of FCFS, and the direct motivation for SJF (§2.4).

Same three processes, same total work — just a 1ms shift in who arrives first — and average waiting time falls from 26.33ms to 1.33ms, a ~20× improvement. This is the convoy effect in its starkest form: P1 and P2 are barely delayed at all once they're not stuck behind P3, while P3 waits 0ms in the original order and 3ms in the modified order. Yes — the convoy effect clearly appears in the original ordering and is eliminated in the modified one.

SJF Scheduling

Choose the shortest ready burst; SRTF additionally reacts to arrivals. Optimality statements require assumptions about which jobs are available and whether bursts are known.

Shortest Job First (SJF) allocates the CPU to whichever ready process has the smallest next CPU burst — the more precise name is the "shortest-next-CPU-burst algorithm," since scheduling depends on the length of the process's next burst, not its total remaining lifetime. Ties break by FCFS (or, per this course's convention, by the lower process ID). SJF comes in two forms: non-preemptive (once started, a process runs to completion of that burst) and preemptive — better known as Shortest-Remaining-Time-First (SRTF) — where a newly-arrived process with a shorter remaining burst immediately preempts whatever's running.

Round Robin

FCFS with a stopwatch — fair, preemptive, and built for time-sharing. Includes a genuine "spot the error" worked example.

Round Robin (RR) is designed specifically for time-sharing systems. It behaves like FCFS but adds preemption: a small time quantum (typically 10–100ms) is defined, and the scheduler cycles through the ready queue giving each process at most one quantum before moving on. If a process's burst is shorter than the quantum, it releases the CPU voluntarily and the scheduler moves to the next process immediately. If its burst is longer, the timer fires, a context switch happens, and the process goes to the tail of the ready queue.

Fig 6. Round Robin's ready queue is effectively circular — each process gets one quantum, then (if unfinished) rejoins the back of the line.

Quantum-size tradeoffs

Performance depends heavily on the quantum size. If the quantum is very large, RR degenerates into FCFS. If it's very small (e.g. 1ms), context-switch overhead dominates and throughput collapses. A rule of thumb: 80% of CPU bursts should be shorter than the time quantum. RR typically has a higher average turnaround time than SJF, but a much better response time — the tradeoff that makes it the right choice for interactive/time-sharing systems specifically.

Priority Scheduling

SJF generalized to any notion of importance — plus the starvation problem it introduces, and a genuinely GATE-famous worked example.

In priority scheduling, each process gets a priority, and the CPU goes to the ready process with the highest priority. Equal-priority processes are scheduled FCFS. SJF is literally a special case of priority scheduling where the priority is the inverse of the predicted next CPU burst (longer burst → lower priority). Like SJF, priority scheduling can be non-preemptive or preemptive.

Watch the convention — it changes between examples

The standard convention (used in most of this course's examples, and in most textbooks) is smallest number = highest priority — priority 0 outranks priority 4. But one worked example in the source material explicitly flips this: "Higher Number Represents Higher Priority." Both conventions are real and both appear on exam papers — always read the question's stated convention before allocating the CPU, never assume.

Starvation and aging

The major problem with priority scheduling is indefinite blocking, or starvation: a low-priority process that's ready to run but perpetually out-prioritized by new arrivals may simply never execute. The standard fix is aging — gradually increasing a waiting process's priority the longer it waits, guaranteeing it eventually becomes the highest-priority process in the queue.

Real-Time CPU Scheduling

Scheduling with deadlines, not just fairness — latency budgets, Rate-Monotonic vs EDF, and a fully verified EDF schedule.

Soft vs hard real-time systems

Soft real-time systems give no hard guarantee about exactly when a critical process will run — only that it's preferred over non-critical processes. Hard real-time systems require a task be serviced by its deadline; service after the deadline is treated as equivalent to no service at all (e.g. a pacemaker or an automotive airbag controller). Real-time tasks are further classed as periodic (repeat at regular intervals, like a sensor poll) or aperiodic (occur unpredictably, like an emergency signal).

Latency

Event latency is the time from an event occurring to it being serviced. Two components drive it:

  • Interrupt latency — from the interrupt arriving at the CPU to the start of its service routine. The OS must finish its current instruction, determine the interrupt type, and save the current process's state before the ISR can even begin. For hard real-time systems, interrupt latency must not just be minimized — it must be bounded.
  • Dispatch latency — the time for the dispatcher to stop one process and start another. Its conflict phase has two parts: preemption of any process running in kernel mode, and release, by a low-priority process, of resources a high-priority process needs. Preemptive kernels are the most effective way to keep dispatch latency low.
Fig 8. Event latency decomposed into interrupt latency (recognizing and routing the interrupt) and dispatch latency (context-switching to the servicing task).

Priority-based scheduling, and two ways to assign priority

The most important feature of a real-time scheduler is responding immediately once a real-time process needs the CPU — so real-time schedulers are priority-based and preemptive. A preemptive priority scheduler alone only guarantees soft real-time behaviour; hard real-time systems need an explicit guarantee that tasks meet their deadlines, which is where RMS and EDF come in.

Proportional share schedulers divide T total shares among all applications; an application holding N shares is guaranteed N/T of total processor time. What to do when one algorithm doesn't fit every kind of process — and how a process can move between queues.

Multilevel queue scheduling

Useful when processes are easily classified into groups with different needs — typically foreground (interactive) processes, which need quick response, and background (batch) processes. The ready queue is partitioned into several separate queues, and each process is permanently assigned to one queue based on some property such as memory size, process priority or process type. Each queue has its own scheduling algorithm — e.g. Round Robin for the foreground queue and FCFS for the background queue.

There must also be scheduling among the queues. Two common ways:

  • Fixed-priority preemptive scheduling — a lower queue runs only when all queues above it are empty (e.g. foreground has absolute priority over background); a newly arrived foreground process preempts a running background one.
  • Time slicing among queues — each queue gets a share of CPU time to schedule among its own processes, e.g. 80% to the foreground queue (RR) and 20% to the background queue (FCFS).
Fig 10. Multilevel queue scheduling — separate queues by process type, strict priority from top to bottom (lowest priority at the bottom).

Drawback: a process can never change queue, so lower queues can starve under fixed priority, and the scheme is inflexible.

Multilevel feedback queue (MLFQ) scheduling

Allows a process to move between queues. The basic idea is to separate processes according to the characteristics of their CPU bursts:

  • A process that uses too much CPU time is demoted to a lower-priority queue. This leaves I/O-bound and interactive processes (short bursts) in the higher-priority queues.
  • A process that waits too long in a lower-priority queue is promoted to a higher-priority queue. This form of aging prevents starvation.
Fig 11. A three-queue feedback scheduler — new processes enter queue 0; CPU hogs sink downward, starved processes are promoted back up.

A multilevel feedback queue scheduler is defined by five parameters:

  1. the number of queues,
  2. the scheduling algorithm for each queue,
  3. the method used to determine when to upgrade a process to a higher-priority queue,
  4. the method used to determine when to demote a process to a lower-priority queue,
  5. the method used to determine which queue a process enters when it needs service.

Processor affinity

When a process migrates, the cache of the old processor must be invalidated and the new one re-populated — expensive. SMP systems therefore try to keep a process on the same processor: this is processor affinity. Soft affinity: the OS tries to keep the process on one processor as a policy but cannot guarantee it, so migration is possible. Hard affinity: the process may specify that it must not migrate to other processors (supported by Linux and Solaris).

Load balancing

Keeps the workload evenly distributed across all processors so that no CPU sits idle while another has a long queue. It is necessary only where each processor has its own private ready queue. Two approaches:

  • Push migration — a specific task periodically checks the load on each processor and, finding an imbalance, pushes tasks from the overloaded processor to idle or less-busy ones.
  • Pull migration — an idle processor pulls a waiting task from a busy processor.
Trade-off to quote

Load balancing counteracts processor affinity: moving a process to balance load destroys the warm cache that affinity tried to preserve.

Symmetric multithreading (SMT / hyper-threading)

Create multiple logical processors on the same physical processor and present several logical processors to the OS. Each logical processor has its own architecture state (general-purpose and machine-state registers) and handles its own interrupts, but they share the physical core's execution resources. SMT is a hardware feature, not a software one — the OS can still help by scheduling threads onto different physical cores first.

Pthread scheduling

The Pthread API lets the programmer specify PCS or SCS at thread creation. Two contention-scope values:

Why monitors?

Semaphores are powerful but error-prone — a single misplaced wait()/signal() breaks everything, and the bug may only show up under one rare timing. Typical mistakes:

  • Swapping the order: signal(mutex) … wait(mutex) — several processes may be in the critical section at once.
  • Repeating: wait(mutex) … wait(mutex) — a permanent deadlock.
  • Omitting wait(mutex), signal(mutex) or both — mutual exclusion is violated or the process blocks forever.

The monitor construct

An abstract data type (ADT) encapsulates data together with functions that operate on it, independent of any implementation. A monitor type is an ADT whose operations are automatically provided with mutual exclusion: it declares the variables whose values define the state of an instance, and the bodies of the procedures that operate on them. Only one process at a time can be active within the monitor, so the programmer does not code the mutual exclusion explicitly. A procedure defined in a monitor can access only the variables declared locally in the monitor and its formal parameters.

monitor monitor_name {
    // shared variable declarations
    procedure P1(...) { ... }
    procedure P2(...) { ... }
    initialization_code(...) { ... }
}

Condition variables

Mutual exclusion alone is not enough: a process must sometimes wait for a condition inside the monitor. So the monitor has a condition construct: condition x, y;. The only operations on a condition variable are:

  • x.wait() — the process that invokes it is suspended (and releases the monitor) until another process invokes x.signal().
  • x.signal() — resumes exactly one process suspended on x. If none is suspended, the signal has no effect (unlike a semaphore signal(), which is remembered in the counter).
Fig 14. A monitor with condition variables — one process active inside; others wait either on the entry queue or on a condition queue.

When P calls x.signal() and Q is suspended on x, both cannot be active. Two options: signal-and-wait (P waits until Q leaves or waits) or signal-and-continue (Q waits until P leaves or waits). Hoare's original proposal uses signal-and-wait; the PDF's semaphore implementation below does the same.

Dining philosophers using a monitor

Each philosopher is in one of three states — THINKING, HUNGRY, EATING — and may eat only if both neighbours are not eating. This is deadlock-free (a philosopher picks up both chopsticks or neither), though a philosopher may still starve. Each philosopher i calls pickup(i), eats, then putdown(i).

monitor DiningPhilosophers {
    enum { THINKING, HUNGRY, EATING } state[5];
    condition self[5];

    void pickup(int i) {
        state[i] = HUNGRY;
        test(i);                     // try to eat
        if (state[i] != EATING) self[i].wait();
    }
    void putdown(int i) {
        state[i] = THINKING;
        test((i + 4) % 5);           // left neighbour may now eat
        test((i + 1) % 5);           // right neighbour may now eat
    }
    void test(int i) {
        if (state[(i + 4) % 5] != EATING && state[i] == HUNGRY
            && state[(i + 1) % 5] != EATING) {
            state[i] = EATING;
            self[i].signal();
        }
    }
    initialization_code() { for (int i = 0; i < 5; i++) state[i] = THINKING; }
}

Implementing a monitor with semaphores

  • For each monitor a semaphore mutex (initialized to 1) is provided. A process executes wait(mutex) before entering the monitor and signal(mutex) after leaving.
  • Since a signalling process must wait until the resumed process either leaves or waits, an additional semaphore next (initialized to 0) is introduced; signalling processes suspend themselves on it. An integer next_count counts the processes suspended on next.
  • For each condition x: a semaphore x_sem and an integer x_count, both initialized to 0.
// each external procedure F is replaced by:
wait(mutex);
    ... body of F ...
if (next_count > 0) signal(next);
else                signal(mutex);          // leave the monitor

// x.wait()
x_count++;
if (next_count > 0) signal(next); else signal(mutex);
wait(x_sem);
x_count--;

// x.signal()
if (x_count > 0) {
    next_count++;
    signal(x_sem);
    wait(next);
    next_count--;
}

Resuming processes within a monitor

If several processes are suspended on x and x.signal() is executed, which one resumes? The simple answer is FCFS. For finer control use the conditional-wait construct x.wait(c): the integer expression c (a priority number) is stored with the suspended process, and x.signal() resumes the process with the smallest priority number.

The ResourceAllocator monitor uses this to allocate a single resource, giving it to the process with the shortest intended usage time t. A process follows the sequence:

R.acquire(t);
    ... access the resource ...
R.release();

The monitor cannot guarantee that processes obey this sequence, so these errors are still possible: accessing the resource without first acquiring it; never releasing it; releasing a resource that was never requested; requesting the same resource twice without releasing it. These must be solved by checking that every process uses the protocol correctly (and that no uncooperative process bypasses the monitor).

monitor ResourceAllocator {
    boolean busy;
    condition x;

    void acquire(int time) {
        if (busy) x.wait(time);       // smallest time resumed first
        busy = TRUE;
    }
    void release() {
        busy = FALSE;
        x.signal();
    }
    initialization_code() { busy = FALSE; }
}

Background & Race Conditions

Why cooperating processes need synchronizing at all — and a concrete example of exactly how things go wrong without it.

Cooperating processes

Cooperating processes are processes that can affect, or be affected by, other processes executing in the system — typically because they share data directly or through shared memory. Concurrent access to that shared data can cause data inconsistency: if two or more processes try to access and modify the same data at the same time, the result can depend on the precise timing of their execution rather than on the logic of either process alone. Maintaining consistency requires mechanisms that ensure cooperating processes execute in an orderly way — this is process synchronization.

2.9

The Critical Section Problem

A precise name for the danger zone, and the three properties every correct solution must guarantee.

Critical, entry, exit, and remainder sections

Consider a system of n processes {P₀, P₁, … Pₙ₋₁}. Each process has a segment of code — its critical section — in which it may be changing data in a shared region of memory (updating a common variable, writing a file, modifying a table). The defining rule: when one process is executing in its critical section, no other process may be executing in its own critical section. The critical-section problem is to design a protocol the processes can use to guarantee this.

Each process must explicitly ask permission before entering its critical section — that request is the entry section. The critical section may be followed by an exit section. Everything else is the remainder section.

Fig 17. The general structure of process Pᵢ — a loop of entry section, critical section, exit section, remainder section.

The three requirements

Any solution to the critical-section problem must satisfy all three of the following:

RequirementWhat it guarantees
1. Mutual ExclusionIf process Pᵢ is executing in its critical section, no other process can be executing in its critical section at the same time.
2. ProgressIf no process is in its critical section and some processes wish to enter, only processes not in their remainder sections can participate in deciding who goes next — and that decision cannot be postponed indefinitely.
3. Bounded WaitingThere's a bound on how many times other processes are allowed to enter their critical sections after a process has requested entry and before that request is granted.
Exam tip

If bounded waiting is not guaranteed, the result is starvation — a process can be requested to enter but perpetually skipped. This is exactly the link back to §Supporting deadlock detail's "drawbacks of semaphores": violating requirement 3 is how starvation happens, not a separate phenomenon. Always name all three requirements when a question asks you to "identify the requirements of a critical section" — partial answers are a common way to drop marks here.

Preemptive vs non-preemptive kernels

Two approaches exist depending on whether the kernel itself is preemptible: a preemptive kernel allows a process to be preempted even while running in kernel mode; a non-preemptive kernel lets a process run until it exits kernel mode, blocks, or voluntarily yields the CPU. Non-preemptive kernels are essentially free of race conditions on kernel data by construction — since only one process is ever actually running in kernel mode at a time — but preemptive kernels are far better suited to real-time programming, since a high-priority process isn't stuck waiting behind a low-priority one running in the kernel.

Peterson's Solution

A purely software two-process solution — and a full proof it satisfies all three critical-section requirements.

Peterson's solution is a classic software-only solution to the critical-section problem, restricted to exactly two processes, Pᵢ and Pⱼ, that alternate between their critical and remainder sections. It illustrates just how much care is needed to satisfy mutual exclusion, progress, and bounded waiting all at once. The two processes share two data items:

int turn; // whose turn it is: if turn==i, Pi may enter its CS boolean flag[2]; // flag[i]==true means Pi is ready/wants to enter its CS

Process Pᵢ

do { flag[i] = true; turn = j; while (flag[j] && turn == j) ; // spin critical section flag[i] = false; remainder section } while (true);

Process Pⱼ

do { flag[j] = true; turn = i; while (flag[i] && turn == i) ; // spin critical section flag[j] = false; remainder section } while (true);
Fig 18. Both processes announce intent (flag) then politely defer (turn) — since each sets turn to the *other* process last, whichever write happens second determines who actually waits.

Correctness proof

  1. Mutual exclusion is preserved. Pᵢ enters its critical section only if flag[j]==false or turn==i. Since both processes set turn to the other process's index just before spinning, whichever process's turn-write happened last is the one left spinning — so at most one of the two conditions can simultaneously fail to hold for both processes at once.
  2. The progress requirement is satisfied. If Pⱼ isn't interested (its remainder section), flag[j]==false and Pᵢ enters immediately. If both want in, exactly one of them "loses" the race to set turn last, and that determination is made the moment both flags are set — the decision is never postponed.
  3. Bounded waiting is met. Once a process has announced interest and yielded turn, the other process can enter at most once before yielding turn back on its next attempt. Under fair execution and finite critical sections, a waiting process therefore cannot be bypassed indefinitely.

Disadvantages of Peterson's solution

Despite the clean proof, Peterson's solution has real limits worth naming if a question asks for them: it's restricted to exactly two processes; it relies on busy-waiting (the spin loop), wasting CPU cycles while blocked rather than yielding the CPU; and — the deeper problem — it isn't guaranteed to work on modern hardware at all, since compilers and CPUs are free to reorder independent-looking memory operations unless the code uses explicit memory barriers, which is exactly why §2.11's hardware-level primitives exist as the practical alternative.

That's a textbook Progress violation (§2.9's requirement 2: a process not in its remainder section shouldn't be blocked by one that is). This is precisely the gap Peterson's solution closes — its flag[] array lets a process signal "I'm not interested" so the other never waits on someone who isn't playing, while turn alone (this scheme's equivalent) only ever encodes "whose turn is it," with no way to say "I don't want a turn right now."

Assumptions behind Peterson’s proof

The textbook proof assumes atomic shared-variable reads/writes and sequentially consistent ordering. These are algorithmic pseudocode listings, not portable C implementations using ordinary shared variables. Unsynchronised C/Pthreads accesses can be data races; real implementations need appropriate atomic operations and ordering guarantees.

2.11

Synchronization Hardware

Software solutions like Peterson's aren't guaranteed to work on modern architectures — so the hardware itself offers atomic instructions to build locks from.

Solutions to the critical-section problem range from hardware techniques to software-based APIs. All of them are based on the premise of locking: protecting critical regions through the use of locks. Software-only solutions such as Peterson's aren't guaranteed to work on modern computer architectures (compiler/CPU instruction reordering can break the assumptions they rely on), so the hardware provides help.

Disabling interrupts — the single-processor solution

In a single-processor environment the problem could be solved simply by preventing interrupts from occurring while a shared variable is being modified. The current sequence of instructions would then run in order without preemption, so no other process could touch the shared variable in the middle of the update.

This is not feasible in a multiprocessor environment. Disabling interrupts on every processor means sending a message to all of them, which is time-consuming, delays entry into each critical section and reduces system efficiency. It also does nothing to stop a process already running on another CPU.

The solution: special hardware instructions that atomically either test and modify the content of a word, or swap the contents of two words. test_and_set() and compare_and_swap() provide an abstraction of such instructions.

test_and_set

boolean test_and_set(boolean *target) { boolean rv = *target; *target = TRUE; return rv; } // executes as a single, indivisible machine cycle

It takes a shared lock variable, unconditionally sets it to TRUE (locked), and returns whatever the lock's value was before that write. By convention 0 means unlocked and 1 means locked.

do { while (test_and_set(&lock)) ; // spin while lock was already held critical section lock = false; remainder section } while (true);
Fig 19. test_and_set's lock/unlock cycle — the atomic read-and-set means only one caller can ever see rv=0 at a time.

compare_and_swap — conditional atomic update

CAS takes a location, an expected value and a replacement. It reads the old value and writes the replacement only when the old value equals the expected value; the textbook version returns the old value in either case. The entire operation is atomic. This differs from unconditionally exchanging two values.

/* Specification of ONE atomic hardware primitive, not ordinary concurrent C. */ int compare_and_swap(int *value, int expected, int new_value) { int old = *value; if (old == expected) *value = new_value; return old; } /* lock initially 0; 0 = free, 1 = held */ do { while (compare_and_swap(&lock, 0, 1) != 0) ; /* retry: another process owns the lock */ /* critical section */ lock = 0; /* remainder section */ } while (true);

The first contender reads 0, writes 1 and enters. A competitor reads 1, leaves it unchanged and retries. Releasing the lock allows a later attempt to succeed. This gives mutual exclusion but does not itself guarantee bounded waiting. In real code, the acquire and release operations need the language/platform’s atomic and memory-ordering facilities.

void swap(boolean *a, boolean *b) { boolean temp = *a; *a = *b; *b = temp; }
Common mistake

Do not place the swap(&lock,&key) call after the while loop with an empty loop body (a bare semicolon). Written that way, key is set to true once and never changes inside the loop, so while(key==true) would spin forever and the swap — which is what actually has a chance of clearing key — would never run. The swap must be the loop's retry body, not a one-shot call after it:

do { key = TRUE; while (key == TRUE) swap(&lock, &key); // retried on every spin, not called once critical section lock = FALSE; remainder section } while (true);

Walk through it: initially lock=false (0). A process sets its local key=true, then repeatedly swaps lock and key until the swap hands it back key=false — which happens exactly when lock was false going into that swap (so the swap sets lock=true for this process and key=false, ending the spin). Once inside, it eventually sets lock=false on exit, letting the next spinning process's swap succeed.

Exam tip

Both test_and_set and compare_and_swap provide mutual exclusion, but neither guarantees bounded waiting on its own — a spinning process has no guaranteed turn order, so in principle one process could keep "winning" the race indefinitely while another starves. This is a genuinely common written-exam point: "do these hardware instructions satisfy all three CS requirements?" — the answer is mutual exclusion yes, bounded waiting not without extra bookkeeping. The algorithm below adds that bookkeeping.

Bounded-waiting mutual exclusion with test_and_set

This algorithm, from the faculty slide "Algorithm to solve issues of bounded waiting", satisfies all three critical-section requirements for n processes. The shared data, all initialised to false:

boolean waiting[n]; // waiting[i] = Pi wants to enter boolean lock; // the test_and_set lock
do { waiting[i] = true; key = true; // local while (waiting[i] && key) key = test_and_set(&lock); waiting[i] = false; /* critical section */ // find the next waiter j = (i + 1) % n; while ((j != i) && !waiting[j]) j = (j + 1) % n; // none waiting: free lock, // else hand CS to Pj if (j == i) lock = false; else waiting[j] = false; /* remainder section */ } while (true);

How it works. Entry: Pi announces itself (waiting[i]=true) and keeps calling test_and_set until either it finds the lock free (key becomes false) or an exiting process hands it the critical section (waiting[i] becomes false). Exit: instead of always releasing the lock, Pi scans the other processes in cyclic order i+1, i+2, …, n−1, 0, …, i−1 and passes the critical section straight to the first waiting one. Only if nobody is waiting does it set lock=false. When the CS is handed over, lock stays true and ownership moves to Pj.

RequirementWhy it holds
Mutual exclusionPi enters only if key==false or waiting[i]==false. key is false only for the first process to execute test_and_set while the lock is free; all others then get true. waiting[i] becomes false only when an exiting process hands over, and each exit releases exactly one process.
ProgressAn exiting process either sets lock=false or sets some waiting[j]=false. Either action lets a waiting process enter, so the decision is never postponed.

Supporting mutex detail from older notes; not separately named in the new syllabus

The simplest software-visible locking abstraction — acquire, use, release.

A mutex lock (mutual-exclusion lock) is a boolean variable, 0 (unlocked) or 1 (locked). A process wanting to enter its critical section must acquire the lock first — if it's already 0 (free), the process sets it to 1 and proceeds; once done, it releases the lock, setting it back to 0.

do { acquire lock critical section release lock remainder section } while (true);

The shared lock variable is often called available, initially true (free):

acquire() { while (!available) ; // busy wait available = false; } release() { available = true; }
The cost hiding in "busy wait"

A mutex lock implemented this way is a spinlock — a waiting process burns CPU cycles continuously re-checking the lock instead of yielding the CPU. That's wasteful on a single-core system (the lock holder can't even run to release it while the waiter spins), but genuinely useful on a multicore system for very short critical sections, since the overhead of a full context switch to sleep-and-wake can exceed the time just spent spinning. This tradeoff — spin vs block — is exactly why semaphores (§2.12) matter: a semaphore's wait() can be implemented to block the calling process instead of spinning, avoiding the wasted cycles.

Semaphores

A synchronization tool more flexible than a mutex — an integer that can gate access to a whole pool of resources, not just one.

A semaphore S is an integer variable that, apart from initialization, is accessed only through two standard atomic operations: wait() and signal().

  • wait() was originally termed P — from the Dutch proberen, "to test".
  • signal() was originally called V — from the Dutch verhogen, "to increment".
wait(S) { while (S <= 0) ; // busy wait — resource unavailable S--; } signal(S) { S++; }

wait() asks "is the resource available?" — if S≤0 it spins; the moment S becomes positive, it breaks out and claims one unit by decrementing. signal() returns a unit to the pool. The successful test-and-decrement and each signal must be atomic. A waiting process must not hold the semaphore’s internal guard while spinning, because a signal must still be able to make progress.

Binary vs counting semaphores

TypeRangeUse
Binary semaphore0 or 1 onlyCan enforce mutual exclusion with one permit, but also signals events. Unlike an ownership-based mutex, the signalling process need not be the one that waited.
Counting semaphoreUnrestricted (0, 1, 2, …)Controls access to a resource with multiple interchangeable instances — the count tracks how many are currently free.

Counting semaphore implementation

  1. The semaphore is initialized to the number of resources available.
  2. Each process that wishes to use a resource performs wait() on the semaphore, which decrements the count.
  3. When a process releases a resource, it performs signal(), which increments the count.
  4. When the value is zero, all resources are in use. Processes that then want a resource are blocked. With the definition above they busy-wait.

Semaphore implementation without busy waiting

The definition of wait() above suffers from busy waiting: a process repeatedly tests for a permit and wastes CPU time. To overcome this, wait() and signal() are modified:

  1. When a process executes wait() and finds the semaphore value is not positive, it must wait. Instead of busy waiting, it blocks itself.
  2. The block() operation places the process into a waiting queue associated with the semaphore and switches the process's state to waiting.
  3. Control then passes to the CPU scheduler, which selects another process to run.
  4. A process blocked on S is restarted when some other process executes signal(). The wakeup() operation changes it from the waiting state to the ready state and places it in the ready queue.
typedef struct { int value; struct process *list; } semaphore; wait(semaphore *S) { S->value--; if (S->value < 0) { add this process to S->list; block(); } } signal(semaphore *S) { S->value++; if (S->value <= 0) { P = remove one process from S->list; wakeup(P); } }

This is textbook operating-system pseudocode. Updates, queue insertion/removal and the transition to sleep/wakeup must be coordinated atomically to avoid lost wakeups; the internal guard is released before the process sleeps. In this signed implementation, a negative value records waiting processes. In the earlier non-negative permit convention, waiting is represented separately and the available count stays at zero.

A mutex protects a critical section with acquire/release ownership; a binary semaphore can provide mutual exclusion or event ordering, and a counting semaphore represents multiple permits. Incorrect wait ordering can cause deadlock; unfair wakeup can cause starvation. The complete classic-problem solutions below show how to initialise and order the semaphore operations.

Bounded-Buffer Problem

Also called the Producer-Consumer problem — the first of three classical synchronization problems, solved with exactly three semaphores.

The producer–consumer problem

A producer process produces information that is consumed by a consumer process. Examples:

  • A compiler produces assembly code that is consumed by an assembler. The assembler in turn produces object modules that are consumed by the loader.
  • Data-processing applications: producers generate data and place it in a shared data store, and consumers retrieve the data and process it.

The producer–consumer problem is solved using a shared buffer of one of two kinds:

BufferSizeWho may have to wait
Unbounded bufferNo practical limitOnly the consumer, when the buffer is empty. The producer can always produce new items.
Bounded bufferFixed size nThe consumer when the buffer is empty and the producer when it is full.

The bounded-buffer problem

A buffer of n slots sits between a producer, which produces data and stores it in the buffer, and a consumer, which removes data from the buffer. Three rules must hold:

  1. The producer must not insert data when the buffer is full.
  2. The consumer must not retrieve data when the buffer is empty.
  3. Producer and consumer must not insert and remove data simultaneously.

Solution using three semaphores

Exam tip — where producing and consuming happen

Producing an item into next_produced and consuming the item in next_consumed happen outside the mutex. Only the buffer insert or remove is the critical section. Also keep the order: wait on the counting semaphore (empty / full) before wait(mutex). With the order reversed, a producer that holds mutex while the buffer is full blocks forever, because the consumer can never get mutex to remove an item.

Readers-Writers Problem

Some processes only need to look; others need exclusive access. Letting the readers share costs nothing — letting two writers collide costs everything.

A database is shared among concurrent processes. Some processes only want to read it; others — writers — want to read and update it. Two readers accessing the data at the same time causes no problem at all. Two writers (or a reader and a writer) accessing it at the same time can cause real chaos. The goal: give writers exclusive access, while letting any number of readers share access freely amongst themselves.

Variations of the readers–writers problem

VariationRequirementWho can starve
First readers–writers problemNo reader is kept waiting unless a writer has already obtained permission to use the shared object.Writers
Second readers–writers problemOnce a writer is ready, that writer performs its write as soon as possible.Readers

Solution to the first readers–writers problem

semaphore rw_mutex = 1; semaphore mutex = 1; int read_count = 0;
VariableTypeInitial valueRole
mutexSemaphore1Protects updates to read_count itself, so two readers incrementing/decrementing it don't race.
rw_mutexSemaphore1Shared between readers and writers — a writer holds it for the whole write; the first reader to arrive also grabs it (locking out writers), and the last reader to leave releases it.
read_countInteger0Tracks how many readers are currently active.
Fig 22. Readers share the database freely amongst themselves; a writer needs exclusive access, gated by the shared rw_mutex semaphore.

Writer code

do { wait(rw_mutex); . . . /* writing */ . . . signal(rw_mutex); } while (true);

Reader code

do { wait(mutex); read_count++; // first reader if (read_count == 1) wait(rw_mutex); signal(mutex); . . . /* reading */ . . . wait(mutex); read_count--; // last reader if (read_count == 0) signal(rw_mutex); signal(mutex); } while (true);

Why if (read_count == 1) wait(rw_mutex) instead of every reader waiting on rw_mutex? Because only the first reader needs to actually contend for exclusive access — once it holds rw_mutex, every subsequent reader can proceed freely (protected only by the quick mutex around the counter update), and only the last reader to leave needs to release rw_mutex for writers.

A known weakness of this particular solution

This solves the first readers–writers problem (readers' preference): as long as at least one reader is active, a new reader can always join in (read_count never drops to 0), so a waiting writer can be starved indefinitely by a continuous stream of readers. A solution to the second problem (writers' preference, not shown here) stops new readers from starting once a writer is waiting. That avoids writer starvation, but readers can then starve instead.

Reference: Silberschatz, Galvin & Gagne, ninth edition — §5.7.2 — synchronization.

2.15

Dining Philosophers Problem

Five philosophers, five chopsticks — a deceptively simple resource-sharing puzzle that deadlocks if solved naively.

Five philosophers sit at a round table, alternating between thinking and eating. Between each pair of adjacent philosophers sits one chopstick — five chopsticks in total — and a philosopher needs both neighboring chopsticks to eat, picking them up one at a time and releasing both when done.

  • When a philosopher thinks, they do not interact with their colleagues.
  • When hungry, a philosopher tries to pick up the two chopsticks closest to them — the ones between them and their left and right neighbours.
  • A philosopher may pick up only one chopstick at a time, and cannot pick up a chopstick that is already in a neighbour's hand.
  • With both chopsticks held, the philosopher eats without releasing them. When finished, they put both down and start thinking again.

Simple semaphore solution: represent each chopstick with a semaphore. A philosopher grabs a chopstick by executing wait() on that semaphore and releases it with signal(). The shared data is semaphore chopstick[5];, with every element initialized to 1.

Fig 23. Five philosophers, five shared chopstick semaphores — each philosopher needs both of their two adjacent chopsticks simultaneously.

The naive semaphore solution — and why it deadlocks

Semaphore chopstick[5]; // all initialized to 1 do { wait(chopstick[i]); wait(chopstick[(i+1) % 5]); eat(); signal(chopstick[i]); signal(chopstick[(i+1) % 5]); think(); } while (true);
Not a bug — a deliberately naive first attempt

This straightforward solution has a real flaw, and the source material presents it precisely so the fix can be taught: if all five philosophers simultaneously pick up their left chopstick, every chopstick[i] is now held, and every philosopher's second wait() blocks forever waiting for their right neighbor's chopstick — who is in turn waiting on them. This is a genuine deadlock (a 5-way circular wait, the same underlying failure mode as §Supporting deadlock detail's 2-process S/Q example, just with 5 participants instead of 2).

Three standard fixes

  1. Limit concurrent diners. Allow at most 4 philosophers to sit at the table simultaneously — with only 4 of 5 possibly holding a first chopstick, at least one is guaranteed to get both of theirs.
  2. Atomic pickup. A philosopher may pick up a chopstick only if both are available — done inside a critical section, so "pick up left, then right" can never leave a philosopher holding just one.
  3. Asymmetric ordering. Odd-numbered philosophers pick up their left chopstick first, then their right; even-numbered philosophers pick up right first, then left. This breaks the symmetry that let all five grab "the same side" simultaneously.

Reference: Silberschatz, Galvin & Gagne, ninth edition — §5.7.3 — synchronization.

Old Supporting deadlock detail · Deadlock & Starvation

Supporting deadlock, starvation and priority-inversion detail; no separate deadlock unit is named in the new syllabus

Semaphores solve the synchronization problem — but misuse them and they introduce two new failure modes of their own.

Deadlock: two or more processes are each waiting indefinitely for an event that only one of the other waiting processes can cause. Starvation (indefinite blocking): a process may simply never be removed from the queue of processes suspended on a semaphore, even though the semaphore keeps being signaled to others.

Fig 24. Circular wait — P0 holds S and wants Q; P1 holds Q and wants S. Neither can ever proceed.
Older course deck p41, classic exampleworked example · verified with real threads
Semaphores S and Q are both initialized to 1. P0 executes wait(S) then wait(Q); P1 executes wait(Q) then wait(S). Show that this can deadlock.

Consider this interleaving: P0 runs wait(S) and acquires S. P1 runs wait(Q) and acquires Q. Now P0 attempts wait(Q) — but Q is held by P1, so P0 blocks. P1 attempts wait(S) — but S is held by P0, so P1 blocks too. Each process is waiting for a resource the other holds, and neither will ever signal because neither can finish its critical section to reach the signal() calls. Reproduced with two real Python threads and a timeout to detect the hang:

P0: attempting wait(S) → acquired S P1: attempting wait(Q) → acquired Q P0: attempting wait(Q) → TIMED OUT (deadlocked) P1: attempting wait(S) → TIMED OUT (deadlocked)

The fix in general: impose a consistent global ordering on resource acquisition — e.g. every process must acquire S before Q, never the other way round — which makes this particular circular-wait interleaving impossible.

Priority inversion

Priority inversion is a scheduling-adjacent problem: a lower-priority process holds a lock that a higher-priority process needs, but the lower-priority process itself can't run to finish and release the lock because a *medium*-priority process (uninvolved in the lock at all) keeps preempting it. The effective priority of the high-priority process has been "inverted" down to the low-priority process's level. The standard fix is the priority-inheritance protocol: temporarily boost the lock-holding process's priority to match the highest-priority process waiting on it, so it can finish and release the lock promptly.

Where this connects back

Deadlock here is the same underlying phenomenon as §2.15's naive dining-philosophers solution (circular wait) and, more generally, exactly what bounded waiting (§2.9, requirement 3) exists to prevent. Semaphores are a *tool* for solving the critical-section problem, not an automatic guarantee against all three failure modes — that's the connective thread across this entire unit.
