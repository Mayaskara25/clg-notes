5.1

File-system structure

What a file is, what the OS records about it, and the layers and tables that connect a file name to blocks on a disk.

A disk is only a long array of numbered blocks. It can rewrite any block in place and can jump straight to any block, but it knows nothing about names, owners or folders. People, on the other hand, think in terms of files: "my report", "the compiler", "today's log". The file system is the part of the OS that bridges the two. It has two separate jobs:

  1. Decide how files look to the user — what a file is, its attributes, the operations allowed on it, and how directories organise files.
  2. Map that logical view onto the physical device — the algorithms and data structures that decide which blocks hold which file.

Everything in Unit V answers one of these two questions. To keep I/O efficient, transfers between memory and disk always happen in whole blocks; each block is one or more sectors (usually 512 bytes or 4 KB).

What is a file?

A file is a named collection of related information that is recorded on secondary storage. From the user's point of view it is the smallest unit of storage: data cannot be written to secondary storage unless it is inside a file. The OS presents every file as a contiguous logical address space (byte 0, byte 1, …), even though the blocks may be scattered over the disk.

The contents are defined by the file's creator. A file can hold data (numeric, character or binary) or a program (source code, object code or an executable). Examples: a text file (lines of characters), a source file (functions and declarations), an executable (code the loader can bring into memory and run).

File naming. A file is named for the convenience of people, so names are strings. Most systems accept letters, digits and some special characters (myfile, file-2-1, file_21), and modern systems allow names of up to 255 characters. Almost every OS supports a two-part name separated by a dot: the part after the dot is the extension, which hints at the type (.c source, .o object file, .pdf, .zip archive, .bak backup). Some systems (UNIX) treat the extension only as a convention; others (Windows) use it to choose the program that opens the file.

Discuss the role of various file attributes in operating systems, explaining how they contribute to security, system auditing, recovery, and efficient file operations. In your answer, include ownership, permissions, timestamps, file size, location, and extended attributes.
Answer

File attributes are the metadata the OS keeps in each file's control block (inode). They are what the OS consults before, during and after every file operation.

  • Ownership (owner and group IDs) — security. Every access request is compared with the owner and group, so the OS knows which set of rights applies. Ownership also decides who may change the permissions.
  • Permissions (rwx bits or an ACL) — security. They state which users may read, write or execute. The OS checks them at open(), so an unauthorised process never gets a file descriptor.
  • Timestamps (created, modified, accessed, status changed) — auditing and recovery. An administrator can reconstruct who changed what and when. Backup programs copy only files modified since the last backup (incremental backup), and tools such as make use modification times to rebuild only stale files.
  • File size — efficient operations and integrity. Reads stop at end of file, space can be reserved before a write, and a size that disagrees with the allocated blocks reveals corruption during a consistency check.
  • Location (block pointers) — efficient operations and recovery. Because the FCB holds the block addresses, the OS reaches any part of the file without searching. After a crash, fsck or a journal replay uses these pointers to rebuild the free-space map.
  • Extended attributes — security and policy. They carry extra labels such as SELinux security contexts, checksums or a "downloaded from the Internet" mark, which the OS uses for mandatory access control, integrity checks or warnings, without altering the file contents.

Conclusion: attributes let the OS protect files (ownership, permissions, labels), keep an audit trail (timestamps, owner), recover after failures (location, size, times) and work fast (location, size), all without reading the file's data.

File types supporting

The OS must know a file's type to treat it sensibly — for example, to refuse to print an executable as text. UNIX-like systems distinguish:

  • Regular files — user information. Either ASCII (text) files, made of lines of text that can be displayed, printed and edited with any editor, or binary files, which have an internal structure known only to the programs that use them. The OS will execute a binary only if it has the proper format (for example, an ELF header with a "magic number" at the start).
  • Directories — system files that maintain the structure of the file system (5.3).
  • Character special files — model serial I/O devices such as terminals, printers and network interfaces.
  • Block special files — model disks and other block devices.

Windows identifies the type mainly from the extension; UNIX uses the extension only as a hint and stores a small type field in the inode, plus magic numbers inside binary files.

File structure: how the bytes are organised

Inside a file, data can be organised in three classic ways:

  1. Unstructured byte sequence. The OS sees only bytes and gives them no meaning; programs impose any structure they like. UNIX and Windows both use this, because it is the most flexible.
  2. Sequence of fixed-length records. Each read returns one record and each write overwrites or appends one record. This suited punched-card-era mainframes (80-character records).
  3. Tree of records. Records of varying length each have a key in a fixed position, and the tree is kept sorted on the key so that a record can be found quickly by key. Large mainframes used this for commercial data processing.

The layered file system

A file system is built in layers. Each layer uses only the services of the layer below it and offers new services to the layer above. Follow one request — "read bytes 5000–5999 of notes.txt" — down the stack in Fig 1:

Fig 1. The layered file system (Silberschatz Fig 12.1), with what each layer does for one read request.
  • I/O control — device drivers and interrupt handlers. A driver is a translator: its input is a high-level command such as "retrieve block 123"; its output is the low-level, hardware-specific instructions written into the device controller's registers.
  • Basic file system — issues generic commands to the driver to read and write physical blocks, identified by numeric disk addresses (drive, cylinder, track, sector). It also manages the buffers and caches that hold file-system, directory and data blocks.
  • File-organization module — knows about files and their logical blocks (numbered 0 to N) and translates them to physical blocks, using the allocation method (5.4). It also contains the free-space manager, which tracks unallocated blocks.
  • Logical file system — manages metadata: everything except the file contents. It manages the directory structure, maintains file structure through file-control blocks, and is responsible for protection.

Why layers? Code is not duplicated: the I/O control and often the basic file system can be shared by several file systems (FAT, NTFS, ext4 can all use the same disk driver), while each file system has its own logical layer and file-organization module. The cost is extra overhead on every request, which can lower performance, and deciding how many layers to use and what each should do is a hard design problem.

Most operating systems support several file systems at once: CD-ROMs use ISO 9660, UNIX uses UFS (based on the Berkeley Fast File System), Windows supports FAT, FAT32 and NTFS, and Linux supports more than forty, with ext3 and ext4 the most common. The virtual file system (5.8) is how one OS hosts many of them.

On-disk structures

Two kinds of structure implement a file system: those stored permanently on disk, and those built in memory while the system runs. On disk, a volume (a formatted partition) contains:

Fig 2. Main on-disk structures of a volume, and the fields of a typical file-control block (Silberschatz Fig 12.2). Real layouts interleave these regions.
  • Boot control block (per volume) — what the system needs to boot an OS from that volume; empty if the volume has no OS. Usually the first block. UFS calls it the boot block; NTFS the partition boot sector.
  • Volume control block (per volume) — volume details: number of blocks, block size, free-block count and pointers, free-FCB count and pointers. UFS calls it the superblock; NTFS keeps it in the master file table.
  • Directory structure (per file system) — organises the files: file names with pointers to FCBs. In UFS this is names plus inode numbers; in NTFS it is stored in the MFT.
  • File-control block (per file) — the file's details (Fig 2), with a unique identifier so a directory entry can refer to it. UNIX calls it an inode; NTFS stores it as a row of the MFT, which works like a relational table with one row per file.

In-memory structures

In-memory information serves both management and speed (caching). It is loaded at mount time, updated during file operations and discarded when the volume is unmounted:

  • Mount table — one entry per mounted volume: which device, which file-system type, where it is mounted.
  • Directory-structure cache — directory information of recently used directories, so path lookups avoid disk reads.
  • System-wide open-file table — a copy of the FCB of each open file, plus an open count of how many processes have it open.
  • Per-process open-file table — one per process; each entry points to the system-wide entry and holds per-process data such as the current file position and the access mode.
  • Buffers — hold file-system blocks while they are being read from or written to disk.

How these tables are used by open() and read() is shown in Fig 3 (5.2). The split into two tables is the key idea: data that is the same for everyone (where the file is, its size) is stored once; data that differs per process (the current offset, the mode) is stored per process.

Partitions and mounting supporting

A disk can be split into partitions. Each is either raw (no file system — used for UNIX swap space or some databases) or cooked (holds a file system). A separate boot partition holds a boot loader, which may understand several file systems and so allow dual booting.

The root partition, holding the kernel, is mounted at boot; others are mounted at boot or later. When mounting, the OS asks the driver to read the device's directory and checks that it has the expected format; if not, a consistency check runs. It then records the mount in the in-memory mount table. Windows mounts each volume in its own name space (C:, F:); UNIX mounts a volume at any directory by setting a flag in that directory's in-memory inode, with a pointer to the mount-table entry, which in turn points to the volume's superblock.

5.2

File operations

The operations a file supports, what open() and read() do inside the kernel, file locking, the access methods, and complete C programs.

A file is an abstract data type: to define it we must say what operations can be done on it. The OS provides these operations as system calls, and every higher-level action (copy, print, edit) is built from them.

The six basic operations

OperationWhat the OS doesUNIX call
CreateFind space for the file in the file system, then make an entry for it in the directory.open(…, O_CREAT), creat()
WriteSearch the directory for the file, then write at the write pointer and advance it.write()
ReadSearch the directory, read from the read pointer into a memory buffer, advance the pointer. Reads and writes share one current-file-position pointer per process.read()
Reposition (seek)Set the current-file-position pointer to a given value. This needs no actual I/O.lseek()
DeleteFind the directory entry, release all the file's space for reuse, and erase the entry.unlink()
TruncateKeep all attributes except the length; reset the length to zero and release the file's space.truncate(), ftruncate()

These six are the minimal set. Others are built from them or added for convenience: append (write only at the end), rename, get attributes and set attributes (for example, read the length or change the owner), and copy (create a new file, then read from the old one and write to the new). The Unit 5 deck adds open, close and seek to this list. create() and delete() work on closed files; the rest work on open files.

One-mark answer (SEE 2025 Q1.11)"The reposition (seek) operation within a file need not involve any actual I/O." It only changes the file-position pointer kept in memory; the next read or write does the I/O.

Why files are opened first

Almost every operation needs the file's directory entry. Searching the directory for every read() would be slow, so systems require an open() call before a file is used. open() takes the name, searches the directory once, checks the requested access mode (read-only, read–write, append…) against the file's permissions, and copies the needed information into an open-file table in memory. It returns a small integer or pointer into that table — a file descriptor in UNIX, a file handle in Windows — and every later operation uses it instead of the name. close() removes the entry.

Several processes may have the same file open, so the OS keeps two levels of table. For each open file it tracks:

  • File pointer — the current read/write position. It differs per process, so it cannot be an on-disk attribute.
  • File-open count — how many opens are outstanding. Each close() decrements it; at zero the entry is removed (otherwise the table would fill up).
  • Disk location of the file — kept in memory so the OS does not reread it for every operation.
  • Access rights — the mode the process opened the file in, so later requests can be allowed or denied.

What open() and read() do: the in-memory tables

Fig 3. In-memory file-system structures (after Silberschatz Fig 12.3): (a) opening a file, (b) reading it. Numbers match the steps below.

(a) open():

  1. The logical file system receives the name and first checks the system-wide open-file table: if the file is already open by another process, it skips straight to step 5. Otherwise it searches the directory, starting with the directory-structure cache.
  2. On a cache miss, the directory blocks are read from disk.
  3. The directory entry gives the FCB (inode) number, and the FCB is located on disk.
  4. The FCB is copied into the system-wide open-file table, with an open count of 1.
  5. An entry is made in the process's per-process open-file table, pointing to the system-wide entry and recording the current position (0) and the access mode.
  6. open() returns the index of that per-process entry: the file descriptor (here 3, because 0, 1 and 2 are already standard input, output and error).

(b) read(): (1) the descriptor selects the per-process entry, which supplies the current offset; (2) its pointer leads to the system-wide entry, whose FCB copy gives the block addresses; (3) the file-organization module turns the offset into a block number and the block is read (or found in the buffer cache); (4) the data is copied into the user's buffer and the offset advances. The file name is never used again after open().

close(): the per-process entry is removed and the system-wide open count is decremented. When it reaches zero, updated metadata is written back to the on-disk directory structure and the system-wide entry is removed.

Two processes using the same file (UNIX)

UNIX splits the bookkeeping into three tables: a per-process file-descriptor table, a system-wide open-file table (one entry per open() call, holding the offset, the access mode and a reference count) and the in-memory inode table (one entry per file, however many times it is open).

Fig 4. UNIX file tables. A's fd 3 and the child's inherited fd 3 share one open-file entry, and therefore one offset; the child's own second open() gets a separate entry and offset. Both entries point to one inode.

File locking supporting

When several processes share a file — say, a system log that many programs append to — their writes can interleave and corrupt each other, just like a race on shared memory in Unit II. File locks let one process lock a file (or part of it) so that others cannot use it at the same time.

  • Shared lock — like a reader lock: several processes may hold it together. Used for reading.
  • Exclusive lock — like a writer lock: only one process at a time. Used for writing. Some systems provide only exclusive locks.
  • Mandatory locking — once a process holds an exclusive lock, the OS blocks every other process's access, even if it never asks for the lock. Windows uses mandatory locks.
  • Advisory locking — the OS records the lock, but processes that do not ask for it can still access the file; it is up to programmers to acquire locks correctly. UNIX systems use advisory locks.
  • Whole-file versus byte-range (record) locks — flock() locks the whole file; fcntl() can lock any byte range, so two processes can update different records at once.

Because locks behave like Unit II synchronization primitives, the same care is needed: hold a lock for as short a time as possible, and acquire several locks in a fixed order, or processes can deadlock.

Closing the descriptor (or the process exiting) also releases fcntl() locks. Java offers the same idea through FileChannel.lock(begin, end, shared).

Access methods supporting

An access method is the order in which a program reaches the records of a file. It is a question about the file's interface; how well each method performs depends on the allocation method underneath.

Fig 5. The three access methods. Sequential moves one record at a time; direct jumps to any numbered block; indexed sequential searches a small index of keys, then reads the one block that can hold the record.
  • Sequential access — records are processed in order, one after another, like a tape. read next reads the next portion and advances the pointer; write next appends and advances; reset (rewind) returns to the beginning; some systems allow skipping n records forward or back. Editors and compilers access files this way, and it is by far the most common method.
  • Direct (relative) access — the file is a numbered sequence of fixed-length logical records (blocks), and a program can read or write them in any order: read block 14, then 59, then write 17. Operations take the block number: read n, write n, or position to n followed by read next. The number is relative to the start of the file (0, 1, 2…), so the OS, not the user, decides where the file is on disk. Databases use it: compute which block holds a record, then fetch it immediately. Sequential access is easy to simulate on top of direct access by keeping a current position cp: reset sets cp = 0; read next is read cp; cp = cp + 1.
  • Indexed sequential access — built on direct access. The file is kept sorted by a key, and a small index holds the first key of each block. To find a record, search the index (in memory), then read the one block it names. If the index itself grows too large, an index of the index is built: IBM's ISAM uses a small master index pointing to blocks of a secondary index, which point to the file blocks.

5.3

Directory implementation

How directories organise files for the user, and how a directory is stored so that a name can be found quickly.

A directory is a symbol table that translates file names into their FCBs (directory entries). Users and programs perform these operations on it: search for a file, create a file (add an entry), delete a file (remove an entry), list the directory, rename a file, and traverse the file system (for example, for backup). Directories are themselves files: UNIX stores a directory exactly like a file with a "directory" type flag; Windows provides separate system calls for files and directories.

Logical directory structures supporting

Before asking how to store a directory, decide how directories are organised. The deck teaches the first two; the rest complete the standard list.

Fig 6. Directory structures. Boxes are directories, circles and rounded tags are files (after Silberschatz Figs 11.9–11.11 and the Unit 5 deck, slide 8).
  • Single-level directory — one directory (the root) holds every file. Simple, and common on early single-user PCs, but with many users or many files, names collide (two users cannot both have a file called test) and the list becomes hard to manage.
  • Two-level directory — each user has a private user file directory (UFD). A master file directory (MFD), indexed by user name or account number, has one entry per user that points to that user's UFD. A search looks only in the caller's UFD, so different users can use the same file names and cannot accidentally delete each other's files. The cost is isolation: to share, a user must name both the user and the file (a path such as user2/a). System programs are usually kept in a special user directory that is searched as well (the search path).
  • Tree-structured directory — the natural generalisation: any directory can contain subdirectories, to any depth. Each process has a current directory; names are given as an absolute path from the root (/home/ana/a.c) or a relative path from the current directory (ana/a.c from /home). This is what UNIX and Windows use.
  • Acyclic-graph directory — a tree that also lets two directories share a subdirectory or file, through links (UNIX hard and symbolic links). Problems: a file may have several path names, and deleting it can leave dangling links; UNIX keeps a link count in the inode and frees the file only when it reaches zero.
  • General-graph directory — links are allowed to form cycles. Searches must avoid looping forever, and a cycle can keep unreachable files' counts above zero, so garbage collection is needed. Most systems prevent this by forbidding hard links to directories.

Implementing a directory: linear list

Now the syllabus question: how are a directory's entries stored on disk? The simplest method is a linear list of file names, each with a pointer to the file's FCB or data blocks.

  • Create: search the whole list to be sure the name is not already used, then add the new entry at the end.
  • Delete: search for the name and release the file's space. The freed entry can be marked unused (a blank name, or a used/unused bit), attached to a list of free entries, or overwritten with the last entry so the list shrinks by one.
  • Weakness: every lookup is a linear search, and directory lookups happen on nearly every path name, so users notice the delay. Remedies: cache recently used directory information in memory; keep the list sorted so a binary search can be used (which also gives sorted listings for free, but makes inserting and deleting more costly); or use a balanced tree.

Implementing a directory: hash table

A hash table keeps the linear list but adds a hash structure: a hash function computes a value from the file name, and the table entry at that value points to the name's place in the list. A lookup then examines one entry (or a few), so search time drops greatly; insertion and deletion are also straightforward.

  • Collisions: two names may hash to the same slot, so some provision is needed.
  • Fixed size: the main difficulty. With a 64-entry linear-probing table and hash = name value mod 64, creating a 65th file forces the table to grow (say to 128), which needs a new hash function (mod 128) and rehashing every existing entry.
  • Chained overflow: each slot holds a linked list of entries; a collision just adds to the list. Lookups may walk a short chain, but this is still far faster than scanning the whole directory, and the table never "fills up".

5.4

Allocation methods

Which disk blocks belong to which file: contiguous, linked (and FAT) and indexed allocation, the UNIX inode, how they compare, and how free blocks are tracked.

Many files share one disk. The allocation method decides which blocks each file gets and how the file system records them, with two goals that pull against each other: use the disk space well and reach any part of a file quickly. Three methods are in wide use — contiguous, linked and indexed (this list is itself a one-mark question). A file system normally uses one method for all its files. This is the job of the file-organization module in Fig 1: turn "logical block i of this file" into a physical block number.

Contiguous allocation

Each file occupies a set of adjacent blocks. If a file of n blocks starts at block b, it occupies b, b + 1, …, b + n − 1, and its directory entry needs only the start block and the length.

Fig 8. Contiguous allocation (Silberschatz Fig 12.5). mail starts at 19 with length 6, so it occupies blocks 19–24.

Access. Both kinds of access are easy. Sequentially, the file system remembers the last block read and reads the next one; directly, block i of a file starting at b is simply b + i. Reading block b + 1 after b normally needs no head movement, so the number of seeks is minimal. This makes contiguous allocation the fastest method.

Problems:

  1. Finding space for a new file. This is the dynamic storage-allocation problem from Unit III (first fit, best fit, worst fit): choose a hole of at least n free blocks. First fit and best fit beat worst fit; first fit is usually faster.
  2. External fragmentation. As files are created and deleted, free space breaks into small holes, and eventually no hole is big enough even though the total free space is. The cure is compaction (defragmentation): copy everything off and back so all free space forms one hole. It can take hours on a large disk; older systems had to do it off-line, and on-line defragmenting costs a lot of performance.
  3. Declaring the size in advance. The file's final size must be known when it is created. Too little, and the file cannot grow (its neighbours are in use), so the program must stop or the file must be copied to a bigger hole. Too much, and the unused space is wasted (internal fragmentation), especially for a file that grows slowly over months.

Extents. A common fix is a modified contiguous scheme: allocate a contiguous chunk, and when it fills, add another contiguous chunk called an extent. The file's location becomes a list of (start, count) pairs. Veritas uses extents; so do NTFS ("runs", 5.6) and ext4 (5.7). Internal fragmentation returns if extents are too large, and external fragmentation if extents of many sizes come and go.

Linked allocation

Each file is a linked list of disk blocks, which may be anywhere on the disk. The directory holds pointers to the first and last blocks; each block holds a pointer to the next. The pointers are hidden from the user: with 512-byte blocks and 4-byte pointers, the user sees 508 bytes per block.

Fig 9. Linked allocation (Silberschatz Fig 12.6). The file jeep starts at block 9 and continues at 16, 1, 10 and 25.

Creating and growing. A new file needs only a directory entry with a null first pointer and size 0. A write takes any free block from the free-space manager and links it to the end. There is no external fragmentation (any free block will do), the size need not be declared, a file can grow while free blocks exist, and compaction is never needed.

Disadvantages:

  • Effectively sequential only. To find block i you must start at the first block and follow i pointers, and each pointer is a disk read (often with a seek). Direct access is inefficient.
  • Space for pointers. 4 bytes of every 512 is 0.78% of the disk. The usual remedy is to allocate clusters of blocks (say 4 blocks, 2048 bytes): the overhead falls to 0.20% and there are fewer seeks, but a partly full cluster wastes more space (more internal fragmentation). Clusters are used in most file systems for this reason.
  • Reliability. If one pointer is damaged by a bug or a disk error, the rest of the file is lost, or the chain may run into the free list or another file. Doubly linked lists, or storing the file name and block number in every block, help, at the cost of more overhead.

The File Allocation Table (FAT): linked allocation with the links in a table

An important variation moves all the pointers out of the data blocks into one table at the start of the volume, the file-allocation table, used by MS-DOS and still used by FAT32 and USB drives. The table has one entry per disk block, indexed by block number:

  • the directory entry holds the number of the file's first block;
  • the FAT entry for a block holds the number of the next block of the file;
  • the last block's entry holds a special end-of-file value;
  • an unused block's entry is 0, so the FAT doubles as the free-space list.
Fig 10. File-allocation table (Silberschatz Fig 12.7). The file test uses blocks 217, 618 and 339, in that order.

Allocating a block is simple: find the first 0 entry, put its number in place of the file's old end-of-file value, and write end-of-file into the new entry. Cost: unless the FAT is cached, every block access needs two head movements, one to the FAT at the start of the volume and one to the block. Benefit: random access improves, because the OS can find block i by walking the chain in the table without reading the data blocks in between.

Answer

This is FAT with the whole table cached in RAM (Tanenbaum calls it "linked-list allocation using a table in memory"). The pointer word is taken out of every disk block and stored in the table, one entry per block; the directory gives the first block and each entry gives the next.

  • Advantage 1 — whole blocks for data. No pointer sits inside the data, so a block stores a full power-of-two of data (512 or 4096 bytes, not 508).
  • Advantage 2 — fast random access. To reach block i, follow i entries in memory, with no disk reads, then read one data block. For the file in Fig 10, logical block 2 is found by two table lookups (217 → 618 → 339) and one disk read.
  • Advantage 3 — free-space tracking for free: 0 entries are the free list.
  • Disadvantage — memory. The entire table must stay in RAM all the time, and it grows with the disk, not with the files in use. A 1 TB disk with 1 KB blocks has 230 blocks; at 4 bytes per entry the table needs 4 GB of memory. This is why large disks use indexed schemes (inodes, MFT), which keep only the open files' pointers in memory.
  • Reliability: one damaged table loses every file, so FAT volumes keep two copies.

Indexed allocation

Linked allocation cannot do direct access efficiently because the pointers are scattered with the blocks. Indexed allocation gathers all of a file's pointers into one place: each file has its own index block, an array of disk-block addresses whose i-th entry points to the i-th block of the file. The directory holds the address of the index block. To read block i, look up entry i. This is the same idea as a page table in Unit III.

Fig 11. Indexed allocation (Silberschatz Fig 12.8). Entry i of index block 19 is the address of jeep's i-th block; −1 marks entries not yet used.

When the file is created, every pointer in its index block is null (−1). When block i is first written, a free block is taken from the free-space manager and its address stored in entry i.

Advantages: direct access is supported, and there is no external fragmentation, because any free block can satisfy a request. Disadvantage: wasted space. A whole index block is needed even for a file of one or two blocks, so the pointer overhead is generally larger than in linked allocation.

How big should the index block be?

Small index blocks waste less space on small files but cannot describe large files. Three mechanisms solve this:

  • Linked scheme — an index block is one disk block; for a large file, the last word of an index block points to another index block (null for a small file).
  • Multilevel index — a first-level index block points to second-level index blocks, which point to the data blocks (like a two-level page table). With 4,096-byte blocks and 4-byte pointers, one index block holds 4096 / 4 = 1024 pointers, so two levels give 1024 × 1024 = 1,048,576 data blocks, a file of up to 1,048,576 × 4 KB = 4 GB.
  • Combined scheme (UNIX inode) — keep, say, 15 pointers in the inode itself. The first 12 are direct pointers to data blocks, so small files need no separate index block at all. The 13th points to a single indirect block (an index block of data-block addresses), the 14th to a double indirect block, and the 15th to a triple indirect block.

Performance and comparison

Choose the method by how files will be used: a system with mostly sequential access should not use the same method as one with mostly random access.

  • Contiguous: any block needs one access, because its address is computed from the start address.
  • Linked: fine for sequential access (keep the next address in memory); for direct access block i may need i disk reads. Some systems therefore use contiguous allocation for direct-access files and linked for sequential ones, and make the user declare the access type at creation.
  • Indexed: one access if the index block is in memory; otherwise the index block first and then the data. With multilevel indexes, a block near the end of a huge file may need several index reads first.
  • Some systems combine methods: contiguous for small files (three or four blocks) and indexed once the file grows. Since most files are small, average performance is good.

Free-space management supporting

Every allocation method needs to know which blocks are free. The free-space list records them (it need not literally be a list):

  • Bit vector (bitmap) — one bit per block: 1 = free, 0 = allocated (Silberschatz's convention; some systems use the opposite). Simple, and very fast at finding the first free block or n consecutive free blocks, because the CPU can test a whole word at a time. Its weakness is size: it must be in memory to be efficient.
  • Linked list — link all free blocks together, keeping a pointer to the first. No extra space, but traversing it needs a read per block (rarely needed, since allocation takes the first block).
  • Grouping — the first free block stores the addresses of n free blocks; the first n − 1 are free and the last holds the next n addresses. Many free addresses are found with one read.
  • Counting — since blocks are often freed in runs, store (first free block, count) pairs, which gives a much shorter list.
  • FAT needs none of these: its 0 entries are the free list.

5.5

Case study: FAT, FAT32 and exFAT

The simplest real file system: a directory entry, a table of next-cluster numbers, and data clusters. Why it is everywhere, and where it runs out.

FAT is the linked allocation with a table from 5.4, turned into a whole file system. It began with MS-DOS and is understood by almost every device — cameras, phones, TVs, car stereos — which is why Windows still formats USB thumb drives, camera flash cards and some external disks with FAT32 for portability, even though its own local volumes use NTFS. Its big weakness is just as simple: FAT does not restrict file access to authorised users. The only way to protect data on a FAT volume is to encrypt it with an application before storing it.

Source noteSilberschatz covers the FAT mechanism (§12.4.2) and its role and weakness (§19.5). The on-disk layout, entry widths, size limits and everything about exFAT are not in your materials; they are standard published facts, kept to what an exam answer needs.

Layout of a FAT volume

Fig 13. FAT-family volume layouts (not in your materials; simplified). The FAT is kept twice in FAT12/16/32; exFAT normally keeps one FAT and tracks free space in a bitmap.
  • Boot sector — boot code plus the BIOS parameter block: bytes per sector, sectors per cluster, number of FATs, size of each FAT, and so on. It plays the role of the volume control block.
  • The FATs — usually two identical copies, so that one damaged table can be recovered from the other.
  • Root directory — in FAT12/16 a fixed-size region right after the FATs (so the root can hold only a fixed number of entries); in FAT32 an ordinary cluster chain that can grow.
  • Data region — divided into clusters (a power-of-two number of sectors, the unit of allocation), numbered from 2.

The directory entry is the FCB. Each 32-byte entry holds an 8.3 name (8-character name, 3-character extension), an attribute byte (read-only, hidden, system, volume label, directory, archive), creation and modification times, the first cluster number and the file size (32 bits). Long names (Windows 95 "VFAT") are stored in extra directory entries placed before the 8.3 entry, 13 characters each.

FAT12, FAT16 and FAT32

exFAT not in your materials

exFAT (Extended FAT, Microsoft, 2006) was designed for flash media that are too large for FAT32 but where NTFS is too heavy. It is the required file system for SDXC memory cards. It keeps the FAT idea but fixes its main limits:

  • 64-bit file sizes — no 4 GB limit; clusters can be up to 32 MB.
  • Allocation bitmap for free space — one bit per cluster, as in 5.4, so free space is found without scanning the FAT.
  • Contiguous files skip the FAT — a directory entry can mark a file as contiguous ("no FAT chain"); its clusters are then just start + i, like contiguous allocation, and the FAT is used only for fragmented files. Fewer writes to one hot spot also suits flash memory, which wears out.
  • Better directories — UTF-16 names up to 255 characters, a hash of each name for faster lookup, and a checksum over each group of directory entries.
  • Like FAT, exFAT has no owners or permissions and no journaling; after a crash or an unsafe removal the volume should be checked. Microsoft published the specification in 2019, and Linux now supports exFAT natively.
One-line summary for examsFAT12/16/32 = linked allocation through a table of next-cluster numbers, with the directory entry as FCB, two copies of the FAT and no security. FAT32 widens the entries to 28 bits but keeps a 4 GB file limit. exFAT adds 64-bit sizes, a free-space bitmap and FAT-free contiguous files for large flash media.

5.6

Case study: NTFS

Windows' native file system: everything, including the metadata, is a file described by a row of the master file table.

NTFS (the NT File System, introduced with Windows NT in 1993) is used for all local Windows volumes. Compared with FAT it adds security (an access-control list on every file), recovery (a transaction log), very large files and volumes, file and volume encryption (BitLocker for whole volumes), compression, sparse files, multiple data streams, Unicode names and volume shadow copies (point-in-time snapshots).

Volumes, clusters and logical cluster numbers

The basic unit is a volume, created by the logical disk manager from a partition; it can be part of a disk, a whole disk, or span several disks. NTFS never deals with sectors directly: it allocates clusters, a power-of-two number of sectors chosen at format time (4 KB by default for volumes larger than 2 GB). Bigger clusters can be faster but waste more space at the end of each file (internal fragmentation).

Disk addresses are logical cluster numbers (LCNs), numbering clusters from the start of the volume, so the byte offset of a cluster is simply LCN × cluster size. Example: LCN 1000 with 4 KB clusters is at 1000 × 4096 = 4,096,000 bytes. Within a file, clusters are numbered by virtual cluster numbers (VCNs) 0, 1, 2…

Files are sets of attributes: the master file table

In UNIX a file is a simple byte stream; in NTFS a file is a structured object made of typed attributes, each an independent byte stream that can be created, read, written and deleted. Standard attributes include the file name (or names: a long name and an MS-DOS 8.3 alias), the standard information (times, flags) and the security descriptor (owner and ACL). The user's bytes are in a data attribute: normally one unnamed data stream, but extra named streams can be added (written file:stream), for example to hold an image thumbnail. Directory listings report only the unnamed stream's size.

Every file is described by one or more records in an array stored in a special file, the master file table (MFT). A record is 1–4 KB (fixed when the volume is formatted).

  • Resident attributes — small attributes are stored inside the MFT record itself. A very small file's data fits in its record, so reading it needs no other disk access.
  • Non-resident attributes — large ones (usually the data) are stored in one or more contiguous extents ("runs") on disk; the record holds a pointer to each run as (starting LCN, length).
  • If a file has many attributes, or is so fragmented that its run list does not fit, the base file record points to overflow records.
  • Each file has a 64-bit file reference = 48-bit file number (its record's slot in the MFT) + 16-bit sequence number, which is incremented whenever the slot is reused. A stale reference to a deleted file then fails a consistency check instead of silently reaching the new file.

Directories and metadata files

The namespace is a hierarchy of directories, as in UNIX. Each directory stores an index of its file names as a B+ tree: every path from the root to a leaf has the same length, so lookups stay fast and the tree never needs a full reorganisation. Each directory entry holds the name and the file reference, plus a copy of the file's timestamp and size, so a directory listing can be produced without opening every file's MFT record.

All volume metadata lives in files, described by the first MFT records (Fig 14): the MFT itself; a mirror of its first records, used for recovery if the MFT is damaged; the log file of metadata updates; the volume file (volume name, NTFS version, and a "dirty" bit saying whether chkdsk must run); the attribute-definition table; the root directory; the bitmap file recording which clusters are free; the boot file (startup code, at a fixed address, which also records where the MFT is); and the bad-cluster file. Because metadata are ordinary files, the cache manager caches them exactly like user data.

Recovery: transaction logging

A simple file system can be scrambled by a power failure in the middle of an update; UNIX's traditional answer is to run fsck over the whole volume after a crash, which is slow and may lose data. NTFS instead performs every change to its data structures inside a transaction:

  1. Before changing a structure, write a log record containing redo and undo information.
  2. Change the structure (in the cache).
  3. Write a commit record to the log.
  4. After a crash, process the log: redo committed transactions, then undo those that never committed.

A checkpoint record is written periodically (usually every 5 seconds); log records older than it are not needed, so the log does not grow without bound. The log is the third metadata file: a circular logging area plus a restart area kept in two copies. Recovery runs automatically the first time the volume is accessed after startup. It guarantees that the metadata are consistent; it does not guarantee that user file contents are complete.

Security

Every file refers to a security descriptor: the owner and an access-control list that grants or denies each listed user or group specific permissions (5.13). Since Windows 2000 the descriptor attribute points to a shared copy, because many files have identical descriptors, saving disk and cache space. By default NTFS does not check permissions on every directory along a path (it matches cached path prefixes instead); POSIX-style traversal checks can be enabled.

5.7

Case study: ext2, ext3 and ext4

Linux's extended file systems: inodes in block groups (ext2), a journal for fast crash recovery (ext3), and extents for large files (ext4).

Linux began with a Minix-compatible file system, limited to 14-character names and 64 MB. Its replacement, the extended file system (ext), was redesigned as ext2 for performance and scalability; adding journaling produced ext3, and adding extents and other modern features produced ext4. Each is backward compatible with the one before. All three follow the UNIX model: directories map names to inode numbers, and the inode (Fig 12) holds the attributes and block pointers.

ext2: inodes and block groups

ext2 allocates in blocks of 1, 2 or 4 KB, chosen when the file system is made. After an initial boot block, the volume is divided into equal-sized block groups, each a small self-contained file system:

Fig 15. ext2 on-disk layout (Kerrisk §14.3; group contents not in your materials). Every group repeats the superblock and descriptors for safety.
  • Superblock (copied into groups for safety) — the volume control block: block size, counts of blocks and inodes, free counts.
  • Group descriptors — where each group's bitmaps and inode table are, and their free counts.
  • Block bitmap and inode bitmap — the bit-vector free-space maps for the group's data blocks and inodes.
  • Inode table — the group's inodes: type, owner, group, permissions, three timestamps, link count, size, block count, and 15 block pointers (12 direct, single, double, triple indirect).
  • Directories are files whose blocks hold a linked list of variable-length entries: inode number, entry length, name length, name.

Allocation policy. Keeping related data together cuts seeks: a file's data goes in the same group as its inode, a file's inode goes in its parent directory's group, and directories are spread across groups to balance the load. Within a group, ext2/ext3 try to keep a file's blocks physically contiguous, search the bitmap a byte at a time for runs of 8 free blocks, and preallocate up to 8 extra blocks to a growing file (returned to the free map when the file is closed).

The problem ext2 left open: a crash in the middle of an update (say, an inode written but not the bitmap) leaves inconsistent metadata, so after every crash fsck must check the entire file system. That takes seconds on a small disk but hours on a large one.

ext3: ext2 plus a journal

Journaling writes every change to the file system first to a journal (log), sequentially, as a transaction:

Fig 16. Journaling (Silberschatz §18.7.3; step names after Three Easy Pieces ch. 42). Recovery reads only the journal, never the whole disk.
  • Once a transaction is written to the journal it is committed. Its entries are then replayed onto the real file-system structures, a pointer tracks which actions are done, and a completed transaction is removed. The journal is a circular buffer, in a separate area of the volume or even on a separate disk.
  • After a crash, committed transactions still in the journal are completed; any changes from an aborted (uncommitted) transaction are undone. That is all the recovery needed — no full consistency check — so even a huge ext3 volume is usable within seconds.
  • Speed: journaling can even make metadata operations (create, delete) faster, because costly synchronous random writes become synchronous sequential writes to the journal, and the random writes to home locations happen later, asynchronously.
  • Modes not in your materials: journal (data and metadata both logged: safest, slowest), ordered (the default: only metadata logged, but data blocks are written before their metadata commits) and writeback (metadata only, no ordering: fastest). ext3 can be set to journal only metadata.
  • Moving from ext2 to ext3 needs no backup and restore — a journal is simply added — and an ext3 volume can still be mounted as ext2. ext3 also added an optional hashed B-tree index for large directories (HTree).

ext4: extents and large volumes mostly not in your materials

Silberschatz notes only that ext4 augments ext3 "with modern file-system features such as extents". The main changes:

  • Extents replace indirect blocks for new files. An extent says "this file's logical blocks L…L+n map to physical blocks P…P+n"; one extent covers up to 32,768 blocks, which is 128 MiB with 4 KiB blocks. The inode holds four extents; more are kept in a small tree. Large contiguous files need a handful of extents instead of thousands of pointers.
  • 48-bit block numbers — volumes up to 248 × 4 KiB = 1 EiB; files up to 232 blocks × 4 KiB = 16 TiB.
  • Delayed allocation — blocks are chosen only when data are flushed to disk, when the final size is known, and a multiblock allocator grabs many blocks at once; both give more contiguous files.
  • Persistent preallocation (fallocate()) reserves contiguous space for a file in advance (useful for videos and databases).
  • Checksums on the journal, nanosecond timestamps, no 32,000-subdirectory limit, and faster fsck because unused inode tables can be skipped.
  • An ext3 volume can be mounted as ext4; old files keep their indirect blocks and new files get extents.

Case study: the Virtual File System (VFS)

How one kernel offers the same open/read/write/close to ext4, FAT, NTFS, network and even imaginary file systems.

A modern OS must support many file-system types at the same time — an ext4 root disk, a FAT32 pen drive, an NTFS external disk, an NFS share — and users must move between them without noticing. Writing separate directory and file routines for each type would be wasteful. Instead, the kernel uses object-oriented techniques: a virtual file system layer separates the generic system-call interface from each file system's implementation.

Three layers

Fig 17. The VFS architecture (after Silberschatz Fig 12.4 and Kerrisk Fig 14-3). The application sees one interface; each file system plugs in underneath.
  1. File-system interface — the open(), read(), write(), close() calls and file descriptors that programs use.
  2. VFS layer — it has two jobs. (a) It separates file-system-generic operations from their implementation by defining a clean VFS interface; several implementations can coexist on one machine, giving transparent access to different file-system types mounted locally. (b) It gives each file a representation that is unique even across a network: the vnode (UNIX inodes are unique only within one file system). The kernel keeps one vnode per active file or directory. The VFS can therefore tell local files from remote ones, and local files apart by file-system type.
  3. File-system implementations — the code for each type (ext4, FAT, NTFS…) or, for remote files, the NFS protocol. The VFS calls the right one for each request.

A file system need not store anything on disk: Linux's /proc file system computes its "files" on demand from kernel data (one directory per process ID, plus files of kernel statistics), and programs read them with ordinary read(). If a file system lacks an operation (FAT has no symbolic links), it returns an error, which the VFS passes back to the program.

The Linux VFS: four object types

The Linux VFS defines four main object types. Every object contains a pointer to a function table listing the addresses of the functions that implement its operations for that particular file system.

Fig 18. The four Linux VFS objects and how an operation is dispatched through a function table (Silberschatz §18.7.1; the field names are simplified).
  • inode object — represents an individual file: owner, size, modification time and pointers to the data blocks. There is only one inode object per file, however many processes use it, and it may stay cached after every process has finished with the file. Because directory operations (create, delete, rename an entry) do not need the directory to be opened, they are defined on the inode object.
  • file object — represents an open file: the current read/write position, the permissions requested at open, and read-ahead state. There is one per open(), usually belonging to one process. A process cannot reach an inode's contents without first obtaining a file object.
  • superblock object — represents an entire file system: one per mounted disk and per connected network file system. Its main job is to provide access to inodes: the VFS identifies every inode by a (file system, inode number) pair and asks the superblock for it.
  • dentry object — represents an individual directory entry. /usr/include/stdio.h has four: /, usr, include and stdio.h. Translating a path means walking these one by one, reading each directory; the dentry cache makes repeated lookups far faster than reading the directories from disk.

How dispatch works. For the file object, the function table (struct file_operations in /usr/include/linux/fs.h) contains entries such as open(), read(), write() and mmap(). Each file system fills in its own functions. The VFS calls "the read entry of this file's table" without knowing or caring whether the file is on a local disk, across the network, a socket or a directory: the right function is always in the same slot.

5.9

Goals and principles of protection

Why an OS needs protection, the difference between policy and mechanism, and the principle of least privilege.

Not in your materials — added for syllabus completenessNone of your faculty material covers system protection. Sections 5.9–5.13 follow Silberschatz, 9th ed., chapter 14 (§§14.1–14.7) and §11.6, using the book's own examples so you can check them.

Protection is a mechanism for controlling the access of programs, processes or users to the resources defined by a computer system — files, memory segments, the CPU, devices. The mechanism must give a way to specify the controls and a way to enforce them. Only processes that have the proper authorisation from the OS may operate on a resource.

Protection is not security. Protection is an internal problem: controlling access to resources by the users and programs already inside the system. Security is a measure of confidence that the integrity of the system and its data will be preserved, which also needs protection against external threats — intruders, malware, attacks. Security depends on protection, plus authentication, encryption and more.

One-mark answer (Paper B, Apr 2023, Q1.10): "What is authentication?"Authentication is verifying the identity of a user (or process) before granting access — proving that you are who you claim to be — using something the user knows (password), has (token, card) or is (fingerprint). It belongs to security; protection then decides what the authenticated user may do.

Goals of protection

Protection began as an add-on to multiprogramming, so that untrustworthy users could safely share a common logical name space (a directory of files) or physical name space (memory). Today it is needed to make any complex system with shared resources reliable:

  1. Prevent intentional misuse — stop a user from mischievously violating an access restriction.
  2. Enforce stated policies — more generally, ensure that each program component active in the system uses resources only in ways consistent with stated policies. This is an absolute requirement for a reliable system.
  3. Improve reliability by detecting errors early — checks at the interfaces between subsystems catch latent errors, so a malfunctioning subsystem cannot contaminate a healthy one.
  4. Distinguish authorised from unauthorised use — an unprotected resource cannot defend itself against use by an unauthorised or incompetent user.
  5. Provide mechanisms for enforcing many policies — some policies are fixed in the system's design, some are set by the administrators, and some by individual users to protect their own files and programs. Policies change from application to application and over time, so protection must be flexible, and application programmers must be able to use it too.

Policy versus mechanism. Mechanisms determine how something is done; policies decide what is done. Keeping them separate gives flexibility: a policy change (say, "students may no longer print after 10 p.m.") should only need new settings, not a new mechanism. The access matrix is the classic example of a general mechanism that can express many policies.

Principles of protection

A guiding principle keeps design decisions consistent. The key, time-tested principle for protection is the principle of least privilege: programs, users and even systems should be given just enough privileges to perform their tasks, and no more.

Analogy: a security guard's passkey that opens only the public areas she guards limits the damage if the key is lost, stolen, misused or copied. A master key that opens everything makes any compromise a disaster. Likewise, if a buffer overflows in a system daemon that has least privilege, the daemon may fail, but the attacker should not gain control of the whole system.

An OS that follows the principle:

  • implements its features, programs, system calls and data structures so that the failure or compromise of one component does the minimum damage;
  • provides fine-grained access controls to applications, with ways to enable privileges only when needed and disable them afterwards;
  • keeps audit trails of all privileged-function access, so administrators can trace protection and security activity;
  • gives each user a separate account with only the privileges that user needs (an operator who mounts tapes and runs backups gets only those commands and files), often through role-based access control;
  • limits each machine to the specific services, remote hosts and times it needs, using access-control lists.

Least privilege helps but does not guarantee security: Windows 2000 had a complex protection scheme yet many security holes, partly because it had more code and services to protect. A related rule, the need-to-know principle, says that at any moment a process should be able to access only the resources it currently needs; it is introduced with domains.

5.10

Domain of protection

Objects, access rights and domains; how a process moves between domains in UNIX and MULTICS.

A computer system is a collection of processes and objects. Objects are hardware (CPU, memory segments, printers, disks, tape drives) or software (files, programs, semaphores). Each object has a unique name and can be accessed only through well-defined operations, so objects behave like abstract data types. The operations depend on the object: a CPU can only execute; memory segments can be read and written; a DVD-ROM can only be read; a tape can be read, written and rewound; data files can be created, opened, read, written, closed and deleted; program files can be read, written, executed and deleted.

A process should access only resources it is authorised for, and at any time only those it currently requires to complete its task. The second requirement is the need-to-know principle. Example: when a process calls procedure A(), the procedure should access only its own variables and the parameters passed to it, not all of the process's variables; a compiler invoked to compile one file should access only the files related to that compilation, not arbitrary files.

Domain structure

A process operates within a protection domain, which specifies the resources it may access.

  • An access right is the ability to execute an operation on an object, written as an ordered pair <object-name, rights-set>. If domain D has <file F, {read, write}>, a process in D can read and write F, and do nothing else to it.
  • A domain is a collection of access rights.
  • Domains may share access rights.
Fig 19. A system with three protection domains (Silberschatz Fig 14.1). D2 and D3 overlap: both may print O4. Only D1 may read and write O1; only D3 may execute it.

Static versus dynamic association. If the set of resources available to a process is fixed for its lifetime, the association is static. But a process may have phases — reading in one, writing in another. A static domain must then include both rights, giving more than is needed in each phase and violating need-to-know. So either the contents of a domain must be changeable, or the association must be dynamic, with domain switching: the process moves from one domain to another (which also achieves a content change, by switching to a new domain with the changed content).

What can be a domain?

  • Each user — the accessible objects depend on the user's identity; switching happens when one user logs out and another logs in.
  • Each process — switching happens when one process sends a message to another and waits for the response.
  • Each procedure — the accessible objects are the procedure's local variables; switching happens at each procedure call.

The familiar dual-mode design (kernel/user mode) is a system with just two domains: kernel mode can run privileged instructions and protects the OS from user processes. A multiprogrammed system needs more, because users must also be protected from one another. UNIX and MULTICS show two ways to do it.

Example: UNIX

In UNIX a domain is associated with the user, and switching domain means temporarily changing the user ID. Each file has an owner ID and a domain bit, the setuid bit. When a user executes a file whose setuid bit is on, the process's (effective) user ID becomes the file owner's for as long as the program runs; with the bit off, it stays the caller's.

Constructed example (Linux)worked example
Ordinary users must change their own password, but the password hashes are in /etc/shadow, which only root may write. How does UNIX allow this without giving users root access?
Answer

The program /usr/bin/passwd is owned by root and has the setuid bit set; ls -l shows it as -rwsr-xr-x (the s in the owner's execute position). When user ana runs it, the process executes in root's domain — its effective user ID is root — so it can update /etc/shadow. The program itself limits what it does (it changes only ana's own entry, after asking for her old password). When it exits, the temporary domain switch ends.

The danger: if a user manages to create a root-owned file with the setuid bit on, that user can become root. Setuid programs are therefore the first targets of attackers and must be written with great care. Alternatives: put privileged programs in a special directory whose programs run with changed IDs (less flexible), or forbid ID changes and use a privileged daemon started at boot, to which users send requests (TOPS-20).

Example: MULTICS rings

In MULTICS, protection domains are organised hierarchically into rings numbered 0 to 7. If j < i, domain Di is a subset of Dj: a process in an inner ring has more privileges, and ring 0 has the most. With only two rings this is exactly kernel/user mode.

Fig 20. MULTICS rings (after Silberschatz Fig 14.2) and the rules for crossing them.

Each segment (MULTICS segments are files) belongs to a ring and has read, write and execute bits. A current-ring-number counter per process records the ring it is executing in. A domain switch happens when a process calls a procedure in another ring, and it must be controlled — otherwise a process could simply start running in ring 0. So each segment descriptor carries an access bracket (b1 ≤ b2), a limit b3 > b2 and a list of gates (permitted entry points), used as in Fig 20. This lets processes with few rights call more privileged procedures, but only at approved entry points.

Access matrix

The general model of protection: a table of who (domain) may do what (rights) to which object, including rights to change the table itself.

The protection model can be viewed abstractly as a matrix, the access matrix. Rows represent domains, columns represent objects, and each entry is a set of access rights: access(i, j) is the set of operations a process executing in domain Di may invoke on object Oj. Because the column names the object, the object name is omitted from the rights in each cell.

D2print
D3readexecute

Access matrix A (Silberschatz Fig 14.3): four domains, three files and a laser printer.

Read it row by row: a process in D1 can read F1 and F3. A process in D4 has the same privileges as D1 and can also write F1 and F3. Only a process in D2 can use the printer.

Mechanism and policy. The matrix is a mechanism: implementing it, and ensuring that a process in Di accesses only the objects in row i and only as the entries allow. The policy decisions are which rights go in each entry and which domain each process runs in. Users normally decide the entries: when a user creates an object Oj, column j is added with the entries the creator chooses. The OS usually decides the domain.

5.12

Implementation of the access matrix

Storing a large, mostly empty matrix: global table, access lists (columns), capability lists (rows) and lock–key, then revocation.

The matrix is usually sparse — most entries are empty (matrix A has 7 non-empty cells out of 16). General sparse-matrix techniques do not suit the way protection is used, so four specific methods are used.

Fig 21. Slicing matrix A: a column becomes an object's access list; a row becomes a domain's capability list.

1. Global table

The simplest implementation: a set of ordered triples <domain, object, rights-set>. When operation M is executed on object Oj in domain Di, the table is searched for <Di, Oj, Rk> with M ∈ Rk; if found the operation continues, otherwise an exception is raised. Drawbacks: the table is large, so it cannot stay in main memory and extra I/O is needed (virtual memory is often used for it); and special groupings cannot be exploited — if everyone may read an object, it needs a separate entry for every domain.

2. Access lists for objects (columns)

Each column becomes an access list for one object, a list of <domain, rights-set> pairs for the domains with non-empty rights; empty entries are discarded. The list can be extended with a default set of rights: to perform M on Oj in Di, search Oj's list for <Di, Rk> with M ∈ Rk; if absent, check the default set (or check the default first, for speed); otherwise deny. Access lists match how users think ("who may use my file?"), but finding all the rights of one domain is hard, and every access requires a search of a possibly long list.

3. Capability lists for domains (rows)

Each row becomes a capability list for one domain: a list of objects with the operations allowed on them. An object is represented by its physical name or address, called a capability. To perform M on Oj, a process names the capability for Oj as a parameter; simple possession of the capability means access is allowed.

The list belongs to a domain, but processes in that domain can never touch it directly: it is a protected object maintained by the OS. Security depends on capabilities never migrating into memory that a user process can modify. Capabilities are distinguished from ordinary data in one of two ways:

  • Tags: every object has a tag (at least one bit, enforced by hardware or firmware) saying whether it is a capability or ordinary data; application programs cannot change tags.
  • Split address space: one part holds the program's normal data and code; the other, holding the capability list, is accessible only to the OS (segmented memory helps).

Capability lists localise a process's rights and make checks quick (just validate the capability), but they do not match how users think, and revoking a right is hard because copies of capabilities are scattered through the system.

4. Lock–key mechanism

A compromise: each object has a list of unique bit patterns called locks, and each domain has a list of unique bit patterns called keys. A process in a domain may access an object only if the domain has a key matching one of the object's locks. The OS manages the key lists; users cannot examine or modify them. Keys can be passed freely between domains, and access is revoked simply by changing an object's locks.

Most systems combine access lists and capabilities. The first time a process accesses an object, the access list is searched; if access is allowed, a capability is created and attached to the process, and later accesses just present the capability; after the last access it is destroyed (MULTICS, CAL). UNIX does exactly this with files: open() searches the directory, checks the permission bits (the access list) and returns an index into the per-process file table. That entry acts as a capability for the modes granted: a file opened for reading gets a read capability, and a later write() is refused by comparing the request with it. Revocation of access rights supporting

In a dynamic system, rights sometimes need to be taken back. Four questions arise: immediate or delayed? selective or general (some users or all)? partial or total (some rights or all)? temporary or permanent?

With access lists, revocation is easy: search the list and delete the rights. It is immediate and can be general or selective, total or partial, permanent or temporary. With capabilities it is hard, because they are spread through the system and must be found first. Schemes:

  • Reacquisition — capabilities are periodically deleted from each domain; a process must reacquire them, and fails if access has been revoked.
  • Back-pointers — each object keeps pointers to all its capabilities, which can be followed and changed (MULTICS; general but costly).
  • Indirection — capabilities point to an entry in a global table, which points to the object; deleting the table entry revokes them (CAL; not selective).
  • Keys — each capability carries a key that must match the object's master key; changing the master key (the set-key operation) invalidates all old capabilities. A list of keys per object, or a global key table, allows selective revocation.

5.13

Access control

Access control in practice: protected operations on files, access-control lists, the UNIX owner/group/others bits, and role-based access control.

Systems that never let users access each other's files need no protection; systems with no restrictions give no protection. Both extremes are useless — what is needed is controlled access: permit or deny each operation depending on, among other things, the type of access requested. The operations usually controlled on a file are read, write, execute, append, delete and list (list the name and attributes). Higher-level operations such as copy or rename are built from these, so protecting the low-level ones is enough: anyone who may read a file can also copy or print it.

Access-control lists (ACLs)

The most common approach is to make access depend on the identity of the user. The most general scheme attaches to each file and directory an access-control list naming users and the access each one is allowed. On every request, the OS checks the file's ACL; if the user is listed for that access it is allowed, otherwise a protection violation occurs. This is the access-list implementation of the matrix (5.12) applied to files.

ACLs allow very detailed policies, but they have two problems: they can be long and tedious to build (allowing everyone to read means listing every user, and the user list may not be known in advance), and the directory entry, previously of fixed size, becomes variable-sized, complicating space management.

Owner, group and universe

To condense the list, many systems recognise three classes of user for each file:

  • Owner — the user who created the file;
  • Group (work group) — a set of users who share the file and need similar access;
  • Universe (others) — all other users.

UNIX gives each class three bits, r (read), w (write) and x (execute), so only 9 bits per file record its protection. The same bits apply to directories: r allows listing the directory, w allows creating and deleting entries in it, and x allows entering it (cd) or passing through it in a path. Groups can be created and changed only by the system manager (or superuser), so control is ultimately by human administration.

The most common modern approach combines the two: owner/group/universe bits by default, plus optional ACLs for files that need finer control. Solaris (and Linux) show an extra + after the permission string when an ACL is present, as in -rw-r--r--+, and use the setfacl and getfacl commands to manage ACLs. Windows NTFS uses ACLs throughout (5.6), with entries that can allow or deny.

Role-based access control (RBAC)

Access control can be applied to more than files. Solaris 10 adds the principle of least privilege to the whole OS through role-based access control. It revolves around privileges: a privilege is the right to execute a system call, or to use an option within a system call (such as opening a file with write access). Privileges can be assigned to processes, limiting each to exactly what its work needs. Privileges and programs can also be assigned to roles; users are assigned roles, or take roles by giving a role's password. A user who takes a role can then run a program with that role's privileges to perform a specific task.

Fig 22. Role-based access control in Solaris 10 (after Silberschatz Fig 14.8). Privileges belong to roles, not to all-powerful accounts.

RBAC reduces the risk of superuser accounts and setuid programs: instead of making a backup operator root, the operator takes a role that has only the "read any file" and "mount tape" privileges. Roles play the part of domains and privileges the part of rights, so RBAC is a structured way of filling in the access matrix.
