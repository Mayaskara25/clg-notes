Old What an Operating System Does

Background retained from older notes; the prerequisite OS definition is included in the required services section

Goals of an OS, the three roles it plays, and how "the operating system" looks different depending on who is looking at it.

A computer system can be divided into four components: the hardware (CPU, memory, I/O devices) which supplies the raw computing resources; the application programs (word processors, browsers, compilers) which define how those resources are used to solve users' problems; the users; and the operating system, which controls the hardware and coordinates its use among the application programs and users. An operating system is thus a program that acts as an intermediary between the user of a computer and the computer hardware — it manages hardware and software resources and provides a stable, consistent environment in which applications can run.

The kernel is the core of the operating system that remains resident and manages privileged access to hardware. “Operating system” can also include associated system software; an OS is not just one continuously executing process. Alongside the kernel there are two other categories of software: system programs, which are associated with the operating system but are not part of the kernel itself, and application programs, which include everything not associated with the operation of the system. Mobile operating systems often also include middleware — frameworks that give app developers services such as databases, multimedia and graphics support, layered on top of the kernel. Familiar examples of operating systems include Windows and macOS on the desktop, Linux across servers/desktops/embedded systems, and Android and iOS on mobile devices.

Goals of an operating system

  • Execute user programs and make solving user problems easier.
  • Make the computer system convenient to use.
  • Use the hardware efficiently.

These goals are usually described through three complementary roles the OS plays:

  • Control freak — it must never lose control of the hardware.
  • Resource manager — it gives resources to applications, takes resources back from them, and enforces protection and security over who gets what.
  • Great pretender — it makes resources look different from how they really are, and makes finite resources appear infinite to the programs using them (for example, virtual memory making a small physical RAM look like a much larger address space).

User view vs. system view

How an operating system is designed and judged depends heavily on the kind of "user" it is built for:

  • Single-user PC — the system is designed mostly for ease of use, with performance mattering to the user but resource utilization (sharing hardware and software fairly among several users) barely mattering, since there is only one user.
  • Terminal connected to a mainframe/minicomputer — many users share the same machine, so the OS is designed to maximize resource utilization: ensuring CPU time, memory and I/O are used efficiently and that no individual user takes more than a fair share.
  • Workstations on a network — users have dedicated resources at their own desk but also share networked resources like file, compute and print servers, so the OS is designed to compromise between individual usability and shared resource utilization.

From the computer's own point of view, the operating system is the program most intimately involved with the hardware, so it can be viewed as a resource allocator: a computer system has many resources — CPU time, memory space, file-storage space, I/O devices — that may be required to solve a problem, and the OS decides how to allocate them among competing programs and users so the system runs efficiently and fairly. A related view treats the OS as a control program that manages the execution of user programs to prevent errors and improper use of the computer, and that is especially concerned with the operation and control of I/O devices.

Moore's law and the variety of operating systems

Present in older notes; not listed in the new syllabus

Moore's law predicted that the number of transistors on an integrated circuit would double roughly every eighteen months (the deck's figure; a doubling every one to two years is the usual statement), and the prediction has held remarkably well. Computers gained functionality and shrank in size, leading to a vast number of uses and a vast variety of operating systems. There is no universally accepted definition of what is part of an OS: "everything a vendor ships when you order an operating system" is a good approximation, but it varies wildly. The one dependable definition is the kernel, as above.

Old 1.2 · Computer System Organization

How the hardware underneath the OS is wired together, why storage is organized in a hierarchy, and how the system starts up.

Computer-system operation

A modern computer system consists of one or more CPUs and a number of device controllers, all connected through a common bus that provides access to shared memory. Each device controller is in charge of a specific type of device (disk drives, USB devices, graphics adapters) and, together with the CPUs, competes for memory cycles. To ensure that all these devices get orderly access to memory, a memory controller synchronizes access to shared memory.

Bootstrap program and interrupts

When a computer is powered on, it must run an initial program called the bootstrap program. It is typically stored in ROM or EPROM — hardware known as firmware — because this memory needs no initialization and is at a fixed location the CPU can start executing from. The bootstrap program initializes all aspects of the system (CPU registers, device controllers, memory contents), then loads and starts the operating-system kernel.

Once running, the OS waits for an event to occur — events are almost always signalled by an interrupt, from either the hardware or the software. Hardware may trigger an interrupt by sending a signal to the CPU, typically over the system bus. Software triggers an interrupt by executing a special operation called a system call (also called a monitor call).

Storage structure and hierarchy

Program instructions and the data they operate on must reside in main memory during execution — main memory is the only large storage area the CPU can access directly (via the load/store instructions of its instruction set). Because main memory is usually too small to hold all needed programs and data permanently, and is volatile (it loses its contents when power is removed), computer systems provide secondary storage — most commonly disks — as an extension of main memory.

Storage systems are organized in a hierarchy by speed, cost, and volatility: registers and cache are small, expensive, and extremely fast; main memory is larger but slower; solid-state and hard disks are larger still but far slower and non-volatile; optical disks and magnetic tape sit at the bottom — cheapest and largest, but slowest, often used only for backup. Caching — copying information into a faster storage system — is the general principle that makes this hierarchy work: main memory itself can be viewed as a cache for secondary storage.

Interrupt handling in more detail low priority

An interrupt is an urgent event that makes the CPU pause its current work, deal with the event, and then resume exactly where it left off. Hardware interrupts come from devices (a key press, a mouse click, a printer asking for more data); software interrupts come from a program executing a system call (also called a monitor call), and a trap (or exception) is a software-generated interrupt caused by an error or a service request. Handling follows a fixed sequence:

  1. The CPU is executing a task when an interrupt arrives; it stops and saves its current state (at least the program counter) so it can come back.
  2. It transfers control to a fixed location that holds the interrupt vector table (IVT) — an array of addresses indexed by interrupt number, each giving the starting address of the matching interrupt service routine (ISR).
  3. The ISR runs and deals with the event (for a key press, it works out which key was pressed).
  4. The saved state is restored and the interrupted computation resumes.

Interrupts make the system efficient: without them the CPU would have to keep polling every device continuously; with them it works on useful tasks and is disturbed only when something genuinely needs attention.

Storage details: the instruction cycle, volatility, tertiary storage low priority

  • Von Neumann instruction–execution cycle. The CPU fetches an instruction from memory into the instruction register; the instruction is decoded and may cause operands to be fetched from memory into internal registers; after the instruction has been executed on the operands, the result may be stored back to memory.
  • Why programs cannot live in main memory permanently: (1) it is usually too small to hold all needed programs and data, and (2) it is volatile. Hence secondary storage — most commonly the magnetic disk, which acts as both source and destination of programs' data — extends main memory.
  • Volatile vs. non-volatile. In the hierarchy, storage above the electronic disk is volatile, below it non-volatile. An electronic disk can be either: it holds data in a DRAM array (volatile) but many include a hidden magnetic disk and a battery, so that if power fails the controller copies the data from RAM to the magnetic disk; flash memory is another form.
  • Tertiary storage (optical disks and magnetic tape) is the slowest and cheapest level, ranging from WORM (write-once, read-many-times) to RW (read-write); it must still be managed by the OS or applications — mounting and unmounting media, allocating devices to processes, and migrating data from secondary to tertiary storage.
  • Disk-management activities of the OS: free-space management, storage allocation, and disk scheduling. Because the whole speed of a computer often hinges on the disk subsystem and its algorithms, these are of central importance.
  • Cache coherency. The same value can exist at several levels at once (magnetic disk → main memory → cache → hardware register). In a multiprocessor each CPU has its own cache, so a copy of a variable may sit in several caches; an update in one must be reflected in all others. This is called cache coherency and is a hardware problem, handled below the OS level.

I/O structure and DMA low priority

A large part of OS code is devoted to I/O, both for reliability and performance reasons and because of the varied nature of devices. Every device has a device controller with a local buffer and a set of special-purpose registers; the controller moves data between the device and its buffer, and the OS has a device driver for each controller that presents a uniform interface to the rest of the OS. Interrupt-driven I/O suits small amounts of data but has high overhead for bulk movement such as disk I/O. For bulk transfers direct memory access (DMA) is used: after the CPU sets up buffers, pointers and counters, the controller transfers an entire block directly between its buffer and main memory with no CPU intervention, and only one interrupt per block is generated to tell the driver the operation is complete. Meanwhile the CPU is free to do other work.

Computer-system architecture low priority

Systems are categorised roughly by the number of general-purpose processors they use.

Single-processor systems

There is one main CPU capable of executing a general instruction set, including instructions from user processes. The system may also contain special-purpose processors (disk, keyboard and graphics controllers) that run a limited instruction set and do not run user processes; the OS sends them tasks and monitors their status. For example, a disk-controller processor implements its own disk queue and scheduling, reducing the main CPU's load. Using such processors does not make the system a multiprocessor — if there is only one general-purpose CPU, it is a single-processor system.

Multiprocessor systems

Also called parallel systems or tightly coupled systems: two or more processors in close communication, sharing the computer bus, the clock, and sometimes memory and peripheral devices. Three main advantages:

  • Increased throughput — more work in less time. The speed-up with N processors is less than N, because of the overhead of keeping all parts working correctly and contention for shared resources.
  • Economy of scale — cheaper than several single-processor systems, since peripherals, mass storage and power supplies are shared.
  • Increased reliability — functions are distributed among processors, so if one fails the system slows down rather than halting. Two techniques: graceful degradation (the system continues to provide service proportional to the surviving hardware) and fault tolerance (a failure is detected, diagnosed and corrected, which needs extra hardware or software support).

Asymmetric multiprocessing (master–slave): each processor is assigned a specific task; a master processor controls the system and schedules and allocates work to slave processors. Symmetric multiprocessing (SMP): all processors are peers — no master–slave relationship; each has its own registers and cache, but they share physical memory. The benefit of SMP is that N processes can run simultaneously on N CPUs without significant performance deterioration; Windows, macOS and Linux all support it. A recent trend is multiple cores on a single chip; on-chip communication is faster than communication between separate chips.

Clustered systems

Two or more individual systems (nodes) joined together over a network, sharing storage and cooperating to provide high availability — service continues even if one or more systems in the cluster fail. Asymmetric clustering: one machine is in hot-standby mode, doing nothing but monitoring the active server and taking over if it fails, while the others run applications. Symmetric clustering: two or more hosts run applications and monitor each other; more efficient since it uses all available hardware, but requires more than one application to be available to run. Other forms are parallel clusters (multiple hosts access the same data on shared storage) and clustering over a WAN; storage-area networks (SAN) let many systems attach to a pool of storage, even miles apart.

Kernel data structures low priority

The kernel makes heavy use of a small set of standard data structures:

  • List — a sequence of items (singly, doubly or circularly linked), used as the basis for stacks and queues; Linux's version is in <linux/list.h>.
  • Stack — last-in, first-out (LIFO); used for function calls (parameters, local variables and return address are pushed, then popped on return).
  • Queue — first-in, first-out (FIFO); used for tasks waiting for a resource, such as print jobs or processes waiting for the CPU (<linux/kfifo.h>).
  • Tree — a hierarchical structure; Linux uses a red-black tree (<linux/rbtree.h>) for CPU scheduling, and balanced binary search trees search in O(log n).
  • Hash function / hash map — computes a number from a key and uses it as an index, giving O(1) lookup.
  • Bitmap — a string of n binary digits representing the status of n items (e.g. which disk blocks are free).

Traditional, mobile and distributed computing, and how virtualization and cloud computing changed what "a computer" even means.

Traditional computing

The classic model: a standalone PC, or a small number of client machines connected to file/print/mail/web servers over a LAN, with each machine running its own dedicated copy of an operating system directly on its own hardware. Resource sharing is limited to what the network explicitly exposes (shared drives, shared printers), and each user's software runs locally on locally-owned resources.

Today the line between "standalone" and "networked" has largely disappeared, because almost every system is interconnected with others (ultimately through the Internet). Companies run portals that provide web access to their internal systems; network computers (thin clients) are essentially web terminals that understand web-based computing; mobile computers synchronise with PCs and connect over wireless networks; and even home systems now sit behind firewalls to protect them from Internet attacks.

Mobile computing

Handheld devices — smartphones and tablets — running operating systems purpose-built for constrained power, memory and screen real-estate (Android, iOS). Mobile operating systems restrict multitasking far more aggressively than desktop OSes: typically only a single foreground process is fully active and visible to the user at a time, while other processes are pushed to the background with strict limits (a short task, a notification handler, a narrow class of long-running tasks such as audio playback). A background process that needs to keep working uses a service — a component with no user interface and a small memory footprint that can keep running even after its parent app is suspended.

Functionally, a handheld smartphone or tablet differs from a traditional laptop mainly in its extra features — hardware such as GPS and a gyroscope, exposed through additional OS features, which allow whole new classes of application such as augmented reality. Connectivity is through IEEE 802.11 wireless or cellular data networks, and the two market leaders are Apple iOS and Google Android (architectures of both are covered in 1.3).

Distributed systems

A distributed system is a collection of physically separate, possibly heterogeneous computer systems that are networked together to give users access to the various resources the system as a whole maintains — CPU cycles, files, printers, and other services spread across multiple machines rather than sitting on one. Communication between the nodes happens over the network using protocols such as TCP/IP. Distributed systems let an organization share resources and balance load across machines, and can improve reliability, since the failure of one site need not bring down the whole system — remaining sites can continue operating (a property sometimes called fault tolerance or robustness).

Virtualization

Virtualization is a technology that abstracts the hardware of a single physical computer (CPU, memory, disk drives, network interfaces) into several different execution environments, thereby creating the illusion that each separate environment is running its own private computer. A layer of software called a hypervisor (or virtual machine manager, VMM) sits between the physical hardware and the guest operating systems, translating each guest's hardware requests into requests against the real, shared hardware. This lets one physical machine run several different operating systems — or several isolated copies of the same OS — simultaneously, each unaware that it is sharing the underlying hardware.

Virtualization lets operating systems run applications within other operating systems, and it is a vast and still-growing industry. Three related techniques are worth distinguishing:

  • Emulation — used when the source CPU type differs from the target type (for example, running PowerPC code on an Intel x86 machine). Every guest instruction must be translated, so it is generally the slowest method.
  • Interpretation — used when the program is written in a language that is not compiled to native code (for example, Java bytecode run on a virtual machine); the interpreter executes it directly.
  • Virtualization proper — the OS is natively compiled for the CPU, and the guest operating systems it runs are also natively compiled for the same CPU. For example, VMware running several Windows XP guests, each running its own applications, all on a native Windows XP host OS. The VMM (virtual machine manager) provides the virtualization services.

Cloud computing

Cloud computing is a computing environment in which large numbers of systems are connected in a private or public network to provide computing resources dynamically, as scalable, on-demand services delivered over the internet, rather than as hardware the user owns and maintains directly. Cloud computing is built heavily on virtualization: providers run many customers' virtual machines multiplexed over shared physical data-center hardware. It is commonly offered at three levels — Infrastructure as a Service (IaaS) (raw virtual machines/storage/networking), Platform as a Service (PaaS) (a ready-to-use runtime/application-development platform), and Software as a Service (SaaS) (a complete, ready-to-use application, e.g. a web-based email client) — each level handing the customer a progressively higher-level, more managed slice of the stack.

Cloud computing delivers computing, storage, and even whole applications as a service across a network. It is a logical extension of virtualization, because it uses virtualization as the base for its functionality — for instance, Amazon EC2 has thousands of servers, millions of virtual machines, and petabytes of storage available across the Internet, with customers paying based on usage. Cloud deployments come in three kinds, in addition to the three service models already listed above (SaaS, PaaS, IaaS):

  • Public cloud — available via the Internet to anyone willing to pay for it.
  • Private cloud — run by a company for that company's own use.
  • Hybrid cloud — includes both public and private cloud components.

The service models, restated as one-line definitions an exam answer can quote: SaaS (Software as a Service) — one or more applications available via the Internet (e.g. a word processor); PaaS (Platform as a Service) — a software stack ready for application use via the Internet (e.g. a database server); IaaS (Infrastructure as a Service) — servers or storage available over the Internet (e.g. storage for backups).

Client–server computing low priority

Designers shifted away from centralised architectures — terminals connected to a central system — so that many of today's systems act as servers satisfying requests generated by client systems. Servers broadly divide into: a compute-server system, which provides an interface to which a client sends a request to perform an action (for example, read data); the server executes it and sends back the results (a database server answering client queries); and a file-server system, which provides a file-system interface where clients create, update, read and delete files (a web server delivering files to browsers).

Peer-to-peer computing low priority

In the peer-to-peer (P2P) model clients and servers are not distinguished: every node is a peer that may act as a client or a server depending on whether it is requesting or providing a service. A client–server system's server is a bottleneck since all services pass through it; in P2P, services are provided by many nodes spread across the network. A node must first join the network, after which it can provide and request services. Discovering which services exist is done in one of two ways: (1) the node registers its service with a centralised lookup service that other nodes query; or (2) a client broadcasts a request for the service to all other nodes, and whichever nodes provide it respond — this needs a discovery protocol.

Web-based computing low priority

The web has increased the importance of networking: devices that were not networked now have wired or wireless access, and networked devices have faster connectivity. It has produced new device categories such as load balancers, which distribute network connections among a pool of similar servers. Operating systems such as Windows 95, which acted as web clients, have evolved into Linux and Windows XP, which can act as web servers as well as clients.

Special-purpose systems low priority

  • Multimedia systems — audio and video (MP3, DVD movies, video conferencing, live webcasts) as well as conventional files. Unlike conventional data, multimedia data such as video frames must be delivered (streamed) according to time restrictions, for example 30 frames per second.
  • Handheld systems — PDAs, smartphones. Developers face limited memory, slow processors and small screens: the OS and applications must manage memory efficiently (returning unused memory to the memory manager), and since faster processors need more power, battery life is a concern. Their limited functionality is balanced by convenience and portability.
  • Real-time embedded systems — embedded computers in devices and automobiles with little or no user interface (maybe LEDs showing status), running a specific task with well-defined, fixed time constraints; processing must be done within them or the system fails.

Open-source operating systems low priority

Operating systems made available in source-code format rather than only as closed-source binaries. This runs counter to the copy-protection and Digital Rights Management (DRM) movement. It was started by the Free Software Foundation (FSF), which uses the copyleft GNU Public License (GPL). Examples include GNU/Linux and BSD UNIX (including the core of macOS). A virtual machine manager such as VMware Player or VirtualBox lets a student run guest operating systems to explore them safely.

The Java Virtual Machine low priority

Java was designed to be platform independent by running only on a Java Virtual Machine (JVM), for which implementations exist on many hardware platforms. Java source code is compiled into bytecode in .class files — binary instructions that run on the JVM. The JVM implements memory management and garbage collection, and consists of a class loader (loads the compiled .class files of the program and the Java API, and checks them for validity) and a Java interpreter that executes the bytecode. It is an example of the "interpretation" technique described under virtualization.

Multiprogramming and time-sharing — the two ideas that let one CPU serve many jobs (and many users) at once.

Multiprogramming

A single program cannot, in general, keep either the CPU or the I/O devices busy at all times — while a program waits on I/O, a non-multiprogrammed CPU simply sits idle. Multiprogramming fixes this by organizing several jobs (code and data) so that the CPU always has something to execute. Because main memory is usually too small to hold every job in the system, jobs are initially kept in a job pool on disk; the subset that fits is loaded into memory, and the OS picks and begins executing one of them. When that job has to wait for some task (typically I/O), the OS simply switches to and executes another job, and so on — as long as at least one job needs to execute, the CPU is never idle. Multiprogrammed systems thus provide an environment in which system resources (CPU, memory, peripherals) are used efficiently, but they do not, by themselves, provide for direct user interaction.

Time-sharing (multitasking)

Time sharing, or multitasking, is a logical extension of multiprogramming in which the CPU switches jobs so frequently that users can interact with each program while it is running, creating interactive computing. Time sharing requires an interactive system that provides direct communication between the user and the system: the user issues a command via an input device and waits for a result, so the system's response time should typically be under one second. A program loaded into memory and executing is called a process. If several jobs are ready to run at the same time, the system needs CPU scheduling to decide which runs next; if processes don't all fit in memory, swapping moves them in and out of memory to keep things running; and virtual memory allows a process to execute even when it is not held completely in memory, by giving each process the illusion of a large, private address space.

Interrupt-driven operation

Modern operating systems are interrupt driven. If there are no processes to execute, no I/O devices to service, and no users to respond to, the OS sits quietly waiting for something to happen. Events are almost always signalled by the occurrence of an interrupt or a trap. A trap (or exception) is a software-generated interrupt caused either by an error (division by zero, an invalid memory access) or by a specific request from a user program that an operating-system service be performed — i.e. a system call. Other process problems that can trigger OS intervention include an infinite loop, or processes modifying each other or the operating system itself. Because the OS and user processes share the hardware and software resources of the system, the OS must ensure that an error in one user program can only affect that one program.

Dual-mode and multimode operation

To protect itself and other system components, the hardware provides (at least) two separate modes of operation: user mode and kernel mode (also called supervisor mode, system mode, or privileged mode). A mode bit, added to the hardware, records the current mode: kernel (0) or user (1). When the system executes on behalf of a user application it is in user mode; when a user application requests a service via a system call, the system must transition to kernel mode to fulfil the request.

Fig 5. A system call traps the CPU from user mode into kernel mode, and returns it to user mode on completion.

At system boot time the hardware starts in kernel mode; the OS is then loaded and starts user applications in user mode. Whenever a trap or interrupt occurs, the hardware switches from user mode to kernel mode (mode bit → 0) — so whenever the OS has control of the computer, it is in kernel mode. The system always switches back to user mode (mode bit → 1) before handing control to a user program.

The dual-mode mechanism lets the hardware designate certain machine instructions as privileged — executable only in kernel mode. If a user-mode program attempts to execute a privileged instruction, the hardware does not execute it, and instead traps it to the operating system as illegal. The instruction to switch to kernel mode is itself a privileged instruction; others include I/O control, timer management, and interrupt management. Increasingly, CPUs also support multimode operation, with additional, more fine-grained privilege levels (e.g. a separate mode for a virtual machine manager, which has more privileges than user processes but fewer than the kernel).

Timer

The OS must ensure it maintains control over the CPU — a user program must never be allowed to get stuck in an infinite loop, or to fail to call system services and never return control to the OS. A timer is used to enforce this: it can be set to interrupt the computer after a specified period, which may be fixed (e.g. 1/60 second) or variable. A variable timer is typically implemented with a fixed-rate clock and a counter: the OS sets the counter, the clock decrements it on every tick, and when the counter reaches 0 an interrupt occurs. Since setting the counter is a privileged instruction, only the OS can arm the timer — before turning control over to a user program the OS ensures the timer is set to interrupt, so it can regain control (or terminate a program that has exceeded its allotted time) when the timer fires.

Protection and security: user and group identifiers

Protection is any mechanism for controlling the access of processes or users to the resources defined by the OS; security is the defence of the system against internal and external attacks — a huge range that includes denial-of-service attacks, worms, viruses, identity theft and theft of service. To decide who can do what, systems first distinguish among users:

  • User identity (user ID, or security ID) — a name plus an associated number, one per user. The user ID is then associated with all of that user's files and processes, and is what the OS consults for access control.
  • Group identifier (group ID) — lets a set of users be defined so that controls can be managed for the whole set; it is likewise associated with each process and file.
  • Privilege escalation — lets a user change to an effective ID with more rights (for example, running one command with administrator privileges). This is what the setuid()/setgid() system calls of 1.2 support.

Management functions of the OS low priority

  • Process management — a process is a program in execution (a program on disk is a passive entity; a process is an active one). The OS schedules processes and threads, creates and deletes user and system processes, suspends and resumes them, and provides mechanisms for synchronisation and communication.
  • Memory management — keep track of which parts of memory are currently used and by whom, decide which processes and data to move into and out of memory, and allocate and deallocate memory space as needed.
  • File-system management — create and delete files and directories, supply primitives to manipulate them, map files onto secondary storage, and back them up on stable (non-volatile) media.
  • Mass-storage management — free-space management, storage allocation and disk scheduling.
  • Caching — information in use is copied into a faster storage level (the cache); a lookup checks the cache first. Because caches are small, cache size and replacement policy matter greatly. Movement between levels may be explicit (OS-controlled, e.g. disk to memory) or implicit (hardware-controlled, e.g. cache to CPU).
  • I/O subsystem — hides the peculiarities of hardware devices from the user: a memory-management component (buffering, caching, spooling), a general device-driver interface, and drivers for specific devices; only the driver knows the specifics of its device.

Operating System Services

An operating system provides an environment for the execution of programs, offering services both to those programs and to their users.

An operating system manages hardware resources and provides services for programs and users. Its kernel controls privileged operations; applications request those operations through system calls. The services below are the required Unit I starting point.

Services helpful to the user

  • User interface (UI) — almost every OS provides one, whether a command-line interface (CLI), a batch interface, or (most commonly) a graphical user interface (GUI).
  • Program execution — the system must be able to load a program into memory, run it, and let it end execution, either normally or abnormally (indicating an error).
  • I/O operations — a running program may need I/O involving a file or a device; for efficiency and protection, users normally cannot control I/O devices directly, so the OS provides the mechanism.
  • File-system manipulation — programs need to read, write, create and delete files and directories, search for a file, list file information, and (on many systems) manage permissions on who may access what.
  • Communications — processes often need to exchange information, either between processes on the same computer or between processes on different computers linked by a network. Communication can be implemented via shared memory, where two or more processes read and write a shared region of memory, or via message passing, where packets of information are moved between processes by the operating system.
  • Error detection — the OS must constantly watch for possible errors, in the CPU/memory hardware (a memory error, a power failure), in I/O devices (a parity error, a connection failure, a printer out of paper), or in the user program (arithmetic overflow, illegal memory access, excessive CPU use), and take the appropriate action — sometimes halting the system, sometimes terminating the offending process, sometimes just returning an error code.

Services that keep the system itself running efficiently

A second set of services exists not to help an individual user directly, but to keep the system as a whole efficient when multiple users or jobs share it:

  • Resource allocation — when multiple users or jobs run concurrently, resources (CPU cycles, main memory, file storage, I/O devices) must be allocated among them; some resources have specialized allocation code, others (like I/O devices) use more general request/release code.
  • Accounting — tracking and recording which users use how much, and what kinds, of computer resources — useful for usage statistics or billing.
  • Protection and security — the owners of information on a multiuser or networked system want to control who can use it. Protection means ensuring all access to system resources is controlled; security starts with requiring users to authenticate themselves (typically by password) and extends to defending external I/O devices from invalid access attempts.

System Calls

The only doorway through which a user program can ask the kernel to do something on its behalf.

What is a system call?

A system call is the mechanism that provides the interface between a running process and the operating system — a programmatic method by which a program requests a service from the kernel. System calls are the only entry points into the kernel: they let a user-level application request services or resources it cannot access on its own, enabling programs to interact with hardware or perform privileged tasks while the OS retains control over security and stability. System calls are generally made available to the programmer through an Application Programming Interface (API) rather than being invoked directly — a program is typically written to the API (for example, POSIX for UNIX/Linux/macOS, or the Windows API), and the run-time support library shipped with the language translates the API call into the actual system call(s) needed, hiding the low-level details from the programmer.

How a system call works

The mechanism is the same trap-based transition shown in §1.5, Fig 5: Step 1 — the process executes in user mode until a system call interrupts it. Step 2 — control passes through an interrupt vector to a service routine inside the kernel; the mode bit is set to kernel mode and the system call executes on a priority basis. Typically a number is associated with each system call, and a system-call interface maintains a table indexed by these numbers to locate the right kernel routine. Step 3 — once the system call finishes executing, control returns to the instruction following the call, and the mode bit is reset to user mode. The kernel examines the interrupting instruction to determine which system call was requested; any additional parameters may be passed in registers, in a memory block/table (the approach used by Linux and Solaris, since there may be more parameters than registers), or pushed onto/popped off a stack by the operating system. The kernel verifies that the parameters are correct and legal before executing the request.

Two models of communication

Under the message-passing model, communicating processes exchange messages with one another, either directly or indirectly through a common mailbox — a connection must be opened, the other communicator identified (via get hostid()/get processid()), and the recipient must usually grant permission via accept connection(); the source of the communication is the client, the receiving daemon the server. Operating System Structure & Mobile OS Architecture

The standard ways of structuring an operating system, followed by iOS and Android as real-world layered/hybrid examples.

Approaches to designing OS structure

Source coverage clarified

The earlier core slide deck did not teach these design approaches in depth. The available CIE-1 Unit 1 handout covers structures on PDF pages 36–38, and Silberschatz §2.7 supplies the detailed theory. This is now required Unit I material.

  • Simple/monolithic structure — the whole OS runs as one program in kernel mode, with no enforced internal boundaries between components (e.g. original MS-DOS, early UNIX). Fast, since there's no overhead crossing internal boundaries, but hard to maintain or extend safely, since a bug anywhere can corrupt the whole kernel.
  • Layered approach — the OS is broken into a stack of layers, each built only on the services of the layer strictly below it (bottom layer = hardware, top layer = user interface). Easier to design, debug and verify one layer at a time, but layer boundaries add overhead and rigid layering can make some features awkward to implement.
  • Microkernel structure — the kernel is stripped down to a minimal core (basic process/memory/communication primitives); everything else that used to live in the kernel (file systems, device drivers) runs as ordinary user-space processes. Communication between these user-space services, and between them and the minimal kernel, happens via message passing — this is exactly what "microkernels use for communication" means. Benefits: easier to extend, more reliable (a failing service doesn't crash the kernel), easier to port; cost: extra message-passing overhead versus a monolithic design.
  • Modules — the kernel has a core set of components plus dynamically loadable modules (e.g. Linux Loadable Kernel Modules) that can be linked in at boot or at run time, combining the performance of a monolithic design with much of the cleanliness of a layered one.
  • Hybrid systems — most real systems (Linux, Windows, macOS) combine elements of several approaches — e.g. mostly monolithic for performance, but with a modular, loadable-driver architecture on top.

OS design and implementation

Present in older notes; not listed in the new syllabus

Design goals. The first problem in designing a system is to define goals and specifications, affected by the choice of hardware and type of system (batch, time-shared, single-user, multiuser, distributed, real-time, general-purpose). Requirements split into two groups: user goals — the system should be convenient and easy to use and learn, reliable, safe and fast; and system goals — easy to design, implement and maintain, and flexible, reliable, error-free and efficient.

Mechanisms and policies. Policies determine what will be done; mechanisms determine how it is done. Example: the timer construct (a counter that is decremented) is the mechanism for CPU protection, while deciding how long the timer is set for a particular user is a policy. Policies change over time, so separating the two is important: if mechanism and policy are properly separated, a policy change needs only a change of parameters or a configuration file, not rewriting the mechanism code.

Implementation. Operating systems were traditionally written in assembly language. Today they are written in higher-level languages — C or C++ — with only critical routines left in assembly. The first OS not written in assembly was the Master Control Program (MCP). Advantages of a higher-level language: code is written faster, is more compact, easier to understand and debug, and easier to port to other hardware; the disadvantages are somewhat reduced speed and increased storage requirements.

Operating-system generation (SYSGEN) and system boot

An OS is designed to run on any of a class of machines, so it must be configured for each specific site. A SYSGEN program obtains information about the specific hardware configuration (which CPU, how much memory, which devices, which options) and produces a tailored system: either by compiling a customised kernel, by selecting precompiled modules from a library and linking them, or by table-driven selection at run time.

Booting is starting a computer by loading the kernel. On power-up, execution starts at a fixed memory location holding the bootstrap program in ROM/firmware, which locates the kernel, loads it into memory and starts it. Process Concept

What a process actually is, what it's made of in memory, the states it moves through, and how the kernel keeps track of it.

Process vs. program

Early computers allowed only one program to execute at a time, with complete access to all the system's resources. Contemporary systems allow many programs to be loaded into memory and executed concurrently — which required firmer control and more compartmentalization, giving rise to the notion of a process: a program in execution. A program is a passive entity, such as an executable file sitting on disk; a process is an active entity, with a program counter specifying the next instruction to execute and a set of associated resources. A program becomes a process once its executable file is loaded into memory — and the same program can produce several separate processes at once (several users running the same web browser, for example), each with equivalent text but its own data, heap and stack.

A process is more than just its program code (the text section). It also includes the current activity, represented by the program counter and the contents of the processor's registers; a data section containing global and static variables; a heap containing memory dynamically allocated at run time; and a stack containing temporary data such as function parameters, return addresses, and local variables.

Fig 8. A process's address space: The conventional process layout has text, data, heap and stack; growth directions shown are a common example, not a universal rule.

Process state

As a process executes, it changes state. A process may be in one of five states:

  • New — the process is being created.
  • Ready — the process is waiting to be assigned to a processor.
  • Running — instructions are being executed.
  • Waiting — the process is waiting for some event to occur, such as an I/O completion or the reception of a signal.
  • Terminated — the process has finished execution.
Fig 9. A ready process is dispatched to running; blocking sends it to waiting, an event returns it to ready, and completion terminates it.

Process Control Block (PCB)

Each process is represented in the operating system by a Process Control Block (PCB), also called a task control block. The PCB is the single data structure that lets the OS track everything it needs to know to suspend and later correctly resume a process. It contains:

  • Process state — new, ready, running, waiting, terminated, etc.
  • Program counter — the address of the next instruction to execute for this process.
  • CPU registers — accumulators, index registers, stack pointers, general-purpose registers, condition codes; saved here on every interrupt so execution can resume correctly.
  • CPU-scheduling information — process priority, pointers to scheduling queues, and other scheduling parameters.
  • Memory-management information — base/limit register values, page tables or segment tables, depending on the memory system in use.
  • Accounting information — CPU time and real time used, time limits, account/process numbers.
  • I/O status information — the list of I/O devices allocated to the process, and its list of open files.
Fig 10. The Process Control Block — one per process, the OS's complete record of that process's context.

Context switch

When the CPU switches from one process to another, the system must save the state of the old process (into its PCB) and load the saved state of the new process — this is a context switch. Context-switch time is pure overhead, since the system does no useful work while switching; its duration depends on memory speed, the number of registers that must be copied, and the availability of special hardware instructions for the purpose.

A brief word on threads

When a process runs a single-threaded program, one thread of instructions executes at a time, letting the process do only one thing at once. Most modern operating systems extend the process concept so a process can have multiple threads of execution, letting it perform more than one task at a time — especially valuable on multicore systems, where separate threads can run in true parallel on separate cores. The key contrast to state in an exam answer: a process is an independent unit with its own private address space (text/data/heap/stack) and its own PCB, and inter-process communication requires explicit OS mechanisms (shared memory or message passing, §1.2); a thread is a single path of execution within a process — threads of the same process share that process's code, data and open files by default, each needing only its own program counter, register set and stack. (The full treatment — benefits, multithreading models, multicore programming and Pthreads — is in 1.8 Threads.)

Process representation in Linux

Present in older notes; not listed in the new syllabus

In the Linux kernel, the PCB is represented by the C structure task_struct, defined in the kernel source tree. It holds all the information needed to represent a process — its state, scheduling and memory-management information, its list of open files, and pointers to its parent. The kernel keeps a pointer, current, to the process presently executing on the system; when that process's state must change, the kernel simply does current->state = new_state;.

The standard UNIX/Linux command to inspect this information from outside the kernel is ps ("process status") — it lists running processes with fields drawn straight from their PCBs (pid, state, CPU time, and more).

Process Scheduling

How the OS keeps multiple processes moving through the system, and which of them gets the CPU next — conceptually, not the specific algorithms (those are Unit 2).

Scheduling queues

As processes enter the system they are placed in the job queue, holding all processes in the system (this queue resides in secondary storage, since main memory can't hold everything). Processes residing in main memory and ready to execute sit in the ready queue, generally implemented as a linked list with a header pointing to the first and last PCBs. When a process is allocated the CPU, it executes for a while and eventually quits, is interrupted, or requests I/O and must wait; if it requests I/O from a shared device that is busy, it joins that device's own device queue — every device has one.

Fig 11. A process migrates between the ready queue, the CPU, and device queues throughout its lifetime.

Schedulers

The OS must select processes from these queues in some fashion — carried out by the appropriate scheduler.

  • Long-term scheduler (job scheduler) — selects which processes should be brought into the ready queue from the job pool on disk. It runs infrequently (seconds to minutes), so it can afford to be slow, and it controls the degree of multiprogramming (the number of processes in memory) by balancing a good process mix of I/O-bound and CPU-bound jobs.
  • Short-term scheduler (CPU scheduler) — selects which of the ready processes should be executed next and allocates the CPU to it. It must run very frequently (every few milliseconds), so it must be fast; it is sometimes the only scheduler present in a system.
  • Medium-term scheduler — can be added if the degree of multiprogramming needs to be reduced. It removes a process from memory (and hence from active contention for the CPU), places it on disk, and can later reintroduce it — this is exactly swapping. It helps balance CPU load, manage memory efficiently, and keep high-priority processes getting CPU time.

I/O-bound vs. CPU-bound processes

The long-term scheduler strives for a good process mix of two broad process types: an I/O-bound process spends more of its time doing I/O than computation (many short CPU bursts); a CPU-bound process spends more of its time doing computation (few, long CPU bursts). A system with too many CPU-bound processes leaves I/O devices idle; too many I/O-bound processes leave the CPU idle — the long-term scheduler's job is to balance the mix. A web server is a textbook I/O-bound example: most of its time is spent waiting on network and disk I/O to serve requests, with comparatively short bursts of CPU computation in between.

Operations on Processes

How processes come into being, how they hand off to new programs, and how they end — including the mechanics behind almost every fork() exam question.

Process creation

During execution, a process may create several new processes. The creating process is the parent; the newly created processes are its children — each of which may in turn create further processes, forming a tree of processes. Most operating systems (UNIX, Linux, Windows) identify each process by a unique process identifier (pid), typically an integer, used as an index to access the process's attributes within the kernel.

When a process creates a child, the child generally needs resources (CPU time, memory, files, I/O devices) to do its work. The parent may either let the child obtain resources directly from the OS, or restrict the child to a subset of the parent's own resources — the latter prevents any one process from overloading the system by creating too many children. There are two independent choices to make when a process creates a new one:

Resource sharing options
  1. Parent and child share all resources.
  2. Child shares a subset of the parent's resources.
  3. Parent and child share no resources.
Execution options
  1. Parent and child execute concurrently.
  2. Parent waits until some or all children have terminated.

There are also two address-space possibilities for the new process: (1) the child is a duplicate of the parent (same program and data), or (2) the child has a new program loaded into it.

Fig 13. Every process except init (pid 1) has a parent — the tree bottoms out wherever a process has spawned no children.

fork() and exec()

In UNIX/Linux, a new process is created with the fork() system call. The new process (the child) is an exact duplicate of the address space of the original (the parent) — both processes continue execution at the instruction right after the fork() call, with one difference: fork()'s return value is 0 in the child, and the child's (nonzero) process ID in the parent. This single difference is what lets the same piece of code branch into parent-only and child-only behaviour. After forking, one of the two processes typically calls exec() to replace its own memory image — code, data, and stack — with a brand-new program; the process ID does not change across an exec() call. The parent can then create more children, or call wait() to move itself off the ready queue until its child terminates.

// classic fork/exec/wait pattern pid_t pid = fork(); if (pid < 0) { // fork failed fprintf(stderr, "Fork Failed"); } else if (pid == 0) { // this is the CHILD (pid==0) execlp("/bin/ls", "ls", NULL); // child replaces itself with /bin/ls } else { // this is the PARENT (pid = child's pid) wait(NULL); // parent blocks until child exits printf("Child Complete"); }
Fig 14. The parent branch blocks on wait() until the child's branch reaches exit(), then resumes.

Process termination

A process terminates when it finishes executing its final statement and asks the OS to delete it via the exit() system call, optionally returning a status value to its parent (retrievable through wait()). All the process's resources — physical and virtual memory, open files, I/O buffers — are then deallocated by the OS. A parent may also terminate a child explicitly (e.g. via abort()/TerminateProcess()), typically because the child exceeded its allocated resources, its task is no longer needed, or because the parent itself is exiting and the OS does not allow a child to outlive it.

Some systems enforce this last case as cascading termination: if a process terminates, all its children (and their children, and so on) are also terminated, a phenomenon normally initiated by the OS itself. When a process terminates, its PCB and process-table entry must remain until its parent calls wait(), because the process table holds the process's exit status — a process that has terminated but whose parent has not yet called wait() is a zombie process (all processes pass briefly through this state). If instead a parent terminates without ever calling wait(), its still-running children become orphans — on UNIX/Linux systems, the init process periodically calls wait() on behalf of orphans, cleaning up their exit status and releasing their process-table entries.

Inter-Process Communication

How cooperating processes exchange data — shared memory and message passing, the producer–consumer problem, and the design choices behind message passing.

Where this comes from The syllabus lists "Inter-process Communication" under Process Concept. It is treated here from the CIE-1 handout (CIE-1 Unit 1.pdf) and standard textbook material, since the two original decks only mention it in passing (see 1.1, Communications).

Independent and cooperating processes

A process is independent if it cannot affect, and cannot be affected by, any other process executing in the system — it shares no data with any other process. A process is cooperating if it can affect or be affected by other processes; any process that shares data with others is a cooperating process. Systems provide an environment for cooperating processes for four reasons:

  • Information sharing — several users may need the same piece of information (for example, a shared file).
  • Computation speed-up — a task can be broken into subtasks that run in parallel (only useful if there are multiple processing cores).
  • Modularity — the system can be divided into cooperating modules, run as separate processes or threads.
  • Convenience — even a single user may work on many tasks at once (editing, listening to music, compiling).

Cooperating processes need some form of inter-process communication (IPC) to exchange data and information. There are two fundamental models: shared memory and message passing.

Fig 15. The two IPC models: (a) shared memory, (b) message passing.

Shared-memory systems

In the shared-memory model, a region of memory is established in the address space of one process, and other processes that want to communicate attach this segment to their own address space. Normally the OS prevents one process from touching another's memory, so the processes must agree to remove that restriction for the shared region. They then exchange information by reading and writing data in it. The form of the data and its location are determined by the processes, not the OS, and the processes are also responsible for ensuring that they do not write to the same location simultaneously.

System calls are needed only to create the shared region; after that, all accesses are ordinary memory accesses with no kernel involvement, which is why shared memory is faster than message passing and is generally the better choice for large amounts of data.

The producer–consumer problem

The classic illustration of cooperating processes. A producer process produces information that is consumed by a consumer process (a compiler produces assembly code that an assembler consumes; a web server produces HTML that a browser consumes). To let them run concurrently, we need a buffer of items in memory shared by both. The producer fills it, the consumer empties it, and they must be synchronised so the consumer never tries to consume an item that has not been produced yet. Two kinds of buffer exist:

  • Unbounded buffer — no practical limit on size. The consumer may have to wait for new items, but the producer can always produce.
  • Bounded buffer — a fixed size. The consumer waits if the buffer is empty, and the producer waits if it is full.

A bounded buffer can be implemented as a circular array with two pointers: in (next free slot) and out (first full slot).

/* shared data */ #define BUFFER_SIZE 10 item buffer[BUFFER_SIZE]; int in = 0, out = 0; /* producer */ while (true) { /* produce an item in next_produced */ while (((in + 1) % BUFFER_SIZE) == out) ; /* buffer full: do nothing */ buffer[in] = next_produced; in = (in + 1) % BUFFER_SIZE; } /* consumer */ while (true) { while (in == out) ; /* buffer empty: do nothing */ next_consumed = buffer[out]; out = (out + 1) % BUFFER_SIZE; /* consume the item in next_consumed */ }
Must-quote conditions Buffer is empty when in == out; buffer is full when ((in + 1) % BUFFER_SIZE) == out. Because one slot is always left unused to tell "full" from "empty", this scheme holds at most BUFFER_SIZE − 1 items at once.

Message-passing systems

Message passing lets processes communicate and synchronise their actions without sharing an address space, which makes it especially useful in a distributed environment where the processes live on different computers connected by a network (a chat program is a typical example). It provides at least two operations:

send(message) /* message size fixed or variable */ receive(message)

If processes P and Q want to communicate, they must establish a communication link between them and then exchange messages using send and receive. The link may be physically a shared memory, a hardware bus, or a network; what matters here is its logical implementation. Message passing is simpler and easier to implement than shared memory and is good for small amounts of data, but it is slower, because every message needs a system call and kernel intervention. Three design issues decide how the link behaves.

1. Naming — direct vs. indirect communication

Direct communication. Each process that wants to communicate must explicitly name the recipient or sender:

send(P, message) /* send a message to process P */ receive(Q, message) /* receive a message from process Q */

Properties of the link: it is established automatically between every pair of processes that want to communicate (they need only know each other's identity); a link is associated with exactly two processes; and between each pair there exists exactly one link. This is symmetric addressing. In an asymmetric variant only the sender names the recipient: send(P, message) and receive(id, message), where id is set to the name of whichever process sent the message. The drawback of both is limited modularity: changing a process's identifier means finding every reference to the old one.

Indirect communication. Messages are sent to and received from mailboxes (also called ports), which are objects into which messages can be placed and from which they can be removed. Each mailbox has a unique identifier:

send(A, message) /* send a message to mailbox A */ receive(A, message) /* receive a message from mailbox A */

Properties of the link: it is established only if the two processes share a mailbox; a link may be associated with more than two processes; and between a pair of processes there may be several different links, each corresponding to one mailbox. A mailbox may be owned by a process (it is part of that process's address space; the owner can only receive and other users can only send, and the mailbox disappears when the owner terminates) or owned by the operating system, which is independent of any process. In the latter case the OS must provide calls to create a new mailbox, send and receive through it, and delete it, and the creating process may be given ownership and receive privilege initially, which it can pass to others.

If more than one process tries to receive from the same mailbox, who gets the message depends on the scheme: allow at most one process to receive from a mailbox, allow only one process at a time to execute receive, or let the system choose arbitrarily (the sender may be told which).

2. Synchronization — blocking vs. non-blocking

Message passing may be blocking (synchronous) or non-blocking (asynchronous):

  • Blocking send — the sender is blocked until the message is received by the receiving process or mailbox.
  • Non-blocking send — the sender sends the message and continues immediately.
  • Blocking receive — the receiver blocks until a message is available.
  • Non-blocking receive — the receiver retrieves either a valid message or a null, and continues.

When both send and receive are blocking, the sender and receiver have a rendezvous, which makes the producer–consumer problem trivial to solve: the producer simply invokes a blocking send() and waits until the message is delivered, and the consumer invokes a blocking receive() and waits until a message is available.

3. Buffering

Whether the communication is direct or indirect, messages exchanged reside in a temporary queue, which can be implemented in three ways:

  • Zero capacity — the queue has maximum length 0, so the link cannot hold any message. The sender must block until the recipient receives the message (no buffering at all).
  • Bounded capacity — the queue has finite length n; at most n messages can reside in it. If the queue is not full, a new message is placed in it and the sender continues without waiting; if the link is full, the sender must block until space is available.
  • Unbounded capacity — the queue's length is potentially infinite, so any number of messages can wait in it, and the sender never blocks.

Threads

Overview, benefits, multithreading models, multicore programming, and the Pthreads library.

Not in your materials — added for syllabus completeness The syllabus lists "Threads: Overview, Multithreading models, Multi-core Programming, Pthreads" under Unit I, but the uploaded decks contain only a one-paragraph mention (1.4). This revision uses Silberschatz Chapter 4 and the matching thread material already present in the older Unit II guide.

Overview

A thread is a basic unit of CPU utilisation. It comprises a thread ID, a program counter, a register set and a stack. It shares with the other threads of the same process its code (text) section, data section, heap and other OS resources such as open files and signals. A traditional (heavyweight) process has a single thread of control; a process with multiple threads can perform more than one task at a time, each thread having its own program counter, registers and stack but sharing everything else.

Many applications are multithreaded: a web browser may have one thread displaying images or text while another retrieves data from the network; a word processor may have a thread for display, one for keystrokes and one for spell-checking in the background; a web server runs one thread per client request instead of creating a heavyweight process for each.

Benefits of multithreading

  • Responsiveness — a program can continue running even if part of it is blocked or performing a lengthy operation, which is especially useful for user interfaces.
  • Resource sharing — threads share the memory and resources of their process by default, so unlike processes they need no special shared-memory or message-passing arrangement; several threads of activity live in one address space.
  • Economy — creating a process is costly because memory and resources must be allocated; threads share their process's resources, so creating and context-switching a thread is far cheaper.
  • Scalability — in a multiprocessor architecture the threads of one process can run in parallel on different cores, whereas a single-threaded process can only run on one.

A Thread Control Block (TCB) is the record used to manage an individual thread: its identity, saved CPU context, scheduling state and stack information. Resources shared by the process remain process-level state; exact record layouts depend on the implementation.

User threads and kernel threads

User threads are supported above the kernel and managed without kernel support, by a thread library in user space: creation and scheduling are fast, but the kernel sees only a single process, so in a many-to-one mapping a blocking system call can block all its user threads. This limitation depends on the mapping, not merely on using a user-space API. Kernel threads are supported and managed directly by the operating system (virtually all modern systems — Windows, Linux, macOS, Solaris — support them): the kernel can schedule threads on different CPUs and a blocking thread does not block the rest, but creation and management are slower. A relationship must therefore exist between user threads and kernel threads; the models below describe it.

Fig 15b. A single-threaded process has one program counter/register-set/stack; a multithreaded process has several, each independently schedulable, all sharing the same code, data, and open files.

Multithreading models

Fig 16. The three multithreading models relating user threads (top) to kernel threads (bottom).

Many-to-one

Many user-level threads are mapped to a single kernel thread. Thread management is done in user space by the thread library, so it is efficient. Drawbacks: if one thread makes a blocking system call, the entire process blocks; and because only one thread can access the kernel at a time, multiple threads cannot run in parallel on a multicore system. Few systems use it today (examples: Solaris Green Threads, GNU Portable Threads).

One-to-one

Each user thread is mapped to its own kernel thread. It provides more concurrency than many-to-one, since another thread can run when one makes a blocking call, and it allows threads to run in parallel on multiprocessors. Drawback: creating a user thread requires creating the corresponding kernel thread, which burdens the system, so most implementations restrict the number of threads. Used by Linux and the Windows family.

Many-to-many

Many user-level threads are multiplexed onto a smaller or equal number of kernel threads. The number of kernel threads may be specific to a particular application or machine. Developers can create as many user threads as needed, and the corresponding kernel threads run in parallel on a multiprocessor; when one thread blocks, the kernel can schedule another thread. It avoids the weaknesses of the other two models but is harder to implement. A popular variant is the two-level model, which is many-to-many but also allows a user thread to be bound to a particular kernel thread (used in IRIX, HP-UX and Tru64 UNIX).

Multicore programming

Modern systems put multiple computing cores on a single chip; to the operating system each core appears as a separate processor. Multithreaded programming provides a mechanism for using these cores efficiently. Two terms must be distinguished:

  • Concurrency — more than one task is making progress. On a single core this is achieved by interleaving the threads' execution over time (the scheduler switches rapidly).
  • Parallelism — more than one task is executing simultaneously, which needs multiple cores. A system can therefore be parallel only if it can perform more than one task at the same instant; concurrency is possible without parallelism, but not the other way round.
Fig 16b. Concurrency (time-sliced interleaving on one core) versus parallelism (simultaneous execution across cores).

Programming challenges

  • Identifying tasks — find areas of the application that can be divided into separate, concurrent tasks, ideally independent of one another so they can run in parallel.
  • Balance — each task should perform about equal work of equal value; if a separate core is used for a task that contributes little, the cost may outweigh the benefit.
  • Data splitting — the data accessed and manipulated by the tasks must be divided to run on separate cores.
  • Data dependency — when one task depends on data from another, the programmer must make sure the execution is synchronised to accommodate the dependency.
  • Testing and debugging — with many execution paths, testing and debugging is inherently more difficult than for a single-threaded application.

Types of parallelism

  • Data parallelism — distributes subsets of the same data across multiple cores and performs the same operation on each (e.g. summing an array of N elements by giving one half to each of two cores).
  • Task parallelism — distributes threads across cores, each performing a different operation, on the same or different data (e.g. two threads computing different statistics over the same array).

In practice an application usually uses a hybrid of the two.

Fig 16c. Data parallelism distributes the same operation over disjoint data; task parallelism distributes distinct operations across cores.

Amdahl's law

Supplementary multicore calculation from older notes; not explicitly named in the new syllabus

Amdahl's law gives the potential speed-up from adding computing cores to an application that has both serial and parallel components. If S is the portion of the application that must be performed serially and N is the number of processing cores:

speedup ≤ 1 / ( S + (1 − S) / N ) As N → ∞, speedup → 1 / S: the serial portion bounds the gain.
Worked example · Amdahl's lawtypical 3–4 marks
An application is 75% parallel and 25% serial. What is the speed-up on 2 cores and on 4 cores, and what is the best possible speed-up?
Solution

Here S = 0.25, so the parallel portion is 1 − S = 0.75.

N = 2: speedup = 1 / (0.25 + 0.75/2) = 1 / 0.625 = 1.6 N = 4: speedup = 1 / (0.25 + 0.75/4) = 1 / 0.4375 = 2.29 N → ∞: speedup = 1 / 0.25 = 4

Doubling the cores from 2 to 4 gains only 0.69 of extra speed-up, and no number of cores can push it past 4×, because the 25% serial portion always has to run on a single core.

2024-25 CIE-I Test-1, Q34 marks
A task has 70% of its code that can be parallelized, and the remaining 30% cannot be parallelized. If you run this task on 5 processors, what is the theoretical maximum speedup according to Amdahl's Law?
Solution
  1. Identify P = 0.7 (parallelizable fraction), 1−P = 0.3 (serial fraction), n = 5 processors.
  2. Substitute into Amdahl's Law: Speedup = 1 / [0.3 + 0.7/5] = 1 / [0.3 + 0.14] = 1 / 0.44.
  3. Speedup = 25/11 ≈ 2.27× (verified with exact rational arithmetic, not rounded floats).

Even with 5 processors thrown at it, the untouchable 30% serial portion limits the maximum possible speedup to under 2.3× — nowhere near 5×.

Pthreads

Fig 16d. Pthread lifecycle: pthread_create() spawns the runner thread, which executes concurrently with main; pthread_join() makes main wait until the runner calls pthread_exit().

Pthreads refers to the POSIX standard (IEEE 1003.1c) defining an API for thread creation and synchronisation. It is a specification for thread behaviour, not an implementation: operating-system designers may implement it any way they like, and it is common on UNIX-type systems (Linux, macOS, Solaris). The API can be implemented using different user/kernel thread mappings; calling Pthreads does not itself imply many-to-one blocking. Windows has its own thread API, and Java threads are managed by the JVM using the host's native thread model. The key functions are:

FunctionPurpose
pthread_create(&tid, &attr, fn, arg)Create a new thread that starts executing fn(arg); tid receives its identifier; attr holds its attributes (stack size, scheduling).
pthread_attr_init(&attr)Initialise a thread-attribute structure to its defaults.
pthread_join(tid, NULL)Wait for the named thread to terminate (the parent's equivalent of wait()).
pthread_exit(0)Terminate the calling thread.
Worked example · Pthreads programtypical 6 marks
Write a multithreaded C program using Pthreads in which a separate thread computes the sum 1 + 2 + … + N, and the main thread prints it.
Solution
#include <pthread.h> #include <stdio.h> #include <stdlib.h> int sum; /* shared by the threads */ void *runner(void *param); /* thread function */ int main(int argc, char *argv[]) { if (argc != 2) { fprintf(stderr, "Usage: %s N\n", argv[0]); return 1; } pthread_t tid; /* thread identifier */ pthread_attr_t attr; /* thread attributes */ if (pthread_attr_init(&attr) != 0) return 1; if (pthread_create(&tid, &attr, runner, argv[1]) != 0) { pthread_attr_destroy(&attr); return 1; } pthread_attr_destroy(&attr); if (pthread_join(tid, NULL) != 0) return 1; /* wait for the thread */ printf("sum = %d\n", sum); return 0; } void *runner(void *param) { int i, upper = atoi(param); sum = 0; for (i = 1; i <= upper; i++) sum += i; pthread_exit(0); }

Assume N is a non-negative integer small enough that the sum fits in int. Compiled with gcc prog.c -pthread and run, the program prints sum = 55 for ./a.out 10 and sum = 5050 for ./a.out 100 (both outputs checked by compiling and running it). The main thread creates runner, then blocks in pthread_join() until it finishes, so the print always sees the final sum; sum is a global, so both threads see the same variable — thread-shared data in action.

2021-22 CIE-I, Q210 marks
Write a program to create threads to perform the following functions on an array simultaneously: (i) sort the array in ascending order, (ii) sort the array in descending order — and record execution time in milliseconds.
Complete C program — compile with gcc -std=c11 -pthread
#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

enum { N = 6 };
typedef struct { int *values; size_t length; int descending; } SortArgs;

static int ascending(const void *left, const void *right) {
    int a = *(const int *)left, b = *(const int *)right;
    return (a > b) - (a < b);
}
static int descending(const void *left, const void *right) {
    return ascending(right, left);
}
static void *sort_array(void *arg) {
    SortArgs *a = arg;
    qsort(a->values, a->length, sizeof(int),
          a->descending ? descending : ascending);
    return NULL;
}
int main(void) {
    int original[N] = {7, 2, 9, 1, 5, 3};
    int up[N], down[N];
    for (int i = 0; i < N; ++i) up[i] = down[i] = original[i];
    SortArgs args[2] = {{up, N, 0}, {down, N, 1}};
    pthread_t workers[2];
    struct timespec start, finish;
    if (clock_gettime(CLOCK_MONOTONIC, &start) != 0) return 1;
    if (pthread_create(&workers[0], NULL, sort_array, &args[0]) != 0)
        return 1;
    if (pthread_create(&workers[1], NULL, sort_array, &args[1]) != 0) {
        pthread_join(workers[0], NULL);
        return 1;
    }
    if (pthread_join(workers[0], NULL) != 0) return 1;
    if (pthread_join(workers[1], NULL) != 0) return 1;
    if (clock_gettime(CLOCK_MONOTONIC, &finish) != 0) return 1;
    double elapsed_ms = (finish.tv_sec - start.tv_sec) * 1000.0
                      + (finish.tv_nsec - start.tv_nsec) / 1000000.0;
    printf("Ascending:");
    for (int i = 0; i < N; ++i) printf(" %d", up[i]);
    printf("\nDescending:");
    for (int i = 0; i < N; ++i) printf(" %d", down[i]);
    printf("\nElapsed wall time: %.3f ms\n", elapsed_ms);
    return 0;
}

Each worker receives a different copy of the input, so opposite sorts cannot race on one array. The argument objects live until both joins finish. CLOCK_MONOTONIC measures elapsed wall time; clock() measures process CPU time. The checked outputs are ascending 1 2 3 5 7 9 and descending 9 7 5 3 2 1; elapsed time depends on the run and is not a fixed answer.

2024-25 SEE Part-B, Q3 (alt. to Q2)8 marks
Develop a program to perform matrix multiplication using pthreads, where each thread computes one row of the resulting matrix.
Complete C program — compile with gcc -std=c11 -pthread
#include <pthread.h>
#include <stdio.h>

enum { N = 2 };
static const int A[N][N] = {{1, 2}, {3, 4}};
static const int B[N][N] = {{5, 6}, {7, 8}};
static int C[N][N];
typedef struct { int row; } RowArgs;

static void *compute_row(void *arg) {
    int row = ((RowArgs *)arg)->row;
    for (int col = 0; col < N; ++col) {
        int sum = 0;
        for (int k = 0; k < N; ++k)
            sum += A[row][k] * B[k][col];
        C[row][col] = sum;
    }
    return NULL;
}
int main(void) {
    pthread_t workers[N];
    RowArgs args[N];
    int created = 0;
    for (int row = 0; row < N; ++row) {
        args[row].row = row;
        if (pthread_create(&workers[row], NULL, compute_row, &args[row]) != 0) {
            for (int i = 0; i < created; ++i) pthread_join(workers[i], NULL);
            return 1;
        }
        ++created;
    }
    for (int row = 0; row < N; ++row)
        if (pthread_join(workers[row], NULL) != 0) return 1;
    for (int row = 0; row < N; ++row) {
        for (int col = 0; col < N; ++col)
            printf("%d%s", C[row][col], col + 1 == N ? "\n" : " ");
    }
    return 0;
}

A and B are read-only, and each worker writes a different output row. Joining all workers before printing makes their results available to main. The argument array remains alive throughout. The compiled program produces 19 22 and 43 50 as its two output rows; these entries were independently recomputed.

Reference: Silberschatz, Galvin & Gagne, ninth edition — §§4.1–4.3; §4.4.1 — threads, multicore, models, Pthreads (PDF p. 187).

Two useful exam distinctions

Both one-to-one and many-to-many mappings can support multicore parallelism. “Runs on multiple cores” alone does not uniquely identify many-to-many; use the complete mapping described in the question. On a uniprocessor, extra CPU-bound threads do not create CPU parallelism: a better matrix-multiplication algorithm can reduce work, while threads may still improve responsiveness or overlap I/O.
