3.1

Address binding

How names and offsets in a program become addresses that memory can use.

Background: memory hardware and protection

  • A program must be brought from disk into memory and placed within a process before it can run.
  • Main memory and the processor registers are the only storage the CPU can access directly. The memory unit sees only a stream of addresses with read requests, or addresses plus data with write requests.
  • A register is accessed in one CPU clock (or less). A main-memory access can take many cycles, so a cache sits between main memory and the CPU registers.
  • Along with speed, memory must be protected: the operating system must be protected from user processes, and user processes from one another. This protection is provided by hardware.

The first requirement is that each process has a separate memory space. To separate memory spaces, the hardware must know the range of legal addresses a process may use. Two registers provide this:

RegisterHolds
Base registerThe smallest legal physical memory address of the process
Limit registerThe size of the legal range

The CPU hardware compares every address generated in user mode with these registers. A legal address satisfies base ≤ address < base + limit. Any attempt by a user-mode program to access operating-system memory or another user’s memory results in a trap to the operating system, which treats it as a fatal error. The base and limit registers can be loaded only by the operating system, using a special privileged instruction. User programs therefore cannot change them.

base/limit figureworked example
A process has base register 300040 and limit register 120900. Which physical addresses may it access? Are 300040, 420939 and 420940 legal?
Legal range: 300040 ≤ address < 300040 + 120900 = 420940 300040 → legal (the base itself) 420939 → legal (last legal byte) 420940 → trap (equals base + limit)

The limit is a length, so the upper bound is exclusive.

From symbolic names to absolute addresses

A program usually resides on disk as a binary executable file. Depending on the memory management in use, the process may be moved between disk and memory during its execution. The processes on disk that are waiting to be brought into memory form the input queue. It would be inconvenient to force the first user process to start at physical address 0000, and addresses are represented differently at different stages of a program’s life:

StageForm of addressExample
Source codeSymbolicA variable name such as count
Compiled codeRelocatable — the compiler binds symbols to relocatable addresses“14 bytes from the beginning of this module”
Linked / loaded codeAbsolute — the linker or loader binds relocatable addresses to absolute ones74014

Each binding maps one address space to another.

Address binding is the mapping of instructions and data from one address representation to another. A source program refers to symbolic names such as count. A compiler or assembler can represent a name as an offset relative to a module. A linker combines object modules and resolves references between them; a loader places the resulting executable in memory. Depending on the scheme, physical placement is fixed during compilation, during loading, or during execution.

Keep the program-preparation stages separate from the time of final address binding. Compilation, linking and loading can all occur even when the final physical address is determined only on a memory reference. Linkers resolve symbols; memory-management hardware translates running-process addresses. These solve related but different problems.

The three binding times

Binding timeHow it worksIf the physical starting address changes
Compile timeThe starting location is known in advance. The compiler generates absolute addresses for that location.Recompile the absolute code for the new location.
Load timeThe compiler produces relocatable code. The loader adjusts address references when it selects the physical starting location.Reload and perform relocation for the new starting location. Ordinary load-time binding does not support moving an executing image merely by changing a base register.

Execution-time binding allows a process to resume at a different physical location after being swapped out, and supports the mappings used in paging and segmentation. The mapping must remain correct for every reference. The operating system controls it using privileged operations so a user process cannot redirect its accesses into another process’s memory.

Constructed practice using §8.1.2 notationworked example
A symbol is at byte offset 14 in a module. The module is placed at physical base 74000, then considered for placement at base 90000. What are the corresponding addresses, and what must change under each binding policy?
First placement: 74000 + 14 = 74014 New placement: 90000 + 14 = 90014

The relative offset stays 14. With compile-time absolute code, regenerate the addresses by recompilation. With load-time binding, reload and relocate the image. With execution-time binding, a logical reference to offset 14 can stay unchanged while the hardware mapping is changed to the new base. The numerical addition is the same; the time and mechanism of the addition differ.

3.2

Logical versus physical addresses

One address identifies a location within a process; another identifies a location in physical memory.

A logical address is generated by the CPU for an instruction or data reference. A physical address identifies the actual location presented to main memory. The collection of logical addresses of a program is its logical address space; the corresponding physical locations form its physical address space. In the textbook’s execution-time model, “virtual address” and “logical address” are used interchangeably.

In the textbook’s simple compile-time and load-time models, the executing instructions use already-bound absolute addresses, so logical and physical addresses coincide. With execution-time binding, they can differ. A memory-management unit (MMU) performs the mapping while the program runs. Thus a pointer can continue to denote the same logical location even when that location has a different physical backing.

Dynamic relocation with a limit check

In a simple contiguous scheme, the relocation register stores the process’s starting physical address. The limit register stores the length of its logical address range. For a nonnegative logical address, the hardware first checks that the offset is smaller than the limit. If it is legal, the MMU adds the relocation value; otherwise it traps to the operating system.

Legal logical offset: 0 ≤ LA < limit If legal: PA = base + LA Physical range: base ≤ PA < base + limit
Fig 2. Relocation with bounds checking; the limit is a length, so the upper bound is exclusive.

The run-time mapping from virtual to physical addresses is done by the MMU. In the simplest scheme, the base register is renamed the relocation register, and its value is added to every address generated by a user process at the time it is sent to memory. (MS-DOS on the Intel 80x86 family used four relocation registers.) The user program deals only with logical addresses and never sees the real physical addresses. Execution-time binding occurs when a reference is made to a memory location. The final location of a referenced address is not determined until the reference is made.

Logical addresses: 0 … max Physical addresses: R + 0 … R + max (R = value in the relocation register)

Only the operating system can load the mapping and protection registers. During a context switch, the dispatcher installs the values for the process that is about to run. Otherwise, the new process could use the previous process’s address range. The check is performed by hardware rather than a system call for every load and store.

Clarifying two base–limit conventions Book §8.1.1 checks an already-physical address against base ≤ address < base + limit. The relocation scheme in §8.3.1 instead checks a logical offset against 0 ≤ LA < limit and then adds the base. State which convention you use; comparing a logical offset directly with the physical base mixes the two models.

3.3

Dynamic loading

Load a routine only when execution actually needs it.

Dynamic loading postpones bringing a routine into memory until the routine is called. The main program is loaded and begins execution, while other routines remain on secondary storage in a relocatable form. Before transferring control to an unloaded routine, the program invokes a loader, which finds space, loads the routine, performs the required relocation, and updates the program’s address information. Subsequent calls can use the resident routine directly.

This improves memory utilization because code that is never executed need not occupy memory. A program may contain a large diagnostic routine for an unusual error; keeping that routine absent during normal operation leaves memory available for useful work. It is the portion currently needed, rather than every possible routine, that must be loaded under this scheme.

Fig 3. First use loads the routine; later calls can take the resident-routine path.
Exam points from the faculty slides
  • A routine is not loaded until it is called.
  • All routines are kept on disk in a relocatable load format.
  • Better memory-space utilization: an unused routine is never loaded.
  • Useful when large amounts of code are needed to handle infrequently occurring cases, such as error routines.
  • No special support from the OS is required. It is implemented through program design, and the OS can help by providing libraries that implement dynamic loading.

Operating-system support and limitations

Dynamic loading does not inherently require special operating-system support: a program can be designed to manage its own routine loading. Library facilities supplied by an operating system can make this easier. This statement concerns the loading technique; normal memory protection and file access still operate under the system’s rules.

Its costs include the delay on first use and the complexity of tracking where routines are located and whether they are resident. A routine that has been loaded does not automatically disappear after returning. A complete implementation must decide when its memory can be released and ensure no outstanding reference still needs it. Dynamic loading alone also does not imply that every arbitrary program larger than RAM can run; the needed code, data and loader structures must fit the scheme’s available memory.

Reusable scenario rule If the question is about an infrequently called routine taking memory unnecessarily, explain dynamic loading. If it is about resolving references to a library at execution time, explain dynamic linking. If it is about transferring individual pages on an access to a nonresident page, that is demand paging, a Unit IV topic.

A conceptual first-call walkthrough

Suppose an application’s recovery routine is kept on disk. Normal requests never enter it, so it stays unloaded. On the first error that needs recovery, the caller discovers that the routine has no resident entry point, requests its loading and relocation, and records its entry address. Control then passes to recovery. A later error can use the recorded address while the routine remains loaded. This walkthrough explains the sequence without assuming a particular operating-system API.

3.4

Dynamic linking and shared libraries

Delay library-reference resolution and let several processes use shared code.

Static linking incorporates the required library object code into a program’s executable image. Separate programs can therefore carry separate copies of the same library routines. Dynamic linking postpones the resolution of library references until the program is run. The executable retains information that allows a runtime linker to locate the required library routines instead of embedding every routine in the executable.

The textbook explains this using a small stub for a library reference. When the reference is first used, the stub locates the routine or arranges to load its library, resolves the address, and directs execution to it. The resolved target is recorded so later calls avoid repeating the same resolution. This is the conceptual lazy-linking model; a runtime linker can also resolve references when the program starts.

In the slides’ words: a stub is a small piece of code included in the image for each library-routine reference. It locates the appropriate memory-resident library routine, replaces itself with the address of the routine, and executes the routine. Dynamically linked libraries are system libraries, such as language subroutine libraries, that are linked to user programs when the programs are run. Some operating systems support only static linking, in which system libraries are treated like any other object module and combined by the loader into the binary program image.

Dynamic loading vs dynamic linking: OS support Dynamic loading needs no special OS support. Unlike dynamic loading, dynamic linking and shared libraries generally require help from the operating system. Processes are protected from one another, so only the OS can check whether the needed routine is already in another process’s memory, and allow several processes to access the same memory addresses.

What is shared, and what stays private?

A shared library can have its read-only code mapped into more than one process. Each process uses its own virtual mappings, so the same physical code need not appear at the same logical address in every process. Writable process-specific state remains private unless shared writable memory is deliberately arranged. Shared code must not modify itself, and hardware permissions should enforce its protection.

Fig 4. Independent process mappings refer to common code and distinct private data.

The operating system supplies protection and the mappings needed to share physical pages safely; the runtime linker resolves library symbols. Dynamic linking and physical sharing are closely related but should not be treated as synonyms. Linking concerns how references are resolved. Sharing concerns which physical memory is used by those mappings.

Benefits and compatibility

Dynamic linking reduces duplication in executables, and shared mappings can reduce physical-memory use. Programs can use a compatible library repair without all being statically relinked. Compatibility still matters: a changed interface or calling convention can break an old program. Library versioning and compatibility rules allow the intended version to be selected, including keeping incompatible versions side by side. An update should not be assumed to replace code inside every process already running.

3.5

Swapping

Temporarily remove a process image from RAM, then restore it so execution can continue.

In standard swapping, the operating system transfers an entire process memory image from main memory to a backing store and later brings it back. Swapping out frees physical space for another process. Swapping in restores the saved image, after which the process’s saved execution state can be used to resume it. The backing store must have enough capacity and permit access to the saved images.

The backing store is commonly a fast disk, large enough to hold copies of all memory images for all users, and it must provide direct access to these images. The system maintains a ready queue of all processes whose memory images are on the backing store or in memory and are ready to run. Swapping lets the total physical memory space of all processes exceed the real physical memory.

Standard swapping: whenever the CPU scheduler decides to execute a process, it calls the dispatcher. The dispatcher checks whether the next process in the queue is in memory. If it is not, and there is no free memory region, the dispatcher swaps out a process currently in memory and swaps in the desired process. It then reloads registers and transfers control to the selected process.

A process whose image is on backing store cannot execute its ordinary instructions there. The dispatcher must ensure that the image needed for the selected process is resident before transferring control to it. Moving images makes it possible to keep more process images in the system than fit in RAM simultaneously, but transfer overhead can dominate useful execution.

Fig 5. Standard swapping exchanges process images between RAM and backing store.

Relocation and pending I/O

Under execution-time binding, the restored process may occupy a different physical location if the operating system updates its mapping. In a simple load-time-bound model, the saved image must normally return to its original physical location unless its addresses are explicitly relocated again. Logical pointers are useful precisely because they can stay unchanged while the physical mapping changes.

A process to be swapped must be completely idle. Pending I/O creates another constraint. A device may still be transferring data into a user buffer at a physical address. If the process is swapped out and another process occupies that space, an unchecked transfer could corrupt the replacement process. The textbook gives two remedies: avoid swapping a process with such pending I/O, or perform I/O through operating-system buffers and copy the data to user space only when that space is safely available. Buffering adds copying overhead. Merely saying “the process is waiting” is therefore insufficient to establish that swapping is safe.

Cost model

The main cost is transferring the image. For an image of size S and a sustained transfer rate R, the transfer-only time in one direction is S/R. Exchanging an outgoing and incoming process requires both transfer times. Seek time, device latency, queueing and execution-state handling add further costs if included in the problem. Use consistent size units and convert seconds to milliseconds only after division.

Book, printed p.359; corrected unit conversionworked example
An outgoing and an incoming process each have a 100 MB image. Backing-store transfer speed is 50 MB/s. Ignoring device latency and other overhead, find the exchange time.
One direction = 100 MB ÷ 50 MB/s = 2 s = 2000 ms Out + in = 2 s + 2 s = 4 s = 4000 ms

This is the image-transfer component of the switch, not an ordinary register-only context-switch time. If the images have different sizes or the read and write rates differ, calculate each direction separately before adding.

Correcting a numerical typo in the source The textbook (printed p.359, PDF p.383) and the faculty slide (p.28) both compute 100 MB ÷ 50 MB/s, then call the one-way time “200 milliseconds.” That conversion is wrong: 2 seconds is 2000 milliseconds. Their total of about 4000 ms for both directions is consistent with the corrected value.
worked example
A system has 4 GB of main memory and the resident operating system takes 1 GB. What is the largest user process? Compare the time to swap out a 100 MB process with a 3 GB process at 50 MB/s.
Largest user process = 4 GB − 1 GB = 3 GB 100 MB ÷ 50 MB/s = 2 s 3 GB ÷ 50 MB/s = 3000 MB ÷ 50 MB/s = 60 s (3072 MB ÷ 50 = 61.44 s with binary units)

The major part of swap time is transfer time, and the total transfer time is directly proportional to the amount of memory swapped. It is therefore useful to know how much memory a process is actually using, not just how much it might use, so that only that amount is swapped.

Swapping in modern and mobile systems

Standard swapping is not used in modern operating systems. It requires too much swapping time and provides too little execution time to be a reasonable memory-management solution. Modified versions are used instead:

  • Swapping is normally disabled, but starts if the amount of free memory falls below a threshold. It is disabled again when free memory rises.
  • Swapping portions of processes, rather than entire processes, to decrease swap time.

Mobile systems typically do not support swapping in any form. They use flash memory rather than large hard disks, and three things make swapping unattractive: the resulting space constraint, the limited number of writes flash memory can tolerate before it becomes unreliable, and the poor throughput between main memory and flash. Instead, when free memory runs low:

SystemResponse to low free memory
Apple iOSAsks applications to voluntarily relinquish allocated memory. Read-only data such as code can be removed and reloaded from flash later; an app that fails to free enough memory may be terminated.
AndroidMay terminate a process if insufficient free memory is available, first writing its application state to flash so it can be restarted quickly.

The whole-process model here explains the syllabus term. It should be distinguished from transferring selected pages of a process, which is developed with virtual memory in Unit IV.

3.6

Contiguous memory allocation

Give each process one continuous physical region; manage the holes between occupied regions.

With contiguous allocation, all of a process’s memory lies in one continuous physical block. The operating system occupies a protected region and allocates user regions from the remaining memory. The relocation-and-limit mechanism in 3.2 both translates process-relative addresses and prevents the process from accessing another region.

Contiguous allocation is one of the earliest efficient methods for sharing main memory between the OS and user processes. Memory protection is achieved with the relocation register and limit register. The relocation register also supports transient operating-system code: OS code, such as a rarely used device driver, that comes and goes as needed. This lets the size of the OS change during execution.

Fixed and variable partitions

In fixed partitioning, memory is divided into predetermined partitions, each holding at most one process. The degree of multiprogramming is bound by the number of partitions, and a process must fit in a suitable partition. This scheme was originally used by IBM OS/360, where it was called MFT (Multiprogramming with a Fixed number of Tasks). Its variable-partition generalisation, MVT, was used primarily in batch environments, and its ideas also apply to time-sharing systems. If a partition is larger than the process, the unused space inside the assigned partition cannot be used by another process. This is internal fragmentation.

In variable partitioning, the operating system maintains the occupied regions and the free regions, called holes. It selects a sufficiently large hole when a process arrives. A larger hole is split into the allocated portion and a remaining free portion. When a process leaves, its region becomes free; adjacent holes are merged, or coalesced. Nonadjacent holes cannot be merged merely by changing a list entry because live process memory lies between them.

As processes enter the system they are put into an input queue. The OS considers each process’s memory requirement and the amount of available memory, and may order the input queue according to a scheduling algorithm. At any time there is a list of available block (hole) sizes and an input queue. Memory is allocated to processes until the requirement of the next process cannot be satisfied. That process can wait, or the OS can skip down the queue to a smaller request. Satisfying a request of size n from a list of free holes is called the dynamic storage-allocation problem.

Internal versus external fragmentation

Fragmentation is the problem that, as processes are loaded into and removed from memory, the free memory space is broken into little pieces.

Internal fragmentation occurs when memory is divided into fixed-sized blocks. If the memory allocated to a process is slightly larger than the memory requested, the difference is unused space inside the allocation. For example, assigning a partition of 18,464 bytes to a request for 18,462 bytes leaves 2 bytes inside the allocation. External fragmentation exists when there is enough total free memory to satisfy a request, but the free space is not contiguous: it is split into small holes interspersed with allocated memory. First fit, best fit and worst fit do not eliminate this structural problem.

The 50-percent rule

Depending on total memory and the average process size, external fragmentation may be a minor or a major problem. Statistical analysis of first fit shows that, even with some optimisation, given N allocated blocks, another 0.5 N blocks will be lost to fragmentation. That is, about one-third of memory may be unusable. This is the 50-percent rule.

Allocated blocks: N Lost to fragmentation: 0.5 N Total = N + 0.5 N = 1.5 N Unusable fraction = 0.5 N ÷ 1.5 N = 1/3
Reading the slide’s 50-percent illustration The faculty slide illustrates the rule with 100 MB of memory: 50 MB allocated to an application, 10 MB of system overhead and 7 MB lost to fragmentation, giving 50 − 10 − 7 = 33 MB usable, “only about a third.” Treat this as a loose illustration of “about one-third is lost or unusable”, not a derivation. The rule itself is the ratio above: with N blocks in use, 0.5 N blocks’ worth of memory is wasted in holes, which is one-third of the 1.5 N total.
Fig 7. Compaction changes physical placement; coalescing only joins already-adjacent holes.

One solution to external fragmentation is compaction: shuffle the memory contents so that all free memory is placed together in one large block. The simplest compaction algorithm moves all processes toward one end of memory. Compaction moves occupied regions so that the holes become one large free region. In the textbook’s simple relocation model, execution-time relocation makes this possible by allowing the mapping to change when a process moves. Compaction costs memory-copy time and must respect outstanding references, including I/O. It reduces external fragmentation, but it does not recover unused bytes inside an allocated partition. Compaction is possible only if relocation is dynamic and done at execution time.

The other solution is to permit the logical address space of a process to be noncontiguous, so that a process can be given physical memory wherever it is available. Two complementary techniques do this: segmentation (3.8) and paging (3.7).

3.7

Paging

Divide logical memory into pages and physical memory into equal-sized frames.

Paging lets a process occupy noncontiguous physical memory. The process’s logical address space is divided into fixed-sized pages, while physical memory is divided into frames of the same size. Any available frame can hold a page. The operating system records the mapping in the process’s page table, and the MMU consults that mapping when translating addresses.

A program can still see a continuous logical address range even though consecutive pages lie in distant frames. When a process is to be executed, its pages are loaded into any available memory frames from their source (a file system or the backing store). The backing store is divided into fixed-sized blocks of the same size as the frames, or clusters of multiple frames. To run a program of size N pages, the OS must find N free frames, load the program and set up a page table. The page size, like the frame size, is defined by the hardware. It is a power of 2, typically between 4 KB and 8 KB on the systems in the slides. Pages are units of logical memory; frames are units of physical memory. A page number and a frame number are therefore different quantities, even when they happen to have the same numerical value. In this introductory model, the pages needed for execution are resident; deciding when to fetch a nonresident page is the separate demand-paging topic in Unit IV.

Splitting and translating an address

For a byte-addressable system with page size P, divide the logical address by P. The quotient is the page number p; the remainder is the offset d within that page. The page table supplies frame number f. Replace the page number by the frame number and retain the offset. If the table stores a frame base address rather than a frame number, add the offset to that base directly.

p = floor(LA / P) d = LA mod P f = page_table[p] PA = f × P + d For an m-bit logical address and P = 2ⁿ bytes: page number: m − n high bits; offset: n low bits

Allocation and internal fragmentation

For basic paging, the operating system counts the process’s required pages and obtains that many free frames. The frames need not be adjacent. A frame table tracks physical frames and their owners; a page table tracks the logical-page mappings for a process. The dispatcher installs the correct page-table state when switching processes.

At page granularity, paging eliminates external fragmentation: any free frame can satisfy the need for one page. It can still waste space inside the last allocated frame when the process size is not an exact multiple of the page size. Smaller pages can reduce that waste but require more mapping entries for the same logical range. Larger pages reduce page-table entries but can increase unused space.

Book, printed p.370worked example
A process requires 72,766 bytes and the page size is 2048 bytes. Find the required frames and internal fragmentation.
72766 = 35 × 2048 + 1086 Frames needed = ceil(72766 / 2048) = 36 Allocated = 36 × 2048 = 73728 bytes Unused = 2048 − 1086 = 73728 − 72766 = 962 bytes

There are 35 full pages and one partial page. The unused part of its assigned frame is internal fragmentation. If the process size were an exact page multiple, this particular last-frame waste would be zero; always use the ceiling rather than automatically adding a frame.

Worst case: a process that needs n pages plus 1 byte is allocated n + 1 frames, wasting almost an entire frame. On average, the waste is about half a page per process.

The OS keeps track of which frames are allocated, which are free and how many frames there are in a data structure called the frame table. It has one entry per physical frame, recording whether the frame is free and, if not, which page of which process it holds. When a process arrives, its pages are placed in frames taken from the free-frame list, and the frame numbers are written into its page table.

Page-table storage and hardware support

Each operating system has its own method of storing page tables. Most allocate a page table for each process, and a pointer to it is stored with the other register values in the process control block. A small page table can be implemented as a set of dedicated registers. A large page table is usually described in this model as residing in main memory, with a privileged page-table base register (PTBR) pointing to it. With one level of page table, no TLB and no other caches, a data reference requires one memory access to obtain the page-table entry and one to obtain the data. The page-table access has a cost even though the referenced data page is already resident.

The translation look-aside buffer (TLB)

The two-memory-access problem is solved by a special fast-lookup hardware cache called associative memory, or a translation look-aside buffer (TLB). Each TLB entry has two parts: a key (tag) — the page number — and a value — the frame number. All keys are compared simultaneously. A TLB is a small, fast associative cache of address translations. It is not a cache of the program’s data bytes. On a TLB hit, the matching entry supplies the frame number and access information without a main-memory page-table lookup. On a TLB miss, the translation must be obtained from the page table, after which it can be inserted into the TLB. The data is then accessed using the translated physical address.

Fig 10. TLB hit and miss paths in a single-level, resident-page model.

After a TLB miss, the page number and frame number are added to the TLB. If the TLB is already full, an existing entry must be replaced (replacement policies range from LRU to random). Some TLB entries can be wired down: they cannot be removed, which is typical for key kernel code.

Translations belong to address spaces. Some TLBs store an address-space identifier (ASID) in each entry, which uniquely identifies a process and provides address-space protection for it. If entries are not tagged with an ASID, the TLB must be flushed (erased) at every context switch so that stale translations are invalidated. ASID tags let translations from different address spaces coexist when the tags are managed correctly. Changing a page mapping or its permissions also requires keeping cached translations consistent with that change.

A TLB miss is not a page fault A TLB miss says only that the translation was not found in the cache. A page-table lookup can resolve it without disk access. A fault due to a nonresident page is part of virtual-memory handling in Unit IV. Never attach disk-transfer time to every TLB miss.

Effective access time

The percentage of times that the page number of interest is found in the TLB is the hit ratio. The faculty slides write the formula directly from the two cases:

TLB_hit_time = TLB_search_time + memory_access_time TLB_miss_time = TLB_search_time + memory_access_time + memory_access_time EAT = TLB_hit_time × hit_ratio + TLB_miss_time × (1 − hit_ratio)

This is the same formula as below with ε = TLB search time and m = memory access time. Let h be the hit ratio, m the main-memory access time, and ε a separate serial TLB lookup time. Assume a single-level table, resident pages, no other cache effects and one lookup per reference. A hit costs ε + m; a miss costs ε + 2m. Weight these cases by their probabilities.

EAT = h(ε + m) + (1 − h)(ε + 2m) = ε + (2 − h)m If TLB lookup overhead is neglected: EAT = (2 − h)m

Protection and page sharing

Memory protection is implemented by associating protection bits with each frame, normally kept in the page table, to mark a page read-only or read-write. More bits can mark a page execute-only, and so on. Hardware checks the requested operation and traps on a violation. A valid–invalid bit in the textbook’s basic model marks whether a page belongs to the process’s legal logical address space. Do not silently equate this basic validity convention with every architecture’s present/resident bit used for demand paging.

Page-granularity checks do not necessarily detect the exact end of a program inside its final page. In the textbook example, the program ends at logical byte 10468 with 2048-byte pages. Page 5 contains that byte, so a whole-page validity check can also permit offsets through logical byte 12287. Pages starting at byte 12288 are invalid in that example. Software still has to respect the actual object and program bounds.

A process rarely uses its whole address range, so a full-size page table would waste space on invalid entries. Some systems provide a page-table length register (PTLR) to indicate the size of the page table. Each logical address is checked against the PTLR value, and an address beyond it causes a trap.

Reentrant code never changes during execution, so two or more processes can execute it at the same time. Different page tables can deliberately map the same physical code frames. This provides the shared-library arrangement in 3.4: common read-only code with distinct writable data frames. The operating system controls the mappings and enforces permissions. The page table provides controlled sharing rather than letting a process access arbitrary frames.

Hierarchical paging

Break the logical address space into multiple page tables. The simplest technique is a two-level page table: we page the page table itself. The page number is split into p1, an index into the outer page table, and p2, the displacement within the page of the inner page table that p1 selects. Address translation works from the outer page table inward, so this scheme is also called a forward-mapped page table.

Hashed page tables

A common approach for handling address spaces larger than 32 bits is a hashed page table, whose hash value is the virtual page number. Each entry of the hash table holds a chain (linked list) of elements that hash to the same location. Each element contains:

  1. the virtual page number,
  2. the value of the mapped page frame, and
  3. a pointer to the next element in the chain.

Translation: the virtual page number p is hashed into the table. p is compared with the first element’s virtual page number. If they match, that element’s frame r is used to form the physical address r | d. Otherwise the following elements in the chain are searched for a match.

Fig 12. Hashed page table: the page number is hashed, then the chain is searched for a matching virtual page number.

Inverted page tables

An ordinary page table has one entry for every logical page a process may use, and every process has its own table. An inverted page table instead has one entry for each real page (frame) of memory. Rather than tracking all possible logical pages of each process, it tracks all physical pages. Each entry holds the virtual address of the page stored in that frame, together with information about the process that owns the page (its process id). Only one page table exists in the whole system.

A logical address is ⟨pid, p, d⟩. The table is searched for the entry matching ⟨pid, p⟩. If it is found at entry i, the physical address is ⟨i, d⟩; otherwise an illegal-address access has been attempted.

Fig 13. Inverted page table: search for ⟨pid, p⟩; the index i of the matching entry is the frame number.

An inverted table decreases the memory needed to store page tables, but increases the time needed to search the table when a page reference occurs, since the table is ordered by physical address while lookups are by virtual address. To limit the search to one, or at most a few, page-table entries, a hash table is used. The TLB can accelerate access further. A drawback is that shared memory is harder to implement, because there is only one virtual-page entry for each physical frame.

3.8

Segmentation

Represent a program as meaningful variable-sized units, each with its own bounds.

Segmentation supports the programmer’s view of memory as a collection of logical units: code, data, a stack, a subroutine or a library. These segments can have different lengths because their sizes follow their purposes. A logical address is a pair ⟨segment number, offset⟩, rather than just an offset in a single undivided region.

The programmer does not think of memory as a linear array of bytes, but as a collection of variable-sized segments with no necessary ordering among them. Segmentation is the memory-management scheme that supports this programmer view: a logical address space is a collection of segments, and each segment has a name and a length. Addresses specify both the segment name and the offset within the segment. For simplicity segments are numbered, so the programmer specifies each address by two quantities. The segmentation hardware maps this two-dimensional, user-defined address to the one-dimensional physical memory.

A process’s segments need not be adjacent to one another in physical memory. In pure segmentation, however, each individual segment is stored contiguously. This distinction explains why segmentation can scatter a process across memory but still suffer external fragmentation when the operating system must find a large enough hole for one segment.

Segment-table translation

The segment table holds a base and a limit for each segment. The base is the segment’s starting physical address, and the limit is its length. For a logical address ⟨s,d⟩, first check that segment number s is a valid table index. Select its entry, check 0 ≤ d < limit[s], and add the offset to the base only if the checks succeed. A bad segment number or an out-of-bounds offset causes a trap.

Check: segment s exists and 0 ≤ d < limit[s] Then: PA = base[s] + d Otherwise: trap to the operating system
Fig 14. Segment translation using the book’s segment 2 example, with explicit bounds checks.

Protection, sharing and allocation

Logical units make it natural to assign different protections to code and data. A code segment can be read-only and executable, while a data segment can allow writes. Sharing can be arranged by making entries in different processes refer to the same protected physical segment. Each process can still have its own stack and data. These are conceptual uses of the segment boundary; the precise permission fields depend on the system.

Segments can grow independently only when the allocation scheme can provide room or relocate them. Because they have variable sizes, their allocation resembles the hole-management problem in contiguous allocation. Pure segmentation does not impose fixed-page rounding waste, but variable-sized free holes can produce external fragmentation. Hardware tables, bookkeeping and alignment can still cost memory; “no fixed-page internal fragmentation” does not mean “zero overhead.”

PagingEqual pages and frames; page table replaces p with f, leaving d unchanged. TLB (key = page, value = frame) caches translations; ASIDs avoid flushing. PTLR bounds the table. Structures: hierarchical (page the page table), hashed (chains for >32-bit), inverted (one entry per frame).Treating a TLB miss as a disk access, or a frame number as a byte base

Prepare a complete long answer

Start with the definition and the problem solved. Draw the corresponding diagram and explain the steps in order. For an allocation or translation question, state units and assumptions, show intermediate results and check legality before calculating the final address. Finish with the method’s costs, fragmentation and protection properties. For a comparison, use the same properties for both methods.
