3.1

Address binding

How names and offsets in a program become addresses that memory can use.

Address binding is the mapping of instructions and data from one address representation to another. A source program refers to symbolic names such as count. A compiler or assembler can represent a name as an offset relative to a module. A linker combines object modules and resolves references between them; a loader places the resulting executable in memory. Depending on the scheme, physical placement is fixed during compilation, during loading, or during execution.

Keep the program-preparation stages separate from the time of final address binding. Compilation, linking and loading can all occur even when the final physical address is determined only on a memory reference. Linkers resolve symbols; memory-management hardware translates running-process addresses. These solve related but different problems.

Fig 1. Program preparation and the possible times of final address binding.

The three binding times

Binding timeHow it worksIf the physical starting address changes

Load timeThe compiler produces relocatable code. The loader adjusts address references when it selects the physical starting location.Reload and perform relocation for the new starting location. Ordinary load-time binding does not support moving an executing image merely by changing a base register.
Execution timeThe running program uses logical addresses. Hardware maps them to physical addresses when they are used.Update the mapping when moving the process; its logical addresses can stay the same. Hardware translation support is required.

Execution-time binding allows a process to resume at a different physical location after being swapped out, and supports the mappings used in paging and segmentation. The mapping must remain correct for every reference. The operating system controls it using privileged operations so a user process cannot redirect its accesses into another process’s memory.

A symbol is at byte offset 14 in a module. The module is placed at physical base 74000, then considered for placement at base 90000. What are the corresponding addresses, and what must change under each binding policy?

With execution-time binding, a logical reference to offset 14 can stay unchanged while the hardware mapping is changed to the new base. The numerical addition is the same; the time and mechanism of the addition differ.

3.2

Logical versus physical addresses

One address identifies a location within a process; another identifies a location in physical memory.

A logical address is generated by the CPU for an instruction or data reference. A physical address identifies the actual location presented to main memory. The collection of logical addresses of a program is its logical address space; the corresponding physical locations form its physical address space. In the textbook’s execution-time model, “virtual address” and “logical address” are used interchangeably.

In the textbook’s simple compile-time and load-time models, the executing instructions use already-bound absolute addresses, so logical and physical addresses coincide. With execution-time binding, they can differ. A memory-management unit (MMU) performs the mapping while the program runs. Thus a pointer can continue to denote the same logical location even when that location has a different physical backing.

Dynamic relocation with a limit check

In a simple contiguous scheme, the relocation register stores the process’s starting physical address. The limit register stores the length of its logical address range. For a nonnegative logical address, the hardware first checks that the offset is smaller than the limit. If it is legal, the MMU adds the relocation value; otherwise it traps to the operating system.

Legal logical offset: 0 ≤ LA < limit If legal: PA = base + LA Physical range: base ≤ PA < base + limit
Fig 2. Relocation with bounds checking; the limit is a length, so the upper bound is exclusive.

Only the operating system can load the mapping and protection registers. During a context switch, the dispatcher installs the values for the process that is about to run. Otherwise, the new process could use the previous process’s address range. The check is performed by hardware rather than a system call for every load and store.

Clarifying two base–limit conventions Book §8.1.1 checks an already-physical address against base ≤ address < base + limit. The relocation scheme in §8.3.1 instead checks a logical offset against 0 ≤ LA < limit and then adds the base. State which convention you use; comparing a logical offset directly with the physical base mixes the two models.

3.3

Dynamic loading

Load a routine only when execution actually needs it.

Dynamic loading postpones bringing a routine into memory until the routine is called. The main program is loaded and begins execution, while other routines remain on secondary storage in a relocatable form. Before transferring control to an unloaded routine, the program invokes a loader, which finds space, loads the routine, performs the required relocation, and updates the program’s address information. Subsequent calls can use the resident routine directly.

This improves memory utilization because code that is never executed need not occupy memory. A program may contain a large diagnostic routine for an unusual error; keeping that routine absent during normal operation leaves memory available for useful work. It is the portion currently needed, rather than every possible routine, that must be loaded under this scheme.

Fig 3. First use loads the routine; later calls can take the resident-routine path.

Operating-system support and limitations

Dynamic loading does not inherently require special operating-system support: a program can be designed to manage its own routine loading. Library facilities supplied by an operating system can make this easier. This statement concerns the loading technique; normal memory protection and file access still operate under the system’s rules.

Its costs include the delay on first use and the complexity of tracking where routines are located and whether they are resident. A routine that has been loaded does not automatically disappear after returning. A complete implementation must decide when its memory can be released and ensure no outstanding reference still needs it. Dynamic loading alone also does not imply that every arbitrary program larger than RAM can run; the needed code, data and loader structures must fit the scheme’s available memory.

Reusable scenario rule If the question is about an infrequently called routine taking memory unnecessarily, explain dynamic loading. If it is about resolving references to a library at execution time, explain dynamic linking. If it is about transferring individual pages on an access to a nonresident page, that is demand paging, a Unit IV topic.

A conceptual first-call walkthrough

Suppose an application’s recovery routine is kept on disk. Normal requests never enter it, so it stays unloaded. On the first error that needs recovery, the caller discovers that the routine has no resident entry point, requests its loading and relocation, and records its entry address. Control then passes to recovery. A later error can use the recorded address while the routine remains loaded. This walkthrough explains the sequence without assuming a particular operating-system API.

3.4

Dynamic linking and shared libraries

Delay library-reference resolution and let several processes use shared code.

Static linking incorporates the required library object code into a program’s executable image. Separate programs can therefore carry separate copies of the same library routines. Dynamic linking postpones the resolution of library references until the program is run. The executable retains information that allows a runtime linker to locate the required library routines instead of embedding every routine in the executable.

The textbook explains this using a small stub for a library reference. When the reference is first used, the stub locates the routine or arranges to load its library, resolves the address, and directs execution to it. The resolved target is recorded so later calls avoid repeating the same resolution. This is the conceptual lazy-linking model; a runtime linker can also resolve references when the program starts.

What is shared, and what stays private?

A shared library can have its read-only code mapped into more than one process. Each process uses its own virtual mappings, so the same physical code need not appear at the same logical address in every process. Writable process-specific state remains private unless shared writable memory is deliberately arranged. Shared code must not modify itself, and hardware permissions should enforce its protection.

Fig 4. Independent process mappings refer to common code and distinct private data.

The operating system supplies protection and the mappings needed to share physical pages safely; the runtime linker resolves library symbols. Dynamic linking and physical sharing are closely related but should not be treated as synonyms. Linking concerns how references are resolved. Sharing concerns which physical memory is used by those mappings.

Benefits and compatibility

Dynamic linking reduces duplication in executables, and shared mappings can reduce physical-memory use. Programs can use a compatible library repair without all being statically relinked. Compatibility still matters: a changed interface or calling convention can break an old program. Library versioning and compatibility rules allow the intended version to be selected, including keeping incompatible versions side by side. An update should not be assumed to replace code inside every process already running.

3.5

Swapping

Temporarily remove a process image from RAM, then restore it so execution can continue.

In standard swapping, the operating system transfers an entire process memory image from main memory to a backing store and later brings it back. Swapping out frees physical space for another process. Swapping in restores the saved image, after which the process’s saved execution state can be used to resume it. The backing store must have enough capacity and permit access to the saved images.

A process whose image is on backing store cannot execute its ordinary instructions there. The dispatcher must ensure that the image needed for the selected process is resident before transferring control to it. Moving images makes it possible to keep more process images in the system than fit in RAM simultaneously, but transfer overhead can dominate useful execution.

Fig 5. Standard swapping exchanges process images between RAM and backing store.

Relocation and pending I/O

Under execution-time binding, the restored process may occupy a different physical location if the operating system updates its mapping. In a simple load-time-bound model, the saved image must normally return to its original physical location unless its addresses are explicitly relocated again. Logical pointers are useful precisely because they can stay unchanged while the physical mapping changes.

Pending I/O creates another constraint. A device may still be transferring data into a user buffer at a physical address. If the process is swapped out and another process occupies that space, an unchecked transfer could corrupt the replacement process. The textbook gives two remedies: avoid swapping a process with such pending I/O, or perform I/O through operating-system buffers and copy the data to user space only when that space is safely available. Buffering adds copying overhead. Merely saying “the process is waiting” is therefore insufficient to establish that swapping is safe.

Cost model

The main cost is transferring the image. For an image of size S and a sustained transfer rate R, the transfer-only time in one direction is S/R. Exchanging an outgoing and incoming process requires both transfer times. Seek time, device latency, queueing and execution-state handling add further costs if included in the problem. Use consistent size units and convert seconds to milliseconds only after division.

Book §8.2.1, printed p.359; corrected unit conversionworked example

3.6

Contiguous memory allocation

Give each process one continuous physical region; manage the holes between occupied regions.

With contiguous allocation, all of a process’s memory lies in one continuous physical block. The operating system occupies a protected region and allocates user regions from the remaining memory. The relocation-and-limit mechanism in 3.2 both translates process-relative addresses and prevents the process from accessing another region.

Fixed and variable partitions

In fixed partitioning, memory is divided into predetermined partitions, each holding at most one process. The number of partitions limits the number of resident processes, and a process must fit in a suitable partition. If a partition is larger than the process, the unused space inside the assigned partition cannot be used by another process. This is internal fragmentation.

In variable partitioning, the operating system maintains the occupied regions and the free regions, called holes. It selects a sufficiently large hole when a process arrives. A larger hole is split into the allocated portion and a remaining free portion. When a process leaves, its region becomes free; adjacent holes are merged, or coalesced. Nonadjacent holes cannot be merged merely by changing a list entry because live process memory lies between them.

Reusing the remainder of a hole is essential in the variable-partition examples below.

Internal versus external fragmentation

Internal fragmentation is unused space inside a block that has already been allocated. For example, assigning a partition of 18,464 bytes to a request for 18,462 bytes leaves 2 bytes inside the allocation. External fragmentation is free space scattered among separate holes: the total may be sufficient for a request even though no individual hole is large enough. First fit, best fit and worst fit do not eliminate this structural problem.

Fig 6. Compaction changes physical placement; coalescing only joins already-adjacent holes.

Compaction moves occupied regions so that the holes become one large free region. In the textbook’s simple relocation model, execution-time relocation makes this possible by allowing the mapping to change when a process moves. Compaction costs memory-copy time and must respect outstanding references, including I/O. It reduces external fragmentation, but it does not recover unused bytes inside an allocated partition.

3.7

Paging

Divide logical memory into pages and physical memory into equal-sized frames.

Paging lets a process occupy noncontiguous physical memory. The process’s logical address space is divided into fixed-sized pages, while physical memory is divided into frames of the same size. Any available frame can hold a page. The operating system records the mapping in the process’s page table, and the MMU consults that mapping when translating addresses.

A program can still see a continuous logical address range even though consecutive pages lie in distant frames. Pages are units of logical memory; frames are units of physical memory. A page number and a frame number are therefore different quantities, even when they happen to have the same numerical value. In this introductory model, the pages needed for execution are resident; deciding when to fetch a nonresident page is the separate demand-paging topic in Unit IV.

Splitting and translating an address

For a byte-addressable system with page size P, divide the logical address by P. The quotient is the page number p; the remainder is the offset d within that page. The page table supplies frame number f. Replace the page number by the frame number and retain the offset. If the table stores a frame base address rather than a frame number, add the offset to that base directly.

p = floor(LA / P) d = LA mod P f = page_table[p] PA = f × P + d For an m-bit logical address and P = 2ⁿ bytes: page number: m − n high bits; offset: n low bits

Allocation and internal fragmentation

For basic paging, the operating system counts the process’s required pages and obtains that many free frames. The frames need not be adjacent. A frame table tracks physical frames and their owners; a page table tracks the logical-page mappings for a process. The dispatcher installs the correct page-table state when switching processes.

At page granularity, paging eliminates external fragmentation: any free frame can satisfy the need for one page. It can still waste space inside the last allocated frame when the process size is not an exact multiple of the page size. Smaller pages can reduce that waste but require more mapping entries for the same logical range. Larger pages reduce page-table entries but can increase unused space.

Book §8.5.1, printed p.370worked example

There are 35 full pages and one partial page. The unused part of its assigned frame is internal fragmentation. If the process size were an exact page multiple, this particular last-frame waste would be zero; always use the ceiling rather than automatically adding a frame.

Page-table storage and hardware support

A small page table can be held in fast registers. A large page table is usually described in this model as residing in main memory, with a privileged page-table base register (PTBR) pointing to it. With one level of page table, no TLB and no other caches, a data reference requires one memory access to obtain the page-table entry and one to obtain the data. The page-table access has a cost even though the referenced data page is already resident.

The translation look-aside buffer (TLB)

A TLB is a small, fast associative cache of address translations. It is not a cache of the program’s data bytes. On a TLB hit, the matching entry supplies the frame number and access information without a main-memory page-table lookup. On a TLB miss, the translation must be obtained from the page table, after which it can be inserted into the TLB. The data is then accessed using the translated physical address.

Fig 9. TLB hit and miss paths in a single-level, resident-page model.

Translations belong to address spaces. If entries are not tagged with an address-space identifier (ASID), changing the address space requires invalidating stale translations. ASID tags let translations from different address spaces coexist when the tags are managed correctly. Changing a page mapping or its permissions also requires keeping cached translations consistent with that change.

A TLB miss is not a page fault A TLB miss says only that the translation was not found in the cache. A page-table lookup can resolve it without disk access. A fault due to a nonresident page is part of virtual-memory handling in Unit IV. Never attach disk-transfer time to every TLB miss.

Effective access time

Let h be the hit ratio, m the main-memory access time, and ε a separate serial TLB lookup time. Assume a single-level table, resident pages, no other cache effects and one lookup per reference. A hit costs ε + m; a miss costs ε + 2m. Weight these cases by their probabilities.

EAT = h(ε + m) + (1 − h)(ε + 2m) = ε + (2 − h)m If TLB lookup overhead is neglected: EAT = (2 − h)m

Protection and page sharing

Page-table entries include protection information such as read, write or execute permission. Hardware checks the requested operation and traps on a violation. A valid–invalid bit in the textbook’s basic model marks whether a page belongs to the process’s legal logical address space. Do not silently equate this basic validity convention with every architecture’s present/resident bit used for demand paging.

Page-granularity checks do not necessarily detect the exact end of a program inside its final page. In the textbook example, the program ends at logical byte 10468 with 2048-byte pages. Page 5 contains that byte, so a whole-page validity check can also permit offsets through logical byte 12287. Pages starting at byte 12288 are invalid in that example. Software still has to respect the actual object and program bounds.

Different page tables can deliberately map the same physical code frames. This provides the shared-library arrangement in 3.4: common read-only code with distinct writable data frames. The operating system controls the mappings and enforces permissions. The page table provides controlled sharing rather than letting a process access arbitrary frames.

Long-answer structure Define pages and frames, draw translation, derive page/offset fields, work one address, explain the TLB, then discuss protection, sharing and fragmentation. Keep the translation mechanism separate from Unit IV’s decisions about loading and replacing pages.

3.8

Segmentation

Represent a program as meaningful variable-sized units, each with its own bounds.

Segmentation supports the programmer’s view of memory as a collection of logical units: code, data, a stack, a subroutine or a library. These segments can have different lengths because their sizes follow their purposes. A logical address is a pair ⟨segment number, offset⟩, rather than just an offset in a single undivided region.

A process’s segments need not be adjacent to one another in physical memory. In pure segmentation, however, each individual segment is stored contiguously. This distinction explains why segmentation can scatter a process across memory but still suffer external fragmentation when the operating system must find a large enough hole for one segment.

Segment-table translation

The segment table holds a base and a limit for each segment. The base is the segment’s starting physical address, and the limit is its length. For a logical address ⟨s,d⟩, first check that segment number s is a valid table index. Select its entry, check 0 ≤ d < limit[s], and add the offset to the base only if the checks succeed. A bad segment number or an out-of-bounds offset causes a trap.

3.1

Background & Race Conditions

Why cooperating processes need synchronizing at all — and a concrete example of exactly how things go wrong without it.

Cooperating processes

Cooperating processes are processes that can affect, or be affected by, other processes executing in the system — typically because they share data directly or through shared memory. Concurrent access to that shared data can cause data inconsistency: if two or more processes try to access and modify the same data at the same time, the result can depend on the precise timing of their execution rather than on the logic of either process alone. Maintaining consistency requires mechanisms that ensure cooperating processes execute in an orderly way — this is process synchronization.

The motivating example: a shared buffer counter

Consider the classic producer-consumer setup: a bounded buffer of n slots, a producer that fills slots, and a consumer that empties them. One simple way to track how many slots are full is a shared integer counter, initially 0, incremented by the producer after each item it adds and decremented by the consumer after each item it removes.

Fig 11. The producer and consumer both update a shared counter — innocuous if they never overlap, dangerous if they do.

Race conditions

At the machine level, counter++ is not one operation — it's three: load counter into a register, increment the register, store the register back. counter-- is the same shape. If the producer's three steps and the consumer's three steps interleave instead of running back-to-back, the final value of counter depends on the exact interleaving — not just on the fact that one increment and one decrement occurred. A situation where several processes access shared data concurrently and the outcome depends on the particular order of access is called a race condition.

Fig 12. A single interleaving of the producer's and consumer's load-modify-store steps — verified by simulating this exact sequence in code — leaves counter at 4, not 5.

counter starts at 5. Producer and consumer execute counter++ and counter-- concurrently, interleaved exactly as S0–S5 in Fig 12. What is the final value of counter?

Simulating this exact instruction sequence gives counter = 4. The only value that would be "correct" from a program-logic standpoint is 5 (one net increment, one net decrement, no change) — 4 is only reachable because the interleaving let the consumer's stale read (S2, before the producer's increment was stored) silently overwrite the producer's work at S4. Different interleavings can just as easily produce 6 instead — the point isn't which wrong answer you get, it's that any answer other than 5 is possible at all.

3.2

The Critical Section Problem

A precise name for the danger zone, and the three properties every correct solution must guarantee.

Critical, entry, exit, and remainder sections

Consider a system of n processes {P₀, P₁, … Pₙ₋₁}. Each process has a segment of code — its critical section — in which it may be changing data in a shared region of memory (updating a common variable, writing a file, modifying a table). The defining rule: when one process is executing in its critical section, no other process may be executing in its own critical section. The critical-section problem is to design a protocol the processes can use to guarantee this.

Each process must explicitly ask permission before entering its critical section — that request is the entry section. The critical section may be followed by an exit section. Everything else is the remainder section.

Fig 13. The general structure of process Pᵢ — a loop of entry section, critical section, exit section, remainder section.

The three requirements

Any solution to the critical-section problem must satisfy all three of the following:

RequirementWhat it guarantees
1. Mutual ExclusionIf process Pᵢ is executing in its critical section, no other process can be executing in its critical section at the same time.
2. ProgressIf no process is in its critical section and some processes wish to enter, only processes not in their remainder sections can participate in deciding who goes next — and that decision cannot be postponed indefinitely.
3. Bounded WaitingThere's a bound on how many times other processes are allowed to enter their critical sections after a process has requested entry and before that request is granted.
Exam tip

If bounded waiting is not guaranteed, the result is starvation — a process can be requested to enter but perpetually skipped. This is exactly the link back to §3.10's "drawbacks of semaphores": violating requirement 3 is how starvation happens, not a separate phenomenon. Always name all three requirements when a question asks you to "identify the requirements of a critical section" — partial answers are a common way to drop marks here.

Preemptive vs non-preemptive kernels

Two approaches exist depending on whether the kernel itself is preemptible: a preemptive kernel allows a process to be preempted even while running in kernel mode; a non-preemptive kernel lets a process run until it exits kernel mode, blocks, or voluntarily yields the CPU. Non-preemptive kernels are essentially free of race conditions on kernel data by construction — since only one process is ever actually running in kernel mode at a time — but preemptive kernels are far better suited to real-time programming, since a high-priority process isn't stuck waiting behind a low-priority one running in the kernel.

3.3

Peterson's Solution

A purely software two-process solution — and a full proof it satisfies all three critical-section requirements.

Peterson's solution is a classic software-only solution to the critical-section problem, restricted to exactly two processes, Pᵢ and Pⱼ, that alternate between their critical and remainder sections. It illustrates just how much care is needed to satisfy mutual exclusion, progress, and bounded waiting all at once. The two processes share two data items:

int turn; // whose turn it is: if turn==i, Pi may enter its CS boolean flag[2]; // flag[i]==true means Pi is ready/wants to enter its CS

Process Pᵢ

do { flag[i] = true; turn = j; while (flag[j] && turn == j) ; // spin critical section flag[i] = false; remainder section } while (true);

Process Pⱼ

do { flag[j] = true; turn = i; while (flag[i] && turn == i) ; // spin critical section flag[j] = false; remainder section } while (true);
Fig 14. Both processes announce intent (flag) then politely defer (turn) — since each sets turn to the *other* process last, whichever write happens second determines who actually waits.

Correctness proof

  1. Mutual exclusion is preserved. Pᵢ enters its critical section only if flag[j]==false or turn==i. Since both processes set turn to the other process's index just before spinning, whichever process's turn-write happened last is the one left spinning — so at most one of the two conditions can simultaneously fail to hold for both processes at once.
  2. The progress requirement is satisfied. If Pⱼ isn't interested (its remainder section), flag[j]==false and Pᵢ enters immediately. If both want in, exactly one of them "loses" the race to set turn last, and that determination is made the moment both flags are set — the decision is never postponed.
  3. Bounded waiting is met. The instant one process exits its critical section (flag[i]=false), the other's while condition becomes false immediately — so a waiting process is delayed by at most one entry of the other process, never indefinitely.

Disadvantages of Peterson's solution

Despite the clean proof, Peterson's solution has real limits worth naming if a question asks for them: it's restricted to exactly two processes; it relies on busy-waiting (the spin loop), wasting CPU cycles while blocked rather than yielding the CPU; and — the deeper problem — it isn't guaranteed to work on modern hardware at all, since compilers and CPUs are free to reorder independent-looking memory operations unless the code uses explicit memory barriers, which is exactly why §3.4's hardware-level primitives exist as the practical alternative.

Mutual exclusion: YES, in both cases

P1's guard (S1==S2) and P2's guard (S1!=S2) are exact logical complements of each other — at any instant, S1 and S2 are either equal or not, so exactly one of "P1 may enter" / "P2 may enter" can be true, never both. This holds regardless of the starting case; simulating both:

Case 1 (S1=0,S2=0): P2 enters first (S1==S2) → S1=0,S2=1 → P1 enters → S1=1,S2=1 → P2 enters → … Case 2 (S1=0,S2=1): P1 enters first (S1≠S2) → S1=1,S2=1 → P2 enters → S1=1,S2=0 → P1 enters → …

Both cases settle into the same clean strict alternation — just starting with a different process going first.

Progress: NO — this is the actual weakness the question is testing

This scheme forces strict alternation: after P2 exits, only P1 can enter next; after P1 exits, only P2 can. Simulating the case where P2 finishes one turn and then has nothing further to do (its remainder section runs long, or forever): P1 gets exactly one more entry using the state P2 already flipped, then is permanently blocked waiting for a flag-flip only P2 can perform — even though P2 isn't competing for the critical section at all. That's a textbook Progress violation (§3.2's requirement 2: a process not in its remainder section shouldn't be blocked by one that is). This is precisely the gap Peterson's solution closes — its flag[] array lets a process signal "I'm not interested" so the other never waits on someone who isn't playing, while turn alone (this scheme's equivalent) only ever encodes "whose turn is it," with no way to say "I don't want a turn right now."

Synchronization Hardware

Software solutions like Peterson's aren't guaranteed to work on modern architectures — so the hardware itself offers atomic instructions to build locks from.

Software-only solutions such as Peterson's aren't guaranteed to work on modern computer architectures (compiler/CPU instruction reordering can break the assumptions they rely on). The alternative is hardware-level atomic instructions — all of the solutions below are built on the idea of locking: protecting a critical region with a lock variable that's tested and set in one indivisible step.

test_and_set

boolean test_and_set(boolean *target) { boolean rv = *target; *target = TRUE; return rv; } // executes as a single, indivisible machine cycle

It takes a shared lock variable, unconditionally sets it to TRUE (locked), and returns whatever the lock's value was before that write. By convention 0 means unlocked and 1 means locked.

do { while (test_and_set(&lock)) ; // spin while lock was already held critical section lock = false; remainder section } while (true);

compare_and_swap

void swap(boolean *a, boolean *b) { boolean temp = *a; *a = *b; *b = temp; }
Clarifying a structural bug in the source

The slide deck's own "Code for Mutual Exclusion" places the swap(&lock,&key) call after the while loop, with the loop's body empty (a bare semicolon). As printed, key is set to true once and never changes inside the loop, so while(key==true) would spin forever and the swap — which is what actually has a chance of clearing key — would never run. The swap must be the loop's retry body, not a one-shot call after it:

do { key = TRUE; while (key == TRUE) swap(&lock, &key); // retried on every spin, not called once critical section lock = FALSE; remainder section } while (true);

Walk through it: initially lock=false (0). A process sets its local key=true, then repeatedly swaps lock and key until the swap hands it back key=false — which happens exactly when lock was false going into that swap (so the swap sets lock=true for this process and key=false, ending the spin). Once inside, it eventually sets lock=false on exit, letting the next spinning process's swap succeed.

Exam tip

Both test_and_set and compare_and_swap provide mutual exclusion, but neither guarantees bounded waiting on its own — a spinning process has no guaranteed turn order, so in principle one process could keep "winning" the race indefinitely while another starves. This is a genuinely common written-exam point: "do these hardware instructions satisfy all three CS requirements?" — the answer is mutual exclusion yes, bounded waiting not without extra bookkeeping (e.g. a waiting array plus these primitives, the standard textbook fix).

3.5

Mutex Locks

The simplest software-visible locking abstraction — acquire, use, release.

A mutex lock (mutual-exclusion lock) is a boolean variable, 0 (unlocked) or 1 (locked). A process wanting to enter its critical section must acquire the lock first — if it's already 0 (free), the process sets it to 1 and proceeds; once done, it releases the lock, setting it back to 0.

do { acquire lock critical section release lock remainder section } while (true);

The shared lock variable is often called available, initially true (free):

acquire() { while (!available) ; // busy wait available = false; } release() { available = true; }
The cost hiding in "busy wait"

A mutex lock implemented this way is a spinlock — a waiting process burns CPU cycles continuously re-checking the lock instead of yielding the CPU. That's wasteful on a single-core system (the lock holder can't even run to release it while the waiter spins), but genuinely useful on a multicore system for very short critical sections, since the overhead of a full context switch to sleep-and-wake can exceed the time just spent spinning. This tradeoff — spin vs block — is exactly why semaphores (§3.6) matter: a semaphore's wait() can be implemented to block the calling process instead of spinning, avoiding the wasted cycles.

Semaphores

A synchronization tool more flexible than a mutex — an integer that can gate access to a whole pool of resources, not just one.

A semaphore S is a non-negative integer variable, shared between processes, that can only be accessed through two indivisible operations: wait() and signal() — originally named P() and V().

wait(S) { while (S <= 0) ; // busy wait — resource unavailable S--; } signal(S) { S++; }

wait() asks "is the resource available?" — if S≤0 it spins; the moment S becomes positive, it breaks out and claims one unit by decrementing. signal() returns a unit to the pool. Both operations execute indivisibly — once one process starts modifying S, no other process can simultaneously modify it.

Also called the Producer-Consumer problem — the first of three classical synchronization problems, solved with exactly three semaphores.

A buffer of n slots sits between a producer, which produces data and stores it in the buffer, and a consumer, which removes data from the buffer. Three rules must hold:

  1. The producer must not insert data when the buffer is full.

Readers-Writers Problem

Some processes only need to look; others need exclusive access. Letting the readers share costs nothing — letting two writers collide costs everything.

A database is shared among concurrent processes. Some processes only want to read it; others — writers — want to read and update it. Two readers accessing the data at the same time causes no problem at all. Two writers (or a reader and a writer) accessing it at the same time can cause real chaos. The goal: give writers exclusive access, while letting any number of readers share access freely amongst themselves.

Solution using two semaphores and a counter

VariableTypeInitial valueRole
mutexSemaphore1Protects updates to readcount itself, so two readers incrementing/decrementing it don't race.
wrtSemaphore1Shared between readers and writers — a writer holds it for the whole write; the first reader to arrive also grabs it (locking out writers), and the last reader to leave releases it.
readcountInteger0Tracks how many readers are currently active.
Fig 18. Readers share the database freely amongst themselves; a writer needs exclusive access, gated by the shared wrt semaphore.

Writer code

do { wait(wrt); // perform the write — // no reader or writer allowed in signal(wrt); } while (true);

Reader code

do { wait(mutex); readcount++; if (readcount == 1) wait(wrt); // 1st reader locks out writers signal(mutex); // perform the read wait(mutex); readcount--; if (readcount == 0) signal(wrt); // last reader lets writers back in signal(mutex); } while (true);

Why if (readcount == 1) wait(wrt) instead of every reader waiting on wrt? Because only the first reader needs to actually contend for exclusive access — once it holds wrt, every subsequent reader can proceed freely (protected only by the quick mutex around the counter update), and only the last reader to leave needs to release wrt for writers.

A known weakness of this particular solution

This is the classic "readers-preference" solution: as long as at least one reader is active, a new reader can always join in (readcount never drops to 0), which means a waiting writer can be starved indefinitely by a continuous stream of readers. A "writers-preference" variant (not shown here) fixes this by having a waiting writer block new readers from starting once it's requested access — worth mentioning if a question specifically asks about fairness.

Dining Philosophers Problem

Five philosophers, five chopsticks — a deceptively simple resource-sharing puzzle that deadlocks if solved naively.

Five philosophers sit at a round table, alternating between thinking and eating. Between each pair of adjacent philosophers sits one chopstick — five chopsticks in total — and a philosopher needs both neighboring chopsticks to eat, picking them up one at a time and releasing both when done.

Fig 19. Five philosophers, five shared chopstick semaphores — each philosopher needs both of their two adjacent chopsticks simultaneously.

The naive semaphore solution — and why it deadlocks

Semaphore chopstick[5]; // all initialized to 1 do { wait(chopstick[i]); wait(chopstick[(i+1) % 5]); eat(); signal(chopstick[i]); signal(chopstick[(i+1) % 5]); think(); } while (true);
Not a bug — a deliberately naive first attempt

This straightforward solution has a real flaw, and the source material presents it precisely so the fix can be taught: if all five philosophers simultaneously pick up their left chopstick, every chopstick[i] is now held, and every philosopher's second wait() blocks forever waiting for their right neighbor's chopstick — who is in turn waiting on them. This is a genuine deadlock (a 5-way circular wait, the same underlying failure mode as §3.10's 2-process S/Q example, just with 5 participants instead of 2).

Three standard fixes

  1. Limit concurrent diners. Allow at most 4 philosophers to sit at the table simultaneously — with only 4 of 5 possibly holding a first chopstick, at least one is guaranteed to get both of theirs.
  2. Atomic pickup. A philosopher may pick up a chopstick only if both are available — done inside a critical section, so "pick up left, then right" can never leave a philosopher holding just one.
  3. Asymmetric ordering. Odd-numbered philosophers pick up their left chopstick first, then their right; even-numbered philosophers pick up right first, then left. This breaks the symmetry that let all five grab "the same side" simultaneously.

3.10

Deadlock & Starvation

Semaphores solve the synchronization problem — but misuse them and they introduce two new failure modes of their own.

Deadlock: two or more processes are each waiting indefinitely for an event that only one of the other waiting processes can cause. Starvation (indefinite blocking): a process may simply never be removed from the queue of processes suspended on a semaphore, even though the semaphore keeps being signaled to others.

Fig 20. Circular wait — P0 holds S and wants Q; P1 holds Q and wants S. Neither can ever proceed.
unit 3.pdf p41, classic exampleworked example · verified with real threads
Semaphores S and Q are both initialized to 1. P0 executes wait(S) then wait(Q); P1 executes wait(Q) then wait(S). Show that this can deadlock.

Consider this interleaving: P0 runs wait(S) and acquires S. P1 runs wait(Q) and acquires Q. Now P0 attempts wait(Q) — but Q is held by P1, so P0 blocks. P1 attempts wait(S) — but S is held by P0, so P1 blocks too. Each process is waiting for a resource the other holds, and neither will ever signal because neither can finish its critical section to reach the signal() calls. Reproduced with two real Python threads and a timeout to detect the hang:

P0: attempting wait(S) → acquired S P1: attempting wait(Q) → acquired Q P0: attempting wait(Q) → TIMED OUT (deadlocked) P1: attempting wait(S) → TIMED OUT (deadlocked)

The fix in general: impose a consistent global ordering on resource acquisition — e.g. every process must acquire S before Q, never the other way round — which makes this particular circular-wait interleaving impossible.

Priority inversion

Priority inversion is a scheduling-adjacent problem: a lower-priority process holds a lock that a higher-priority process needs, but the lower-priority process itself can't run to finish and release the lock because a *medium*-priority process (uninvolved in the lock at all) keeps preempting it. The effective priority of the high-priority process has been "inverted" down to the low-priority process's level. The standard fix is the priority-inheritance protocol: temporarily boost the lock-holding process's priority to match the highest-priority process waiting on it, so it can finish and release the lock promptly.

Where this connects back

Deadlock here is the same underlying phenomenon as §3.9's naive dining-philosophers solution (circular wait) and, more generally, exactly what bounded waiting (§3.2, requirement 3) exists to prevent. Semaphores are a *tool* for solving the critical-section problem, not an automatic guarantee against all three failure modes — that's the connective thread across this entire unit.

Hardware primitives at a glance

test_and_set(target): atomically reads target, sets it TRUE, returns the old value. compare_and_swap / swap(a,b): atomically exchanges two values. Both give mutual exclusion; neither alone gives bounded waiting.

Deadlock vs starvation vs priority inversion

Deadlock: circular wait, nobody proceeds (e.g. P0 holds S wants Q, P1 holds Q wants S). Starvation: a process is never picked from the semaphore's wait queue, even though others keep proceeding. Priority inversion: a low-priority lock-holder can't finish because a *medium*-priority process keeps preempting it, indirectly blocking a high-priority waiter — fixed by priority inheritance.
