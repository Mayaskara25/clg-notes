 Section 1 — CPU Scheduling: Basic Concepts (12 questions)

 Q1. Define CPU scheduling. Explain when CPU scheduling decisions may occur.

 Answer:

 Definition: CPU scheduling is the operating-system function that chooses a process from
 the ready queue and assigns the CPU to it. It is the basis of multiprogramming: while one
 process waits for I/O, another can execute so the processor remains productive (Unit 2, pp.
 22–23).

 The four situations in which a scheduling decision may take place:

   1. Running → Waiting: a process requests I/O or waits for an event. The CPU becomes
      available to another ready process.
   2. Running → Ready: a timer interrupt or higher-priority process preempts the currently
      running process.

   3. Waiting → Ready: an I/O operation or event completes; the awakened process may
      compete for the CPU.
   4. Running → Terminated: the executing process completes and the CPU must be
      assigned to another process.

 Scheduling in cases 1 and 4 is necessarily non-preemptive (the running process relinquishes
 the CPU); scheduling decisions in cases 2 and 3 can support preemption. Goal: keep the CPU
 busy and optimize throughput, waiting, turnaround and response times.

 Q2. In preemptive scheduling, when can a running process be interrupted?

 Answer:

 A running process may be interrupted when its time quantum expires, when a higher-
 priority process becomes ready, or when a newly arrived process has a shorter
 remaining burst under SRTF. A process can also yield the processor voluntarily or be
 interrupted by hardware. On preemption: (1) save the running process’s registers/program
 counter in its PCB, (2) move it to the ready state, (3) select another ready process, and (4)
 restore that process’s context. Example: if P1 has remaining CPU time 8 ms and P2 arrives
 with 2 ms, SRTF preempts P1 to run P2.

 Q3. Which algorithm is most suitable for a time-sharing system?

 Answer:

 Round Robin (RR). It is designed for interactive/time-sharing systems (Unit 2, p. 45). Step
 1: maintain the ready queue in FIFO order. Step 2: give the first process a fixed time slice
 (quantum). Step 3: if it finishes, remove it; otherwise preempt it and append it to the queue.
 Step 4: repeat. Every waiting process receives frequent CPU access, improving response
 time. A very small quantum causes context-switch overhead; a very large quantum
 approaches FCFS.

 Q4. Fill in the blanks: ______ scheduling is more appropriate for time-shared/
 interactive systems, and ______ scheduling is often used in long-term/job
 scheduling.

 Answer:

 Answer: Preemptive scheduling; Non-preemptive scheduling. The first permits
 interruption for responsive interactive services; the second can finish an admitted batch/job
 without time slicing. Note: A long-term scheduler controls job admission rather than
 specifically choosing CPU bursts; this is the conventional exam interpretation of the blanks.

 Q6. Define the convoy effect and explain its consequences.

 Answer:

 The convoy effect occurs mainly in FCFS when a long CPU-bound process runs first and
 many short I/O-bound processes wait behind it (Unit 2, p. 28).

 Example: CPU bursts P1=20, P2=2, P3=2, all ready at time 0. FCFS Gantt: 0–20 P1 | 20–22
 P2 | 22–24 P3 . Waiting times are 0, 20 and 22; average = (0+20+22)/3 = 14. If shorter jobs
 run first: 0–2 P2 | 2–4 P3 | 4–24 P1 ; average WT = (0+2+4)/3 = 2.

 Consequences: larger mean waiting/turnaround, poor response for short tasks, alternation
 between CPU and I/O device idleness, and reduced effective utilization. Remedy: SJF/SRTF
 or RR where appropriate.

 Q7. Explain starvation and aging in CPU scheduling.

 Answer:

 Starvation (indefinite blocking): a ready process waits for a very long or unlimited time
 because the scheduling algorithm repeatedly chooses other processes. Example: under strict
 Priority scheduling, a priority-9 task may never run while priority-1 tasks continuously arrive.

 Aging: progressively increase the effective priority of a process the longer it waits. For a
 scheme where 1 is highest, a waiting process might change from priority 9 → 8 → 7 → ... → 1

 at regular intervals. It eventually gets service, preventing starvation. Unit 2, p. 41, identifies
 starvation as the key Priority-scheduling drawback and aging as the remedy.

 Q8. Which scheduling algorithm suffers starvation? Explain the solution with
 an example.

 Answer:

 Priority scheduling can cause starvation of low-priority processes; SJF/SRTF may also
 starve long jobs if short jobs keep arriving.

 Example: P1 (priority 5) is ready at t=0. Every 2 ms a new process of priority 1 arrives and
 consumes the CPU for 2 ms. Without intervention P1 can keep waiting indefinitely. Apply
 aging: decrease P1’s numerical priority by one after each 4 ms of waiting (5 → 4 → 3 → 2 →
 1). Once it reaches the highest-priority class, FCFS within that class eventually schedules P1,
 provided class membership and aging rules ensure fairness. This restores bounded progress
 under fair admission.

 Q9. State the disadvantages of SJF and Priority scheduling.

 Answer:

 SJF/SRTF: (1) next CPU burst is not precisely known and must be estimated; (2) large CPU-
 burst jobs may starve; (3) SRTF creates context switches and monitoring overhead; (4) job
 length estimation may be inaccurate. Priority: (1) low-priority jobs may starve; (2) priority
 assignment may be subjective or difficult; (3) priority inversion occurs if a low-priority thread
 holds a lock needed by a high-priority thread; (4) preemptive priority can increase context-
 switch overhead. Remedies: aging for starvation and priority inheritance for priority
 inversion.

 Q10. The time taken by the dispatcher to stop one process and start another
 is called ______.

 Answer:

 Dispatch latency. It is the time needed for the dispatcher to stop one running process and
 start another. A context switch is a principal part of this delay (Unit 2, p. 54).

 Q11. Explain the four actions in a context switch with a diagram.

 Answer:

 Context switch: The CPU stops executing one process and resumes a different process by
 saving and restoring process state.

 Four actions:

   1. Interrupt/trap or scheduling event: control enters the kernel and a scheduling
      decision is required.
   2. Save the current context: store P1’s program counter, CPU registers, stack pointer,
      flags and necessary bookkeeping in P1’s PCB; mark P1 as ready or waiting.

   4. Restore and dispatch: load P2’s saved registers, stack pointer, and program counter

 Q12. Discuss the different schedulers in operating systems.

 Answer:

 1. Long-term (job) scheduler: selects which jobs from secondary storage enter memory/
 ready state. It controls the degree of multiprogramming and balances CPU-bound versus
 I/O-bound jobs. Runs relatively infrequently.

 2. Short-term (CPU) scheduler: picks one of the ready processes to execute next. It runs
 frequently (on interrupts, blocking and termination) and therefore must be fast. FCFS, SJF,
 Priority and RR are CPU scheduling methods.

 3. Medium-term scheduler (swapper): temporarily suspends/swaps out a process from
 memory and brings it back later to manage memory pressure and multiprogramming.

 Flow diagram: Job pool → [Long-term] → Ready queue → [Short-term] → CPU ; Ready/
 blocked ↔ [Medium-term] ↔ Suspended/swapped-out .

 Comparison: long-term = admission; short-term = CPU allocation; medium-term =
 suspension/resumption.

 Section 2 — CPU Scheduling Criteria (4 questions)

 Q1. Discuss the criteria for evaluating CPU-scheduling algorithms.

 Answer:

 Unit 2, pp. 24–25, lists CPU utilization, throughput, turnaround time, waiting time
 and response time.

   1. CPU utilization = (CPU busy time / elapsed time) × 100% ; maximize.

RVCE • Unit II & III • Exam Revision                                                        5 / 85OS CIE 2 | Complete Solved Question Bank

   2. Throughput = number of processes completed / elapsed time ; maximize.
   3. Turnaround time (TAT) = completion time (CT) − arrival time (AT) ; minimize.
   4. Waiting time (WT) = TAT − CPU burst time (BT) for CPU-only numerical problems;
      minimize. It measures time in the ready queue.
   5. Response time (RT) = first time scheduled − arrival time ; minimize, especially in
      interactive systems.

 Example: AT=2, BT=5, first dispatch=6, CT=13 → TAT=13−2=11; WT=11−5=6;
 RT=6−2=4. Average each metric over all processes for comparisons.

 Q2. Define CPU utilization and state its goal.

 Answer:

 CPU utilization is the percentage of the total observed interval during which the CPU
 executes useful processes. Formula: CPU utilization (%) = (total CPU busy time / total
 elapsed time) × 100 (for a problem with scheduling overhead, specify whether overhead
 counts as useful or occupied time).

 Example: Across 100 ms, jobs execute for 75 ms and the CPU is idle for 25 ms. CPU
 utilization = (75/100)×100 = 75%. Goal: maximize utilization by keeping a ready process
 executing whenever possible; avoid unnecessary idle time and excessive dispatch overhead
 (Unit 2, pp. 22, 24–25).

 Q3. Compare algorithms on average waiting time and turnaround time.

 Answer:

 Calculate for each algorithm and the same process workload:

  TAT_i = CT_i − AT_i and WT_i = TAT_i − BT_i ; then Average WT = Σ WT_i / n ,
  Average TAT = Σ TAT_i / n .

 Example: Three processes arrive at t=0 with bursts 8, 2, 1 (P1, P2, P3). FCFS: 0–8 P1 | 8–
 10 P2 | 10–11 P3 . WT=(0,8,10), average 6; TAT=(8,10,11), average 29/3 = 9.67. SJF: 0–1
 P3 | 1–3 P2 | 3–11 P1 . WT=(3,1,0), average 4/3 = 1.33; TAT=(11,3,1), average 15/3 = 5.

 Inference: SJF reduces both averages in this example; in general it has the optimal mean
 waiting time for a fixed set with known CPU bursts. FCFS may produce a convoy effect. RR
 usually sacrifices some mean WT/TAT for lower response time and fairness. Priority varies
 with assigned priorities.

 Q4. Explain the effect of context switches on scheduling performance.

 Answer:

 A context switch saves the current process state and restores another process state. It
 takes CPU time but performs no useful application processing. If N context switches each
 cost d ms, total switching overhead is approximately N × d ms. Example: 40 switches × 0.2
 ms = 8 ms lost to switching.

 Impacts: (1) reduces effective throughput and CPU time available for work, (2) increases
 completion/turnaround times, (3) can harm cache/TLB locality, and (4) too many switches
 increase scheduler overhead. RR trade-off: very small q produces many switches and fast
 initial response; very large q approaches FCFS (Unit 2, pp. 47–48). Good design: choose a
 practical quantum, use efficient dispatching, and avoid unnecessary preemption.

 Section 4 — Real-Time CPU Scheduling (3 questions)

 Q1. Explain the distinguishing characteristics of a real-time operating system
 (RTOS).

 Answer:

 A real-time operating system (RTOS) must provide predictable, bounded response
 times, especially when tasks have deadlines. Unlike general-purpose OS scheduling,
 correctness depends on when a result is produced as well as what result is produced.

 Features:

   1. Deadline awareness: tasks have release times, execution demands and deadlines.
   2. Deterministic scheduling: bounded interrupt and dispatch latencies are essential (Unit
      2, pp. 53–54).

RVCE • Unit II & III • Exam Revision                                                      48 / 85OS CIE 2 | Complete Solved Question Bank

   3. Priority-aware preemption: urgent work should be able to run rapidly.
   4. Predictable synchronization: shared-resource access must limit blocking and priority
      inversion.
   5. Reliability: system must behave consistently under expected load.

 Types: A hard real-time system must meet a deadline; a late result may be useless (e.g.,
 airbag control). A soft real-time system prefers timeliness but may tolerate occasional
 deadline misses (e.g., streamed media). Event latency is the time from an event to service;
 it includes interrupt latency and dispatch delay. Lower, bounded latency is especially
 important for hard real time.

 Section 5 — Process Synchronization: Background (4
 questions)

 Q1. Define race condition and mention methods to avoid it.

 Answer:

RVCE • Unit II & III • Exam Revision                                                                            50 / 85OS CIE 2 | Complete Solved Question Bank

 A race condition occurs when two or more processes/threads concurrently access and
 manipulate shared data, and the outcome depends on the order in which the accesses are
 interleaved (Unit 3, p. 7).

 Prevention techniques: (1) protect shared updates with a mutex/lock, (2) use binary/
 counting semaphores, (3) use monitors or condition variables, (4) use atomic operations
 such as test_and_set or compare_and_swap, (5) design correct critical sections satisfying
 mutual exclusion, progress and bounded waiting, or (6) use message passing to avoid unsafe
 shared-memory access. Principle: updates that must happen together must be atomic or
 correctly synchronized.

 Q2. What is a race condition? Explain with a suitable example.

 Answer:

 Suppose counter=5 . A producer increments it and a consumer decrements it; logically the
 final value should remain 5.

 Machine-level steps:

       Producer: R1 = counter; R1 = R1 + 1; counter = R1;
       Consumer: R2 = counter; R2 = R2 - 1; counter = R2;

 Unsafe interleaving:

   Step              Instruction                                                   R1   R2   counter

   Start             Initial                                                       —    —          5

   1                 Producer R1 = counter                                          5   —          5

 Section 6 — Critical Section Problem (5 questions)

 Q1. Define the critical-section problem, show its general structure and explain
 its requirements.

 Answer:

 A critical section (CS) is a part of a process that reads/writes shared variables, shared
 memory, files or other common resources. The critical-section problem is to design an
 entry/exit protocol so concurrent processes access these resources safely (Unit 3, pp. 8–10).

 General structure of process Pi:

RVCE • Unit II & III • Exam Revision                                                             52 / 85OS CIE 2 | Complete Solved Question Bank

    while (1) {
         // Entry section: request permission
         // Critical section: use/update shared resource
         // Exit section: release permission
         // Remainder section: unrelated work
    }

 Three compulsory properties:

   1. Mutual exclusion: if Pi is inside its CS, no other process can simultaneously execute a
      CS for the same shared resource.
   2. Progress: when no process is inside the CS and interested processes exist, the choice of
      the next entrant is not postponed indefinitely; unrelated remainder-section processes
      must not prevent a decision.
   3. Bounded waiting: after Pi requests entry, there is a finite bound on how often other
      processes may enter before Pi gets its turn; prevents starvation.

 A correct solution should not assume fixed CPU speeds or a favorable timing order.

 Q2. Define the critical-section problem with an example and explain any two
 conditions.

 Answer:

 Definition: When multiple concurrent processes update the same shared data, the OS must
 control entry so the shared state remains consistent.

 Example: balance=100 . P1 executes balance=balance+50 and P2 executes
 balance=balance−30 . Their read–modify–write sequences can interleave and produce the
 wrong answer. Encapsulating each update in a CS prevents the race.

 Condition 1 — Mutual exclusion: while P1 changes the balance, P2 cannot access the
 same update CS. Hence each transaction observes a consistent balance.

 Condition 2 — Progress: if no transaction is updating the balance, then a waiting
 transaction must eventually be selected; a process doing unrelated work cannot hold up
 entry. A complete solution additionally requires bounded waiting so neither P1 nor P2
 starves.

 Q4. Why is mutual exclusion important in solving the critical-section problem?

 Answer:

 Mutual exclusion ensures that shared-data modifications behave as though they occur
 sequentially, not as unsafe interleavings.

 Consider x=0 , P1 executes x=x+1 , and P2 does the same. Without mutual exclusion both can
 read 0 and store 1, leaving the incorrect result 1. With a lock, one completes 0→1 ; the other
 then completes 1→2 , giving 2.

 Importance: (1) prevents lost updates, (2) preserves integrity of shared tables/files, (3)
 avoids race conditions, and (4) supports correct concurrent execution. Limitation: mutual
 exclusion alone does not guarantee progress or bounded waiting; those must also be
 examined.

 Q5. Analyze S1/S2 Boolean protocol for initial (0,0) and (0,1); are mutual
 exclusion and progress guaranteed?

 Answer:

 Given:

    // P1
    while (S1 == S2) ;
    /* critical section */
    S1 = S2;

    // P2
    while (S1 != S2) ;
    /* critical section */
    S2 = !S1;

 Case 1: S1=0, S2=0:

   1. P1 checks S1==S2 → 0==0 , true, so P1 busy-waits.
   2. P2 checks S1!=S2 → 0!=0 , false, so P2 enters its CS.

   3. On P2 exit, S2=!S1=1 ; now (S1,S2)=(0,1) .
   4. P1’s condition 0==1 is false; P1 may enter its CS. On exit, S1=S2=1 , returning the turn to
      P2.

 Case 2: S1=0, S2=1:

   1. P1 checks 0==1 → false, so P1 enters.
   2. P2 checks 0!=1 → true, so P2 waits.
   3. On P1 exit, S1=S2=1 ; now P2 can enter and later set S2=!S1=0 .

 Mutual exclusion: Yes in both cases, under atomic reads/writes: the two while-conditions

 and the variables change only on exit.

 section, P1 waits even though the CS is empty. Similarly if (0,1) and P1 is not interested, P2
 waits. This is strict alternation, which violates progress despite preserving mutual
 exclusion. Conclusion: not a fully valid CS solution.

 Section 7 — Peterson’s Solution (5 questions)

 Q1. Explain Peterson’s solution to the critical-section problem.

 Answer:

 Peterson’s algorithm for two processes Pi and Pj, with j = 1−i :

    // Shared variables
    bool flag[2] = {false, false};
    int turn;

    // Process Pi, where j = 1-i
    while (true) {
         flag[i] = true;                // declare interest
         turn = j;                     // allow j to win a simultaneous tie
         while (flag[j] && turn == j)
              ;                        // busy wait

         /* CRITICAL SECTION */

         flag[i] = false;               // leave critical section
         /* REMAINDER SECTION */
    }

 Meaning: flag[i] says Pi wants to enter; turn resolves competition if both want in. If only
 Pi wants entry, flag[j]=false , so it enters immediately. If both want entry, the last writer to
 turn yields, so one enters and the other waits. (Unit 3, pp. 13–15.)

 Result: Peterson’s design uses only the shared flag[2] and turn variables and satisfies the
 three classical requirements in its ideal memory model.

RVCE • Unit II & III • Exam Revision                                                           55 / 85OS CIE 2 | Complete Solved Question Bank

 Correctness proof (assuming sequentially consistent atomic reads/writes):

   1. Mutual exclusion: Assume both Pi and Pj are in their CS. Both flags must be true. For Pi
      to pass its while-loop, turn ≠ j , i.e., turn=i . For Pj to pass, turn ≠ i , i.e., turn=j . Since
      turn cannot equal i and j simultaneously, this is impossible. Thus only one enters.
   2. Progress: If only Pi is interested, flag[j]=false and Pi enters. If both are interested, the
      final value of turn makes exactly one while-condition false, selecting one process; an
      uninterested process cannot prevent entry.
   3. Bounded waiting: After Pi sets flag[i]=true , Pj can enter at most once before Pi. On
      finishing Pj sets flag[j]=false ; if Pj immediately retries, it writes turn=i , giving Pi
      priority. Hence Pi cannot be bypassed indefinitely.

 Restrictions: only two processes, spinning wastes CPU cycles, shared-memory ordering
 must be respected (compiler/CPU reordering may break naïve code on modern hardware),
 and it is not a drop-in replacement for production mutexes.

 Q1. Explain a hardware solution to the critical-section problem for two
 processes.

 Answer:

 Hardware provides atomic read–modify–write operations, so no competing CPU can
 observe a partially completed lock acquisition. A two-process (and multiprocess) solution
 may use test_and_set.

 Atomic test_and_set primitive:

    bool test_and_set(bool *target) { // executed ATOMICALLY by hardware
         bool old = *target;
         *target = true;
         return old;
    }

 Spinlock using it:

    bool lock = false;            // shared, initially unlocked
    while (true) {
         while (test_and_set(&lock))
              ;                  // busy wait
         /* CRITICAL SECTION */
         lock = false;           // atomic unlock/store
         /* REMAINDER SECTION */
    }

 If a process finds lock=false , it atomically receives false and sets lock=true ; it enters. All
 other calls return true and spin. The owner releases by storing false .

 Why it works: the lock can change from false to true for only one process per successful
 atomic acquisition, preserving mutual exclusion. However, this simple TAS spinlock does
 not guarantee bounded waiting: one process can repeatedly win the lock. A scheduling
 assumption that the lock holder eventually runs and releases it is also needed for progress.
 (Unit 3, pp. 16–18.)

 Section 9 — Semaphores and Mutex Locks (14 questions)

 Q1. Define a semaphore and explain its need in process synchronization.

 Answer:

 A semaphore is an integer synchronization variable that is accessed only through two
 atomic operations: wait(S) (also called P) and signal(S) (also called V) (Unit 3, pp. 22–
 23).

    wait(S):       acquire one available permit; if none, block/wait
    signal(S):     release a permit, possibly waking one waiter

 Conceptual counting definition:

    wait(S) {
         while (S <= 0) ;         // textbook spinning variant
         S--;                      // test/decrement must together be atomic
    }
    signal(S) {
         S++;                      // increment must be atomic
    }

 Why needed: (1) enforce mutual exclusion, (2) order dependent tasks, (3) control access
 to multiple instances of a resource, and (4) avoid producer/consumer races. Example: a
 binary semaphore mutex=1 protects a shared counter. Every process does wait(mutex);
 counter++; signal(mutex); , ensuring only one updates the counter at a time. In practical
 blocking semaphores, a waiter sleeps rather than repeatedly checking the value.

 Q2. Name the two types of semaphores and give an example of each.

 Answer:

 1. Binary semaphore: count is either 0 or 1, typically used for exclusive access. Example
 mutex=1 ; first wait(mutex) changes it to 0, so other threads must wait until signal(mutex)
 returns it to 1.

 2. Counting semaphore: permits range from 0 to N for N equivalent resource instances
 (an internal blocking implementation may represent waiting processes using a negative
 bookkeeping count). Example printers=3 ; at most three threads can hold a printer

 Q8. What happens if a non-recursive mutex is locked twice by the same
 thread?

 Answer:

 Normally the second lock blocks and the thread deadlocks against itself, because
 the mutex is already held and the same thread cannot reach the unlock. In POSIX, behavior

 requires the same number of unlocks. Exam answer: self-deadlock for a normal non-

 is their neighbor. P2 may eat if its neighbors are not eating. On P0’s putdown , the monitor
 checks both neighbors and signals whichever can eat. A monitor is easier to reason about
 than managing several fork locks manually.

 Q3. Write C routines for a deadlock-free solution to Dining Philosophers.

 Answer:

 Deadlock-free semaphore algorithm (room limit):

    semaphore room = 4;
    semaphore fork[5] = {1, 1, 1, 1, 1};

    void philosopher(int i) {
         while (true) {
              think();
              wait(room);                // at most 4 contenders
              wait(fork[i]);
              wait(fork[(i + 1) % 5]);
              eat();
              signal(fork[(i + 1) % 5]);
              signal(fork[i]);
              signal(room);
         }
    }

 Why no deadlock: When at most four philosophers may compete, at least one of the five
 forks is not held by a participating philosopher during any configuration of “each holds one
 fork,” so the complete 5-way circular wait cannot occur. Some participant can obtain a
 second fork and finish. Caveat: this proves deadlock freedom, not unconditional
 starvation freedom, if the semaphore implementation is unfair.

 C routines corresponding to the pseudocode:

    #include <semaphore.h>
    #define N 5
    sem_t forks[N], room;

    void take_forks(int i) {
         sem_wait(&room);
         sem_wait(&forks[i]);
         sem_wait(&forks[(i + 1) % N]);
    }
    void put_forks(int i) {
         sem_post(&forks[(i + 1) % N]);
         sem_post(&forks[i]);
         sem_post(&room);
    }
    /* In main: sem_init(&room,0,4); initialize each fork to 1. */

 Explanation: philosophers invoke take_forks(i) before eat() , then put_forks(i) after
 finishing. room=4 removes the possibility that all five simultaneously hold their left fork and
 block. This is deadlock-free provided holders eventually finish eating.

 Q4. Write a C program to solve Dining Philosophers using semaphores.

 Answer:

 Complete C / Pthreads / POSIX semaphore program ( gcc dining.c -pthread -o
 dining ):

    #include <stdio.h>
    #include <pthread.h>
    #include <semaphore.h>

    #define N 5
    #define ROUNDS 2
    sem_t fork_sem[N], room;

    void *philosopher(void *arg) {
         int i = *(int *)arg;
         for (int round = 0; round < ROUNDS; round++) {
              printf("P%d thinking
    ", i);
              sem_wait(&room);                           // max 4 contenders
              sem_wait(&fork_sem[i]);
              sem_wait(&fork_sem[(i + 1) % N]);

              printf("P%d eating (round %d)
    ", i, round + 1);
              /* eating work */

              sem_post(&fork_sem[(i + 1) % N]);
              sem_post(&fork_sem[i]);
              sem_post(&room);
         }
         return NULL;
    }

    int main(void) {
         pthread_t t[N];
         int id[N];
         sem_init(&room, 0, N - 1);
         for (int i = 0; i < N; i++)
              sem_init(&fork_sem[i], 0, 1);

         for (int i = 0; i < N; i++) {
              id[i] = i;
              pthread_create(&t[i], NULL, philosopher, &id[i]);
         }
         for (int i = 0; i < N; i++)
              pthread_join(t[i], NULL);

         for (int i = 0; i < N; i++)
              sem_destroy(&fork_sem[i]);
         sem_destroy(&room);
         return 0;
    }

 Steps: (1) create five fork semaphores, each 1; (2) initialize room=4 ; (3) create five
 philosopher threads; (4) each takes the room permit and both forks before eating; (5) after
 eating, it releases both forks and room; (6) join and clean up. Why correct: neighbors
 cannot use the same fork concurrently; at most four contenders eliminates complete circular
 deadlock. Output order may differ on each run because scheduling is concurrent. The
 room-limit method is taken from Unit 3, p. 39; complete runnable C is supplemental.

 Q5. Design a solution guaranteed free from both deadlock and starvation.

 Answer:

RVCE • Unit II & III • Exam Revision                                                     82 / 85OS CIE 2 | Complete Solved Question Bank

 Provably deadlock-free and starvation-free (under finite eating and fair
 scheduling): FIFO waiter/host monitor. This conservative solution allows one
 philosopher to eat at a time, ensuring both forks are available. It sacrifices concurrency
 in exchange for an easy fairness proof.

    Shared in monitor:
         nextTicket = 0
         servingTicket = 0
         condition turnChanged

    pickup(i):
         myTicket = nextTicket
         nextTicket = nextTicket + 1
         while myTicket != servingTicket:
              wait(turnChanged)        // release monitor while sleeping
         // i now owns the dining permission for both forks

    putdown(i):
         servingTicket = servingTicket + 1
         broadcast(turnChanged)

    Philosopher i:
         while true:
              think()
              pickup(i)
              eat()                    // keep exclusive permission until finished
              putdown(i)

 Mutual exclusion: Only the philosopher whose ticket equals servingTicket may eat.
 Deadlock freedom: no philosopher waits while owning a fork or a different needed lock;
 the current ticket-holder can eat and release. Starvation freedom: all requests receive
 monotonically increasing FIFO tickets; a philosopher is preceded by only finitely many older
 tickets. If every meal eventually finishes and threads are eventually scheduled, the ticket is
 eventually served. Trade-off: concurrency is limited (one eater at a time), but it satisfies the
 two requested liveness properties.

 Note: a room semaphore set to 4 prevents deadlock but by itself does not guarantee
 starvation freedom. The ticket-host approach explicitly imposes FIFO admission; this is why it
 satisfies both requirements. For higher concurrency, a more sophisticated fair central waiter
 can grant non-adjacent philosophers together while preserving FIFO progress.

 Q6. Explain the Dining Philosophers problem with an algorithm.

 Answer:

 Problem: Five philosophers sit around a circular table, each alternating between thinking
 and eating. Five forks/chopsticks lie between adjacent philosophers. Philosopher i requires
 both adjacent forks fork[i] and fork[(i+1)%5] to eat, and releases both afterward (Unit 3,
 pp. 38–40).

 Simple, unsafe code:

RVCE • Unit II & III • Exam Revision                                                         83 / 85OS CIE 2 | Complete Solved Question Bank

    wait(fork[i]);
    wait(fork[(i+1)%5]);
    eat();
    signal(fork[(i+1)%5]);
    signal(fork[i]);

 Deadlock trace: If all five pick up their left fork first, every fork is held by one philosopher.
 Each then waits for the right fork held by a neighbor. All five wait forever in a circular chain.
 Possible remedies from Unit 3, p. 39: (i) permit at most four philosophers to try at a
 time, (ii) make acquisition of both forks atomic, or (iii) asymmetric order (odd/even
 philosophers pick in opposite orders). Starvation requires a separate fairness argument.

 Deadlock-free semaphore algorithm (room limit):

    semaphore room = 4;
    semaphore fork[5] = {1, 1, 1, 1, 1};

    void philosopher(int i) {
         while (true) {
              think();
              wait(room);                // at most 4 contenders
              wait(fork[i]);
              wait(fork[(i + 1) % 5]);
              eat();
              signal(fork[(i + 1) % 5]);
              signal(fork[i]);
              signal(room);
         }
    }

 Why no deadlock: When at most four philosophers may compete, at least one of the five
 forks is not held by a participating philosopher during any configuration of “each holds one
 fork,” so the complete 5-way circular wait cannot occur. Some participant can obtain a
 second fork and finish. Caveat: this proves deadlock freedom, not unconditional
 starvation freedom, if the semaphore implementation is unfair.

 Algorithm walkthrough: P0 requests room, fork0 and fork1, eats, then releases fork1,
 fork0 and room. P1 may hold fork1 only after P0 releases it; while one philosopher is eating,
 neither immediate neighbor can eat, but non-adjacent philosophers may eat concurrently.
 Since only four may compete for forks, a circular wait involving all five is broken. Answer:
 the modified semaphore algorithm provides mutual exclusion and avoids deadlock; fairness
 requires FIFO admission or another starvation-prevention rule.
